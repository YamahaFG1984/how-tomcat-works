第 10 章

安全

Web 应用里有些内容只能给特定的人看。Servlet 规范允许在 web.xml 里声明「安全约束」， 容器负责执行它。Tomcat 的做法再次用到了管道：它往 Context 的管道里装一个叫认证器（authenticator）的阀， 在请求到达 Servlet 之前检查用户的身份。认证器自己不知道谁是合法用户，它要去问域（Realm）。

本章目标

  • 认识安全相关的几个对象：Realm、Principal、角色、SecurityConstraint、LoginConfig
  • 理解认证器阀在管道中的位置，以及它如何拦截未认证的请求
  • 弄清 HTTP Basic 认证的完整往返过程
  • 理解 ContextConfig 如何根据 auth-method 动态安装认证器

认证器是一个阀

认证器阀在启动时被装进 Context 的管道。它调用 Context 关联的 Realm 的 authenticate 方法：认证成功就调用下一个阀，最终显示 Servlet；失败就直接返回，用户看不到 Servlet。

安全相关的对象

Realm

Realm（域）是用来认证用户的组件：给它用户名和密码，它告诉你对不对。一个容器只能有一个 Realm，通过 setRealm 关联，通常挂在 Context 上。Realm 里最重要的是四个 authenticate 重载（第一个最常用）和 hasRole：

public Principal authenticate(String username, String credentials);
public Principal authenticate(String username, byte[] credentials);
public Principal authenticate(String username, String digest, String nonce, String nc,
                              String cnonce, String qop, String realm, String md5a2);   // DIGEST
public Principal authenticate(X509Certificate certs[]);                                 // 客户端证书
public boolean hasRole(Principal principal, String role);

抽象类 RealmBase 提供基础实现，具体实现有 JDBCRealm（数据库）、JNDIRealm（LDAP）、MemoryRealm（默认，启动时读 tomcat-users.xml）、UserDatabaseRealm。

GenericPrincipal

java.security.Principal 代表一个已认证的身份，Catalina 的实现是 GenericPrincipal：它总是关联一个 Realm，有名字、密码和一组角色。角色数组在构造时排好序，hasRole 用二分查找。Tomcat 5 支持 Servlet 2.4，角色 * 表示「任何人」：

public boolean hasRole(String role) {
    if ("*".equals(role))          // Servlet 2.4：特殊角色，表示所有人
        return true;
    if (role == null)
        return (false);
    return (Arrays.binarySearch(roles, role) >= 0);
}

LoginConfig

org.apache.catalina.deploy.LoginConfig 包含域名和认证方式。认证方式必须是 BASIC、DIGEST、FORM、CLIENT-CERT 之一；FORM 方式还要提供登录页和错误页的地址。认证器会把域名发给浏览器显示在登录对话框里，没有域名时发送「服务器名:端口」。

Authenticator

org.apache.catalina.Authenticator 是一个没有任何方法的标记接口，让其他组件可以用 instanceof 判断某个阀是不是认证器。

NonLoginAuthenticator 用于没有指定 auth-method 的情况：它只检查安全约束，不做用户认证。

安装认证器阀

部署描述符里 login-config 只能出现一次，所以一个 Context 只有一个 LoginConfig、只用一种认证器。用哪个类取决于 auth-method：

auth-method认证器类
BASICBasicAuthenticator
FORMFormAuthenticator
DIGESTDigestAuthenticator
CLIENT-CERTSSLAuthenticator
（未指定，即 NONE）NonLoginAuthenticator

因为认证器类直到运行时才知道，所以要动态加载。正式的 Tomcat 里由 ContextConfig（第 15 章）完成；本章的 SimpleContextConfig 在 Context 的 START 事件里调用 authenticatorConfig()：

private synchronized void authenticatorConfig() {
    SecurityConstraint constraints[] = context.findConstraints();
    if ((constraints == null) || (constraints.length == 0))
        return;                                                   // ① 没有约束，不需要认证器
    LoginConfig loginConfig = context.getLoginConfig();
    if (loginConfig == null) {
        loginConfig = new LoginConfig("NONE", null, null, null);
        context.setLoginConfig(loginConfig);
    }
    Pipeline pipeline = ((StandardContext) context).getPipeline();
    if (pipeline != null) {                                       // ② 已经装过认证器了吗？
        Valve basic = pipeline.getBasic();
        if ((basic != null) && (basic instanceof Authenticator))
            return;
        Valve valves[] = pipeline.getValves();
        for (int i = 0; i < valves.length; i++) {
            if (valves[i] instanceof Authenticator)
                return;
        }
    } else {
        return;
    }
    if (context.getRealm() == null)                               // ③ 没有 Realm 就无从认证
        return;
    String authenticatorName = "org.apache.catalina.authenticator.BasicAuthenticator";
    try {                                                         // ④ 动态加载并装进管道
        Class authenticatorClass = Class.forName(authenticatorName);
        Valve authenticator = (Valve) authenticatorClass.newInstance();
        ((StandardContext) context).addValve(authenticator);
        System.out.println("Added authenticator valve to Context");
    } catch (Throwable t) {
    }
}

Java 17 对照版

源码java17/src/main/java/modern/ch10/realm/authenticator/core/startup/tomcat/EmbeddedSecurity.javajava17/conf/tomcat-users.xml

Java 17 版在迷你容器上完整实现了「约束 → 认证器阀 → 域 → Principal」这条链，同时修正了原书中几个今天看来不能接受的安全做法。

① 认证器阀的判断流程

@Override
public void invoke(HttpRequest request, HttpResponse response, ValveContext next) throws Exception {
    Optional<SecurityConstraint> constraint = context.findConstraints().stream()
            .filter(c -> c.matches(request.getRequestURI(), request.getMethod()))
            .findFirst();
    if (constraint.isEmpty()) {
        next.invokeNext(request, response);
        return;
    }
    Principal principal = authenticate(request.getHeader("Authorization"));
    if (principal == null) {
        response.setHeader("WWW-Authenticate", "Basic realm=\"" + realmName + "\", charset=\"UTF-8\"");
        response.sendError(HttpServletResponse.SC_UNAUTHORIZED, null);
        return;                                       // 不调用 invokeNext：Servlet 不会被执行
    }
    boolean allowed = constraint.get().roles().stream()
            .anyMatch(role -> context.getRealm().hasRole(principal, role));
    if (!allowed) {
        response.sendError(HttpServletResponse.SC_FORBIDDEN, null);
        return;
    }
    request.setUserPrincipal(principal, role -> context.getRealm().hasRole(principal, role));
    next.invokeNext(request, response);
}

private Principal authenticate(String authorization) {
    if (authorization == null || !authorization.regionMatches(true, 0, "Basic ", 0, 6)) return null;
    String decoded = new String(Base64.getDecoder().decode(authorization.substring(6).trim()), UTF_8);   // Java 8 Base64
    int colon = decoded.indexOf(':');
    return colon < 0 ? null
         : context.getRealm().authenticate(decoded.substring(0, colon), decoded.substring(colon + 1));
}
💡 调试时发现的一个规范细节

第一次测试时，401 响应里竟然没有 WWW-Authenticate 头。原因是第 3 章 HttpResponse.sendError() 里调用了 reset()，把已经设置的响应头也清掉了。Servlet 规范说 sendError 只清空缓冲的正文，响应头要保留——改成 resetBuffer() 后就正常了。

ⓘ 原书之后的变化
  • Tomcat 8 引入 CredentialHandler：Realm 可以配置 SecretKeyCredentialHandler（PBKDF2）存储加盐哈希，而不是明文。
  • Servlet 3.0 增加了编程式安全：request.login(user, pass)、logout()、authenticate(response)，以及 @ServletSecurity 注解。
  • JDBCRealm 已被删除，改用基于连接池的 DataSourceRealm；Jakarta Authentication（JASPIC）允许插入第三方认证模块。
  • 现代应用更多使用 OAuth 2 / OpenID Connect、JWT，通常由 Spring Security 等框架在应用层实现。

设计要点

这一章的代码里有几个可以带到别的项目里的设计决定。每条按「做法 → 取舍 → 替代方案 → 还能用在哪」来写；系统的讨论见设计篇。

1认证方式和用户存储正交

Authenticator（BASIC/FORM/DIGEST）负责「怎么问用户要凭据」，Realm（内存/JDBC/LDAP）负责「凭据对不对」。

取舍
两个维度任意组合，3 种认证 × 3 种存储不需要 9 个类。
还能用在
Spring Security 的 AuthenticationFilter + AuthenticationProvider / UserDetailsService 是同样的拆分。
延伸：第 30 章 · 扩展点设计
2声明式安全

受保护的 URL、需要的角色写在 web.xml 的 <security-constraint> 里，不写在 Servlet 代码里。

取舍
集中、可审计、不会漏写；但粒度只到 URL，细粒度权限还得写代码。
替代方案
代码里 if (!user.hasRole())（容易遗漏）。
还能用在
把「谁能访问什么」集中成一张表，代码只负责检查。
延伸：第 29 章 · 整体架构：分层与边界
3安全检查放在必经之路上

认证器是一个阀，加在 Context 管道里，所有请求都会经过。

取舍
单一入口，不会有绕过的路径；但要注意顺序——它必须在业务阀之前。
还能用在
网关鉴权、统一的拦截器；不要把权限检查分散在每个接口里。
延伸：第 30 章 · 扩展点设计
4密码不存明文，比较要常量时间

原书的 SimpleRealm 明文比较；Java 17 版改为 PBKDF2 加盐哈希，并用 MessageDigest.isEqual 比较。

取舍
计算慢一些（这正是目的）；常量时间比较防止计时攻击。
替代方案
bcrypt、scrypt、Argon2。
还能用在
任何存储凭据的系统。
延伸：第 32 章 · 并发、隔离与演进

小结

  • 安全约束由一个认证器阀执行，它位于 Context 管道里、Wrapper 之前；认证失败就不调用下一个阀。
  • 认证器调用 Realm 的 authenticate，成功时得到代表用户的 Principal（GenericPrincipal）。
  • SecurityConstraint 描述「哪些 URL/方法需要哪些角色」，LoginConfig 描述认证方式和域名。
  • 认证器类由 auth-method 决定，在 Context 启动时由 ContextConfig 动态安装。
  • 现代实践：密码加盐慢哈希、常数时间比较、HTTPS、禁用 XML 外部实体。
