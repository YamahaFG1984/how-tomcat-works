第 11 章

StandardWrapper

前几章我们一直用自己写的 SimpleWrapper。这一章看 Catalina 里真正的 Wrapper 实现：StandardWrapper。 它负责加载 Servlet、分配实例、为 Servlet 准备 ServletConfig；它的基础阀 StandardWrapperValve 则负责一件我们还没碰过的事——执行过滤器链，最后才调用 Servlet 的 service。

本章目标

  • 完整走一遍：从连接器收到请求到 Servlet 的 service 被调用，中间经过了哪些方法
  • 理解 SingleThreadModel 的真实含义，以及 StandardWrapper 如何为它维护实例池
  • 理解 StandardWrapper 为什么同时是 ServletConfig，以及 StandardWrapperFacade 的作用
  • 理解过滤器链：FilterDef、ApplicationFilterConfig、ApplicationFilterChain

一个请求的完整调用序列

注意分工：StandardWrapper 只负责加载和分配 Servlet，它不调用 service；调用 service 的是它管道里的基础阀 StandardWrapperValve。

SingleThreadModel

实现了 javax.servlet.SingleThreadModel 接口的 Servlet 俗称 STM Servlet。规范的原话是：

ⓘ Servlet 2.4 规范 SRV.14.2.24

如果 Servlet 实现了这个接口，可以保证不会有两个线程同时执行同一个 Servlet 实例的 service 方法。容器可以通过同步访问单个实例来保证这一点，也可以维护一个 Servlet 实例池、把每个新请求分派给空闲的实例。这个接口并不能防止访问共享资源（如静态变量、Servlet 之外的类）时出现的同步问题。

分配 Servlet：allocate()

StandardWrapperValve 调用 wrapper.allocate() 获得 Servlet 实例。由于要支持 STM，allocate 分成两部分：

非 STM：只有一个实例
if (!singleThreadModel) {
    if (instance == null) {
        synchronized (this) {
            if (instance == null) {
                instance = loadServlet();
            }
        }
    }
    countAllocated++;
    return (instance);
}
STM：从实例池里取
synchronized (instancePool) {
    while (countAllocated >= nInstances) {
        if (nInstances < maxInstances) {   // 默认 20
            instancePool.push(loadServlet());
            nInstances++;
        } else {
            instancePool.wait();          // 等别人归还
        }
    }
    countAllocated++;
    return (Servlet) instancePool.pop();
}

非 STM Servlet 只加载一次，之后所有请求共用同一个实例——Servlet 程序员要自己处理并发访问共享资源的问题。归还实例时调用 deallocate()，它会 countAllocated--，STM 的情况下还会把实例压回池里并 notify。

加载 Servlet：loadServlet()

  1. 非 STM 且已有实例 → 直接返回。
  2. 开始捕获 System.out/System.err，以便稍后写进 ServletContext 的日志。
  3. 确定类名：通常是 servletClass；如果是 JSP 页面，则用 JSP Servlet 的类名。类名为空 → 抛异常。
  4. 取得 Loader 及其类加载器。如果是 org.apache.catalina 包下的容器提供的特殊 Servlet，改用 Catalina 自己的类加载器，使其能访问容器内部（第 19 章）。
  5. 加载类、实例化；检查 isServletAllowed()；如果是 ContainerServlet，调用 setWrapper(this)。
  6. 触发 BEFORE_INIT_EVENT，调用 servlet.init(facade)；load-on-startup 的 JSP 还会预编译；触发 AFTER_INIT_EVENT。
  7. 如果是 STM Servlet，创建实例池；停止捕获输出，返回实例。

ServletConfig 与 StandardWrapperFacade

servlet.init() 需要一个 ServletConfig。StandardWrapper 自己就实现了这个接口——Servlet 的名字就是 Wrapper 的名字，初始化参数就存在 Wrapper 的 parameters 表里：

public String getServletName() { return (getName()); }

public String getInitParameter(String name) { return (findInitParameter(name)); }

public ServletContext getServletContext() {
    if (parent == null)
        return (null);
    else if (!(parent instanceof Context))
        return (null);
    else
        return (((Context) parent).getServletContext());   // 所以 Wrapper 必须放在 Context 里
}

public void addChild(Container child) {
    throw new IllegalStateException(sm.getString("standardWrapper.notChild"));
}

public void setParent(Container container) {
    if ((container != null) && !(container instanceof Context))
        throw new IllegalArgumentException(sm.getString("standardWrapper.notContext"));

}

StandardWrapperValve 与过滤器链

StandardWrapperValve 做两件事：执行与该 Servlet 相关的所有过滤器，然后调用 Servlet 的 service。它的 invoke 方法依次：

  1. wrapper.allocate() 取得 Servlet 实例；
  2. createFilterChain() 创建过滤器链；
  3. filterChain.doFilter()——这一步最终会调用 service()；
  4. 释放过滤器链；
  5. wrapper.deallocate(servlet)；
  6. 如果 Servlet 被标记为永久不可用，调用 wrapper.unload()。

FilterDef 与 ApplicationFilterConfig

FilterDef 对应 web.xml 中的 <filter> 元素（过滤器名、类名、初始化参数等）。ApplicationFilterConfig 实现 javax.servlet.FilterConfig，负责在 Web 应用启动时创建并管理过滤器实例：

Filter getFilter() throws ... {
    if (this.filter != null)
        return (this.filter);                         // 每个过滤器只有一个实例
    String filterClass = filterDef.getFilterClass();
    ClassLoader classLoader = null;
    if (filterClass.startsWith("org.apache.catalina."))
        classLoader = this.getClass().getClassLoader();   // 容器自带的过滤器
    else
        classLoader = context.getLoader().getClassLoader();
    Class clazz = classLoader.loadClass(filterClass);
    this.filter = (Filter) clazz.newInstance();
    filter.init(this);                                // 它自己就是 FilterConfig
    return (this.filter);
}

ApplicationFilterChain

ApplicationFilterChain 实现 javax.servlet.FilterChain。它的 doFilter 调用链上第一个过滤器的 doFilter，并把自己作为第三个参数传进去；过滤器调用 chain.doFilter() 就会进入下一个过滤器；最后一个过滤器之后，就是 Servlet 的 service。

🔑 阀 vs 过滤器

两者长得几乎一样，区别在于归属：阀是 Tomcat 的扩展点，配置在 server.xml 里，可以作用于 Engine/Host/Context/Wrapper，能拿到容器内部对象；过滤器是 Servlet 规范的扩展点，配置在应用自己的 web.xml 里，任何 Servlet 容器都能用，只能拿到标准的请求和响应。

② 过滤器链只需十几行

public class ApplicationFilterChain implements FilterChain {
    private final List<Filter> filters;
    private final Servlet servlet;
    private int pos;

    @Override
    public void doFilter(ServletRequest request, ServletResponse response) throws IOException, ServletException {
        if (pos < filters.size()) {
            filters.get(pos++).doFilter(request, response, this);   // 把自己传给过滤器
        } else {
            servlet.service(request, response);
        }
    }
}

@Override
public void invoke(HttpRequest request, HttpResponse response, ValveContext valveContext) throws Exception {
    Servlet servlet = wrapper.allocate();
    try {
        var chain = createFilterChain(request, servlet);
        chain.doFilter(Facade.of(HttpServletRequest.class, request), Facade.of(HttpServletResponse.class, response));
    } finally {
        wrapper.deallocate(servlet);              // try/finally：抛异常也要归还
    }
}

private ApplicationFilterChain createFilterChain(HttpRequest request, Servlet servlet) throws ServletException {
    var context = (StandardContext) wrapper.getParent();
    List<Filter> filters = new ArrayList<>();
    for (FilterMap map : context.findFilterMaps()) {          // filter-mapping 的顺序就是执行顺序
        if (map.matches(request.getRequestURI())) {
            filters.add(context.findFilterConfig(map.filterName()).getFilter());
        }
    }
    return new ApplicationFilterChain(filters, servlet);
}

FilterDef、FilterMap 都写成了 record：原书的 FilterDef 用了 100 多行 getter/setter 来表达「一组数据」。

③ SingleThreadModel 已被删除，但池化思想还在

SingleThreadModel 在 Servlet 6.0（Tomcat 10.1）中被彻底删除，Java 17 版无法也不应该再实现它。但原书实例池的思想很有价值，InstancePool 用 Semaphore 重写了它：

原书：Stack + wait/notify + 3 个计数器
synchronized (instancePool) {
    while (countAllocated >= nInstances) {
        if (nInstances < maxInstances) {
            instancePool.push(loadServlet());
            nInstances++;
        } else {
            instancePool.wait();
        }
    }
    countAllocated++;
    return (Servlet) instancePool.pop();
}
Java 17：Semaphore + 并发队列
private final Semaphore permits =
    new Semaphore(maxInstances, true);
private final Deque<T> idle = new ConcurrentLinkedDeque<>();

public T allocate() throws InterruptedException {
    permits.acquire();               // 借满了就阻塞
    T instance = idle.pollFirst();
    return instance != null ? instance : factory.get();
}

public void deallocate(T instance) {
    idle.offerFirst(instance);
    permits.release();               // 唤醒一个等待者
}

设计要点

这一章的代码里有几个可以带到别的项目里的设计决定。每条按「做法 → 取舍 → 替代方案 → 还能用在哪」来写；系统的讨论见设计篇。

1单实例 + 多线程，要求 Servlet 无状态

默认一个 Servlet 实例服务所有请求，并发安全由 Servlet 自己负责。

取舍
没有实例创建和池化的开销；代价是开发者必须理解「实例字段是共享的」。
还能用在
Spring 的单例 Controller/Service 也是如此：把状态放在方法局部变量、请求对象或外部存储中。
延伸：第 32 章 · 并发、隔离与演进
2被推翻的设计：SingleThreadModel

STM Servlet 用实例池保证「一个实例同时只服务一个请求」。Servlet 2.4 废弃，6.0 移除。

取舍
它给了虚假的安全感：静态变量、Session、外部资源仍然共享；实例池还限制了吞吐。
还能用在
并发安全不能靠框架「魔法」兜底，要靠无状态设计和明确的同步。
延伸：第 32 章 · 并发、隔离与演进
3过滤器链用下标推进

ApplicationFilterChain 保存过滤器数组和当前位置，每次 doFilter 前进一格，走完调用 Servlet。

取舍
和 ValveContext 一样是外部迭代器；Filter 是规范接口，所以这个结构一直保留下来。
还能用在
实现可短路、可前后包裹的中间件链时，这是最直接的写法。
延伸：第 31 章 · 设计模式实战
4懒加载 vs load-on-startup

默认第一次请求时才加载 Servlet；配置 load-on-startup 后在启动时加载。

取舍
懒加载启动快，但第一次请求慢，初始化错误也要等到有人访问才暴露。
还能用在
关键组件启动时预热并做健康检查，非关键组件懒加载。
延伸：第 32 章 · 并发、隔离与演进
5卸载前等待正在处理的请求

countAllocated 记录正在使用的实例数，unload() 等它降到 0（有超时）再调用 destroy()。

取舍
优雅停机要多等一会儿，但不会在请求处理中途销毁对象。
还能用在
优雅停机的通用写法：停止接收新请求 → 等待在途请求 → 超时强制关闭。
延伸：第 32 章 · 并发、隔离与演进

小结

  • 请求依次经过 Context 管道 → StandardContextValve → Wrapper 管道 → StandardWrapperValve → 过滤器链 → Servlet。
  • StandardWrapper 负责加载和分配 Servlet；非 STM Servlet 只有一个实例，STM Servlet 有一个最多 20 个实例的池。
  • SingleThreadModel 不能保证线程安全，已被废弃并在 Servlet 6.0 删除。
  • StandardWrapper 实现 ServletConfig，但交给 Servlet 的是 StandardWrapperFacade；Wrapper 必须放在 Context 里。
  • StandardWrapperValve 创建 ApplicationFilterChain，过滤器通过 chain.doFilter 层层传递，最后调用 service。

动手练习

  1. 写一个过滤器，当请求参数 block=1 时直接返回 403、不调用 chain.doFilter。验证 Servlet 没有被执行，TimingFilter 仍然打印了耗时。
  2. 交换两个 addFilterMap 的顺序，观察过滤器执行顺序的变化。
  3. 给 Java 17 版的 StandardWrapper 加上 loadOnStartup 属性：值 ≥ 0 的 Wrapper 在 Context 启动时就调用 allocate()。
  4. 写一个线程不安全的 Servlet（用实例字段计数），用 ab 或 wrk 压测，观察计数错误；再用 AtomicInteger 修好它。
