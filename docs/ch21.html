ServletContext 与 RequestDispatcher

原书讲完了容器怎么把请求送到 Servlet，却没讲 Servlet 之间怎么协作。 这一章补上两块日常开发天天用到的拼图：代表整个 Web 应用的 ServletContext， 以及在服务器内部把请求「转交」给另一个 Servlet 的 RequestDispatcher。 我们会看到 forward 和 include 并不产生新请求，而是把同一个请求包一层再交出去。

本章目标

  • 知道 ServletContext 在 Tomcat 里由谁实现、和 StandardContext 是什么关系
  • 分清 request、session、application 三种作用域的生命周期
  • 说出 forward、include、sendRedirect 的区别，以及各自对路径、参数、响应的影响
  • 理解 Tomcat 如何用包装器（ApplicationHttpRequest）实现分派
  • 知道过滤器为什么要声明 DispatcherType

ServletContext：一个应用一份

第 12 章的 StandardContext 是容器眼里的 Web 应用；而 Servlet 眼里的 Web 应用是 jakarta.servlet.ServletContext。Tomcat 用 org.apache.catalina.core.ApplicationContext 实现这个接口，每个 StandardContext 持有一个。交给 Servlet 的不是它本身，而是外观 ApplicationContextFacade——第 2 章的外观模式又出现了。

它主要提供四类能力：

能力方法典型用途
应用级属性get/setAttribute全局缓存、计数器、Spring 的根容器（WebApplicationContext 就存在这里）
初始化参数getInitParameterweb.xml 的 <context-param>，例如配置文件位置
资源访问getResource、getResourceAsStream、getRealPath读取 WAR 里的文件，不管它是目录还是压缩包
分派与注册getRequestDispatcher、getNamedDispatcher、addServlet…本章主题；addServlet 等编程式注册见第 25 章

三种作用域

请求属性、会话属性、应用属性用的是同一组方法名，区别只在活多久、谁能看到。 选错作用域是新手最常见的 bug 来源之一：把用户数据放进 ServletContext，所有用户都会看到。

⚠️ 应用属性会被并发访问

ApplicationContext 的属性表本身是 ConcurrentHashMap，放进去的值却要自己保证线程安全。 计数器用 AtomicLong 而不是 Long：get 出来加一再 set 回去会丢更新。

forward、include、redirect

一个请求经常需要多个 Servlet 合作：控制器处理业务，再交给视图渲染；页面由头部、正文、尾部拼起来。 Servlet 规范提供了两种服务器内部的分派方式，外加一种让浏览器重新发请求的方式：

forwardincludesendRedirect

谁写响应只有目标调用方 + 目标第二个请求的处理者
调用前已写的内容被 resetBuffer() 清掉；已提交则抛 IllegalStateException保留被清掉
目标看到的 getRequestURI()目标路径原路径新路径

典型用途MVC：控制器 → 视图公共页头、页脚表单提交后跳转（PRG 模式）、登录后跳回

获取分派器有三种方式，区别在于路径怎么解释：

// ① 相对上下文根，必须以 "/" 开头
getServletContext().getRequestDispatcher("/WEB-INF/views/product?lang=zh");
// ② 也可以是相对当前请求的路径（不以 "/" 开头），Tomcat 会先拼成绝对路径
request.getRequestDispatcher("detail");
// ③ 按 Servlet 名字：不经过 URL 映射，路径信息保持不变，也不设置 forward/include 属性
getServletContext().getNamedDispatcher("fragment");

forward 的内部：给请求套一层

Tomcat 的实现类是 org.apache.catalina.core.ApplicationDispatcher。 创建它时，ApplicationContext.getRequestDispatcher() 已经用第 12 章那套映射规则（今天由 Mapper 完成） 找到了目标 Wrapper，并算好了目标的 servletPath、pathInfo、查询串。 调用 forward() 时它做这几件事：

  1. 检查响应是否已提交。提交了就抛 IllegalStateException——响应头已经发给浏览器，没法反悔。
  2. response.resetBuffer()：调用方写进缓冲区、还没发出去的内容全部丢掉。
  3. 用 ApplicationHttpRequest 把原请求包起来：路径方法返回目标路径，查询参数合并（新的优先）， 并在这一层放上 jakarta.servlet.forward.request_uri 等属性记录原始路径（嵌套 forward 时保留最初的值）。
  4. 为目标构建过滤器链（只包含声明了 FORWARD 的过滤器），然后调用目标 Wrapper 的 Servlet。
  5. 返回后关闭响应：调用方在 forward() 之后写的任何东西都会被丢弃。

为什么包装而不是复制？因为请求属性就是 Servlet 之间传数据的通道：控制器 setAttribute("product", …)， 视图 getAttribute("product")。包装层只拦截路径和参数相关的方法，其他调用原样传给里面那层， 属性自然是共享的。forward 返回后包装层被丢弃，调用方看到的又是原来的路径。

include：只许写响应体

include 的请求包装和 forward 类似，但方向相反：getRequestURI() 等方法仍返回原路径（片段通常不关心自己在哪）， 目标路径放在 jakarta.servlet.include.* 属性里。响应也要包一层 ApplicationHttpResponse， 它的 included 标志为真时，所有改状态码和响应头的调用都直接 return：

规范这样设计的理由很简单：调用方决定这是一个什么样的响应（状态码、类型、缓存策略），片段只是其中的一部分。 如果片段能改状态码，那么页脚里的一个 bug 就能把整个页面变成 500。

分派类型与过滤器

第 11 章的过滤器链默认只在来自客户端的请求上执行。分派时会不会再执行一遍过滤器， 取决于过滤器映射声明的 DispatcherType：

DispatcherType什么时候典型过滤器
REQUEST（默认）客户端发来的请求认证、日志、编码设置
FORWARDforward() 到目标时视图层的通用处理（如模板变量注入）
INCLUDEinclude() 目标时很少用
ERROR容器转到 error-page 时（第 22 章）错误页也需要的过滤器（如字符编码）
ASYNCAsyncContext.dispatch() 时（第 24 章）需要在异步分派后再执行的过滤器
🔑 为什么默认只拦截 REQUEST？

想象一个认证过滤器：如果它也拦截 FORWARD，那么用户访问 /products/42 被认证一次， 控制器 forward 到视图时又被认证一次；一个页面 include 了十个片段就认证十一次。 大多数横切逻辑只应该在「请求进入应用」时执行一次。

另外，过滤器的 URL 模式匹配的是分派路径。按名字分派（getNamedDispatcher）没有路径， 所以只有按 servlet-name 映射的过滤器会执行——下面的运行结果能看到这一点。

① forward：检查、清空、包装、调用、关闭

@Override
public void forward(ServletRequest req, ServletResponse resp) throws ServletException, IOException {
    var request = (HttpServletRequest) req;
    var response = (HttpServletResponse) resp;
    if (response.isCommitted()) {
        throw new IllegalStateException("响应已经提交，不能再 forward（Tomcat 抛同样的异常）");
    }
    response.resetBuffer();                           // 调用方之前写进缓冲区的内容全部作废

    var wrapped = new DispatchedRequest(request, DispatcherType.FORWARD,
            requestURI, servletPath, pathInfo, queryString);
    // 嵌套 forward 时保留最初的值：属性描述的是「客户端原本请求的是什么」
    if (request.getAttribute(FORWARD_REQUEST_URI) == null) {
        wrapped.special(FORWARD_REQUEST_URI, request.getRequestURI());
        wrapped.special(FORWARD_SERVLET_PATH, request.getServletPath());
        wrapped.special(FORWARD_QUERY_STRING, request.getQueryString());
        // …context_path、path_info 同理
    }
    servlet.service(wrapped, response);
    // forward 返回时响应就结束了：调用方之后再写的内容都会被丢弃
    ...
}

② 包装器：只覆盖路径和参数

HttpServletRequestWrapper 是规范自带的装饰器基类，所有方法默认委托给被包装的请求。 我们只覆盖需要「换答案」的几个方法；setAttribute 没覆盖，自然穿透到原请求。 

final class DispatchedRequest extends HttpServletRequestWrapper {

    private final Map<String, Object> special = new HashMap<>();   // forward.* / include.* 属性
    private Map<String, String[]> params;

    @Override public DispatcherType getDispatcherType() { return type; }
    @Override public String getRequestURI() { return requestURI; }
    @Override public String getServletPath() { return servletPath; }
    @Override public String getParameter(String name) {
        String[] v = params.get(name);
        return v == null ? null : v[0];
    }

    void mergeQuery(String query) {                    // 分派路径上的参数优先
        var merged = new LinkedHashMap<String, String[]>(QueryString.parse(query));
        getRequest().getParameterMap().forEach(merged::putIfAbsent);
        params = Collections.unmodifiableMap(merged);
    }

    @Override public Object getAttribute(String name) {
        Object v = special.get(name);
        return v != null ? v : super.getAttribute(name);
    }
}

④ 嵌入式 Tomcat 11：同样的场景

真实版本不写 web.xml，而是在 ServletContainerInitializer 里编程式注册 Servlet 和过滤器 （第 25 章会细讲这套机制）。注意过滤器映射的第一个参数就是 DispatcherType 集合：

ctx.addParameter("site.name", "Tomcat 教程商店");            // 相当于 <context-param>
ctx.addServletContainerInitializer((classes, sc) -> register(sc), null);

// register(sc) 里：
sc.addServlet("front", new HttpServlet() {
    @Override protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        ((AtomicLong) getServletContext().getAttribute("visits")).incrementAndGet();
        req.setAttribute("product", "商品 #" + req.getPathInfo().substring(1));
        req.getRequestDispatcher("/WEB-INF/views/product?lang=zh").forward(req, resp);

}).addMapping("/products/*");

sc.addFilter("onRequest", onRequest)
  .addMappingForUrlPatterns(EnumSet.of(DispatcherType.REQUEST), false, "/*");
sc.addFilter("onDispatch", onDispatch)
  .addMappingForUrlPatterns(EnumSet.of(DispatcherType.FORWARD, DispatcherType.INCLUDE), false, "/*");
⚠️ 分派路径是 URI，要先编码

第一版代码写的是 getRequestDispatcher("/fragments/header?title=首页")，结果 500： UnmappableCharacterException。Tomcat 把分派路径里的查询串当作 URI 处理，非 ASCII 字符必须先 URLEncoder.encode("首页", UTF_8)。我们的迷你版不做解码所以没暴露这个问题——这也说明， 「自己写一个简化版」之后，一定要和真实实现对照着跑一遍。

Tomcat 的 servletPath 是 /WEB-INF/views（前缀映射），我们的迷你版用的是扩展名映射 *.view， 所以 servletPath 是整个路径——两者都符合第 12 章讲的规则。Servlet 4.0 起还多了一个 FORWARD_MAPPING 属性，用 HttpServletMapping 对象描述原始请求是按哪条规则匹配的。

设计要点

这一章的代码里有几个可以带到别的项目里的设计决定。每条按「做法 → 取舍 → 替代方案 → 还能用在哪」来写；系统的讨论见设计篇。

1包装而不是复制

分派时在原请求外面套一层 ApplicationHttpRequest，只改写路径和参数相关的方法，其余调用穿透。

取舍
属性天然共享、几乎没有拷贝成本；代价是层层包装后调试时要一层层 getRequest() 拆开看，instanceof 判断也会失效。
替代方案
复制一份请求对象（属性要同步回去，容易出错）。
还能用在
中间件需要「临时改写」上下文时（路由前缀剥离、租户切换），用装饰器包一层，退出时丢掉即可。
延伸：第 31 章 · 设计模式实战
2按生命周期划分作用域

request / session / application 三种作用域用同一套 API，只在存活时间和可见范围上不同。

取舍
API 统一好学；但放错作用域不会报错，只会在并发或多用户时出 bug。
还能用在
依赖注入容器的 scope（Spring 的 request / session / singleton）、任务框架的 job / step 上下文：先问「它应该活多久、谁能看到」。
延伸：第 32 章 · 并发、隔离与演进
3元数据由调用方决定

被 include 的片段只能写内容，状态码和响应头的修改被静默忽略。

取舍
局部错误不会破坏整体响应；代价是「静默忽略」让片段作者很难发现自己的设置没生效。
替代方案
抛异常（更显眼，但一个片段的小问题会导致整页失败）。
还能用在
组合式渲染（模板片段、微前端）、插件往宿主输出内容时：给插件一个受限的视图，只开放它该动的部分。
延伸：第 30 章 · 扩展点设计
4服务端分派与客户端重定向各有其位

forward 适合「同一个请求的不同处理阶段」，redirect 适合「这个请求已经结束，请去另一个地方」。

取舍
forward 少一次往返，但刷新页面会重复提交表单；redirect 多一次往返，但地址栏和浏览器历史是正确的。
还能用在
Post/Redirect/Get 模式；API 网关里「内部转发」与「返回 3xx 让客户端跳转」的选择。

小结

  • 每个 Web 应用一个 ServletContext，Tomcat 里是 ApplicationContext，交给 Servlet 的是它的外观。
  • 三种作用域的区别是生命周期和可见范围；应用属性会被并发访问，值本身要线程安全。
  • forward 和 include 不产生新的 HTTP 请求，而是用 ApplicationHttpRequest 包装原请求再调用目标 Servlet。
  • forward 会清空缓冲区并在返回后关闭响应，已提交时抛 IllegalStateException；include 不能修改状态码和响应头。
  • 原始路径（forward）或目标路径（include）保存在 jakarta.servlet.forward.* / include.* 属性里。
  • 过滤器默认只拦截 REQUEST；分派时是否执行取决于映射声明的 DispatcherType。

动手练习

  1. 在迷你版里实现嵌套 forward：A forward 到 B，B 再 forward 到 C。确认 C 看到的 forward.request_uri 仍然是 A 的路径。
