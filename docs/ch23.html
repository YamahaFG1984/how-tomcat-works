Coyote 与 NIO 连接器

第 4 章的默认连接器一个连接占一个线程：客户端不发数据，线程就干等着。 原书出版后不久，Tomcat 就把它换成了名为 Coyote 的连接器框架； 到 Tomcat 8.5，阻塞式（BIO）实现被彻底删除，默认的 HTTP/1.1 连接器变成了基于 Java NIO 的 NioEndpoint。 这一章拆开 Coyote 的分层，自己用 Selector 写一个迷你 NIO 连接器，并用一千个「慢客户端」和第 4 章的连接器正面比较。

本章目标

  • 说出 Coyote 的四层：ProtocolHandler、Endpoint、Processor、Adapter，以及它们和第 4 章类的对应关系
  • 理解阻塞模型的瓶颈在「等待」，以及 Selector 如何让一个线程看住所有空闲连接
  • 掌握 NioEndpoint 的三类线程：Acceptor、Poller、Worker 各自做什么
  • 分清 maxConnections、acceptCount、maxThreads 三个上限
  • 知道 CoyoteAdapter 是协议层和容器之间唯一的接缝

阻塞模型的天花板

回忆第 4 章：HttpProcessor 拿到 socket 后调用 input.read()，客户端没发数据，线程就阻塞在那里。 对一个 keep-alive 连接来说，大部分时间都是在「等下一个请求」：

线程是昂贵的：每个平台线程默认要 512 KB～1 MB 的栈，操作系统调度几千个线程时上下文切换的成本也很可观。 于是连接数被线程数卡死。更糟的是，攻击者只要打开几百个连接、每个都慢慢地发请求头（Slowloris 攻击）， 就能用极少的带宽让服务器拒绝所有正常用户——后面的实验会复现这一点。

NIO：一个线程看住所有连接

Java NIO（JDK 1.4 引入，和原书同一年）提供了 非阻塞 socket 和 Selector： channel.read() 没有数据时立即返回 0 而不是阻塞；Selector 则可以同时监视成千上万个 channel， 调用一次 select() 就告诉你「哪几个连接现在有数据可读」。底层对应 Linux 的 epoll、macOS 的 kqueue。

NioEndpoint 的三类线程

有了 Selector，剩下的问题是怎么分工。Tomcat 的答案是三类线程，用 jstack 或 VisualVM 看任何一个 Tomcat 进程都能看到它们的名字： http-nio-8080-Acceptor、http-nio-8080-Poller、http-nio-8080-exec-1……

  1. Acceptor 阻塞在 accept() 上（只有一个线程，阻塞没关系）。拿到连接后设为非阻塞，交给 Poller。连接数到达 maxConnections 时，它会先停下来不再 accept。
  2. Poller 是唯一操作 Selector 的线程。其他线程想注册或修改关注事件，必须把操作放进它的事件队列再 wakeup()，否则会和正在阻塞的 select() 互相卡住。
  3. 连接可读时，Poller 先把关注事件清零（interestOps(0)），保证同一个连接同一时刻只有一个 Worker 在处理，然后把它交给线程池。
  4. Worker 非阻塞地读取数据。请求头不完整就把已读的字节留在连接自己的缓冲区里，立即归还线程，等 Poller 下次通知。这一步就是 NIO 能扛住慢客户端的原因。
  5. 请求完整后，Worker 调用 Processor 解析、Adapter 进入容器，一直到 Servlet 返回——这段时间线程是被占用的。
  6. Poller 还顺带做超时检查：空闲超过 keepAliveTimeout 的连接被关掉。
🔑 状态从线程栈搬到了对象里

阻塞模型里，「这个连接读到哪儿了」保存在线程的局部变量里，所以线程走不开。NIO 模型把这些状态搬到了每个连接一个的 NioSocketWrapper 上（我们的版本叫 SocketWrapper），线程就可以随时离开、下次由别的线程接着处理。 这是所有事件驱动系统（Netty、Node.js、Nginx）的共同思路。

CoyoteAdapter：协议和容器之间唯一的接缝

Processor 解析出来的是 org.apache.coyote.Request：只有原始字节和协议字段，很多值甚至还没解码（用 MessageBytes 指向缓冲区里的一段，用到才转成 String）。 CoyoteAdapter.service() 负责：

  1. 取出（或创建并缓存）对应的 org.apache.catalina.connector.Request/Response，两者都是可回收复用的对象。
  2. postParseRequest()：URI 解码和规范化（拒绝 /../ 这类路径）、解析会话 ID，然后调用 Mapper 一次性找出 Host、Context、Wrapper（第 12、13 章逐层映射的现代版）。
  3. 调用 connector.getService().getContainer().getPipeline().getFirst().invoke(request, response)——从这里起就是第 5 章以来熟悉的阀链。
  4. 返回后结束响应、回收对象，或者在异步模式（第 24 章）下什么都不做，等待之后再完成。

迷你版 NioEndpoint 大约 250 行，结构和 Tomcat 的同名类一致：一个 Acceptor 线程、一个 Poller 线程、一个固定大小的 Worker 线程池。 省略了 SSL、HTTP/2、请求体和 sendfile，但保留了非阻塞读、流水线、keep-alive 超时和连接数上限。

    while (running) {
        connectionLimit.acquire();                         // Semaphore ≈ Tomcat 的 LimitLatch
        SocketChannel ch = server.accept();                // 阻塞：只有这一个线程，没关系

② Poller：只有它碰 Selector

/** 其他线程不能直接改 Selector 的注册状态，所以把操作排队，由 Poller 自己执行 */
final Queue<Runnable> events = new ConcurrentLinkedQueue<>();

void readAgain(SocketWrapper w) {
    events.add(() -> { if (w.key.isValid()) w.key.interestOps(SelectionKey.OP_READ); });
    selector.wakeup();
}

public void run() {
    while (running) {
        for (Runnable r; (r = events.poll()) != null; ) r.run();
        selector.select(1000);
        var it = selector.selectedKeys().iterator();
        while (it.hasNext()) {
            SelectionKey key = it.next();
            it.remove();
            key.interestOps(0);                            // 交给 Worker 期间不再报告这个连接
            executor.execute(new SocketProcessor((SocketWrapper) key.attachment()));
        }
        timeout();                                         // 关掉空闲太久的长连接
    }
}

⚠️ NIO 解决的是「等客户端」，不是「等业务」

最后一组数字说明：请求进入 Servlet 之后，线程仍然被占用到 Servlet 返回。如果业务要等数据库或远程服务 2 秒， 4 个线程每 2 秒只能完成 4 个请求，连接器是不是 NIO 都一样。解决这个问题要靠第 24 章的异步 Servlet，或第 27 章的虚拟线程。

设计要点

这一章的代码里有几个可以带到别的项目里的设计决定。每条按「做法 → 取舍 → 替代方案 → 还能用在哪」来写；系统的讨论见设计篇。

1按变化维度分层

Coyote 把连接器拆成 Endpoint（IO 模型）、Processor（协议）、Adapter（容器接口），协议和 IO 模型可以自由组合。

取舍
N 种协议 × M 种 IO 只需要 N + M 个实现；代价是层与层之间的接口要设计得足够通用，调用栈也变深了。
替代方案
每种组合写一个连接器（第 4 章的做法，组合一多就失控）。
还能用在
存储层（序列化格式 × 存储介质）、消息系统（协议 × 传输）、报表（数据源 × 输出格式）：找出独立变化的维度，各自抽象。
延伸：第 29 章 · 整体架构：分层与边界
2把状态从线程搬到对象上

连接的读取进度保存在 SocketWrapper 里，线程只在有事可做时才出现。

取舍
少量线程服务海量连接；代价是代码要写成「可中断、可恢复」的状态机，比顺序代码难读、难调试。
替代方案
虚拟线程（第 27 章）：让顺序代码在等待时自动「让出」载体线程，兼得两者。
还能用在
长流程的工作流引擎、聊天服务器、游戏服务器：把「进行到哪一步」存进对象或数据库，任何线程都能接着推进。
延伸：第 32 章 · 并发、隔离与演进
3单线程拥有共享资源，其他线程发消息

只有 Poller 线程操作 Selector，其他线程通过事件队列 + wakeup() 提交修改请求。

取舍
不需要锁，也不会和阻塞中的 select() 互相卡住；代价是修改不是立即生效，多一次排队。
还能用在
GUI 的事件分派线程、Redis 的单线程模型、Actor 模型：一个资源一个主人，其他人只能发消息。
延伸：第 32 章 · 并发、隔离与演进
4在每一级都设上限

backlog（acceptCount）、连接数（maxConnections）、线程数（maxThreads）分别限制请求流转的三个阶段。

取舍
任何一级被打满都不会拖垮其他级；代价是参数多、相互影响，调错了会出现「有空闲线程却连不上」这类现象。
还能用在
任何流水线式系统：消息消费者的预取数量、并发度、下游调用的连接池，各自设上限并监控。
延伸：第 28 章 · 运维：调优、监控与加固

小结

  • Coyote 把连接器拆成 ProtocolHandler、Endpoint、Processor、Adapter 四层；Tomcat 8.5 起删除了 BIO，NIO 成为默认实现。
  • 阻塞模型一个连接占一个线程，慢客户端就能耗尽线程池；NIO 用 Selector 让空闲连接不占线程。
  • NioEndpoint 有三类线程：Acceptor 接收连接，Poller 用 Selector 监视可读事件，Worker 线程池处理请求；读不全时立即归还线程。
  • acceptCount、maxConnections、maxThreads 分别限制内核队列、连接数、并发处理数。
  • CoyoteAdapter 是协议层和容器之间唯一的接缝：转换请求对象、用 Mapper 映射，然后调用 Engine 管道。
  • NIO 不能让慢业务变快：请求进入 Servlet 后仍然占用线程，这要靠异步 Servlet 或虚拟线程解决。

动手练习

  1. 给迷你连接器加上 connectionTimeout：新连接在 3 秒内没有发完请求头就关闭。再跑一次 SlowClients，观察服务器端连接数的变化。
  2. 把 maxConnections 设为 100，用 SlowClients 打开 300 个连接，观察第 101 个之后的连接停在哪里（提示：ss -tn state syn-recv、ss -ltn 的 Recv-Q）。
  3. 为 RawRequest 增加 Content-Length 请求体的支持：请求头完整但请求体不完整时，同样把线程还回去。
  4. 用 jstack 或 jcmd <pid> Thread.print 打印 Tomcat 进程的线程，在 Poller 线程的栈里找到 EPoll.wait（Linux）。
