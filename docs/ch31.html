设计模式实战：在 Tomcat 里找到它们，在业务里用上它们

设计模式最难的不是记住类图，而是知道「什么问题该用它」。Tomcat 是一个绝佳的教材：每个模式都是被真实问题逼出来的， 而且你已经在前面的章节里读过它们的源码。这一章按「问题 → Tomcat 怎么用 → 业务里怎么用 → 要注意什么」把十二个模式过一遍， 每个模式都配了一段可以运行的电商场景代码。

本章目标

  • 能在 Tomcat 源码里认出十二个常用模式，并说出它们解决的问题
  • 能把每个模式迁移到一个业务场景里
  • 理解模式之间如何组合，而不是孤立地使用
  • 认识每个模式最常见的误用

结构：外观、组合、适配器、装饰器

这四个模式都是「包一层」，区别在于包的目的：

① 外观 Facade

问题
内部对象有很多公开方法（因为同一个包里的其他类要用），但交给外部代码时，不希望对方调用它们。
Tomcat
Servlet 拿到的是 RequestFacade 而不是 Request；如果拿到 Request，Servlet 可以向下转型调用 recycle() 把别人的请求清空。
业务
把订单交给插件、脚本、模板引擎时，交出只读视图；对外 API 返回 DTO 而不是实体。
注意
外观只挡住「方法」，挡不住「可变对象」：如果视图返回了内部的可变集合，外部照样能改。返回不可变副本或 List.copyOf。
var order = new Order("A-1", new BigDecimal("100"));
OrderView forPlugin = Facade.of(OrderView.class, order);       // 第 2 章的 JDK 动态代理外观
System.out.println("插件看到：" + forPlugin.id() + " " + forPlugin.total());
System.out.println("能向下转型吗？" + (forPlugin instanceof Order));   // false：applyRefund 碰不到

⑤ 组合 Composite

问题
有层级结构，希望对「一个」和「一组」用同样的方式处理。
Tomcat
四种容器都是 Container，start()、backgroundProcess()、invoke() 都能沿着树递归。第 5 章甚至可以只部署 Context + Wrapper 两层。
业务
组织架构、菜单权限、商品套装、审批流程的嵌套步骤、规则组（AND / OR 嵌套）。
注意
叶子节点不该支持的操作（Wrapper 的 addChild）只能抛异常。Java 17 的 sealed 接口可以把节点类型限定死，让编译器帮你检查。
sealed interface Item permits Product, Bundle { BigDecimal price(); String name(); }

record Product(String name, BigDecimal price) implements Item { }

record Bundle(String name, List<Item> items, BigDecimal discount) implements Item {
    @Override public BigDecimal price() {
        return items.stream().map(Item::price).reduce(BigDecimal.ZERO, BigDecimal::add).subtract(discount);
    }
}
// 套装 = 手机 + 礼盒(手机壳 + 贴膜 − 10) − 100 → 2970

⑧ 适配器 Adapter

问题
手上的东西和需要的接口形状不一样，又不能（或不该）改其中任何一方。
Tomcat
CoyoteAdapter 把协议层的 coyote.Request 转成 Servlet 世界的 HttpServletRequest；Commons Modeler 用描述符把普通对象适配成 MBean（第 20 章）。
业务
包装第三方 SDK（短信、支付、对象存储），让业务代码只依赖自己定义的接口——换供应商时只写一个新适配器。
注意
适配器里只做「翻译」：参数格式、错误码转异常、重试默认值。业务逻辑一旦溜进适配器，换供应商时就要重写它。
var sdk = new LegacySmsSdk();                           // 改不了的第三方 SDK：sendSms(mobile, content, retry) 返回错误码
Notifier notifier = (user, text) -> {                   // 我们需要的接口：notify(user, text)
    if (sdk.sendSms(mobiles.get(user), text, 3) != 0) throw new IllegalStateException("短信发送失败");
};
notifier.notify("alice", "您的订单已发货");

⑨ 装饰器 Decorator

问题
想给一个对象加行为（缓存、计时、改写某些返回值），又不想改它、也不想用继承。
Tomcat
分派时用 ApplicationHttpRequest 包住原请求，只改写路径和参数（第 21 章）；Servlet 规范提供 HttpServletRequestWrapper 作为装饰器基类，压缩、XSS 过滤等过滤器都用它。
业务
给 Repository 加缓存、给远程调用加超时和重试、给任何接口加指标统计。Spring 的 AOP 代理本质上就是自动生成的装饰器。
注意
层层包装后 instanceof 和 equals 会出乎意料；调试时要知道去拆包装（getRequest()）。
PriceService cached = new PriceService() {             // 同一个接口，包在外面加缓存
    private final Map<String, BigDecimal> cache = new ConcurrentHashMap<>();
    @Override public BigDecimal priceOf(String sku) { return cache.computeIfAbsent(sku, remote::priceOf); }
};
for (int i = 0; i < 3; i++) cached.priceOf("SKU-1");   // 远程调用 1 次

行为：责任链、观察者、模板方法、策略、状态机

② 责任链 Chain of Responsibility

问题
一个请求要经过一串可增可减的处理步骤，每一步都可能修改请求、提前结束、或者在后续步骤前后做事。
Tomcat
每个容器的 Pipeline：附加阀按顺序执行，基础阀在最后；Servlet 的 FilterChain 同理。
业务
价格计算（会员价 → 满减 → 优惠券 → 结算）、请求校验、审批流、风控规则。
注意
顺序就是语义：先打折再满减和先满减再打折结果不同。把顺序写进配置并加测试，不要依赖注册的先后。
var pricing = new Pipeline<Cart>(c -> c.notes.add("应付 " + c.price));          // 基础阀：结算
pricing.addValve((c, next) -> {                                                   // 会员 95 折
            c.price = c.price.multiply(new BigDecimal("0.95")).setScale(2, RoundingMode.HALF_UP);
            next.invoke(c);
        })
        .addValve((c, next) -> {                                                  // 满 100 减 10
            if (c.price.compareTo(new BigDecimal("100")) >= 0) c.price = c.price.subtract(BigDecimal.TEN);
            next.invoke(c);
        });
// 原价 120 → [会员 95 折, 满 100 减 10, 应付 104.00]

③ 观察者 Observer

问题
一件事发生后，有好几方需要知道，但发生事件的一方不应该依赖它们。
Tomcat
组件状态变化时通知 LifecycleListener：ContextConfig 借此在 Context 启动时解析 web.xml（第 15 章），HostConfig 借此部署应用（第 18 章）——核心类不知道它们的存在。
业务
领域事件：订单支付后通知积分、短信、库存、数据仓库。Spring 的 ApplicationEvent、消息队列都是它的放大版。
注意
事件链一长，「谁改了这个状态」就很难追踪；监听器之间不要有顺序依赖；在主线程同步执行的监听器会拖慢主流程。
List<Consumer<OrderEvent>> listeners = new CopyOnWriteArrayList<>();
listeners.add(e -> System.out.println("  [积分] " + e.orderId() + " 加 10 分"));
listeners.add(e -> System.out.println("  [短信] 通知用户：订单 " + e.orderId() + " " + e.type()));
listeners.forEach(l -> l.accept(new OrderEvent("A-1", "已支付")));   // 订单服务不认识积分和短信

④ 模板方法 Template Method

问题
多个类的流程相同、只有某几步不同；流程本身有容易写错的规则（状态检查、异常处理、事件通知）。
Tomcat
LifecycleBase.start() 是 final 的，负责状态机和事件，子类只实现 startInternal()；HttpServlet.service() 按方法名分派到 doGet/doPost；第 7 章的 LoggerBase。
业务
批量导入（读取 → 校验 → 保存 → 汇总）、报表生成、对接多家支付渠道的通用流程。
注意
继承只能用一次。如果「不同的那几步」需要自由组合，改用策略（把步骤做成可注入的对象）。
abstract static class ImportJob {
    final String run(List<String> rows) {               // 流程固定，final 防止子类改顺序
        int ok = 0;
        for (String row : rows) {
            if (!validate(row)) continue;
            save(row);
            ok++;
        }
        return getClass().getSimpleName() + "：导入 " + ok + "/" + rows.size();
    }
    protected abstract boolean validate(String row);
    protected void save(String row) { }                   // 钩子方法：有默认实现，按需覆盖
}

⑥ 策略 Strategy

问题
同一件事有多种做法，要能在运行时或部署时选择，而且不影响使用它的代码。
Tomcat
Context 用哪个 Realm 校验密码、用哪个 Manager 存会话、用哪个 Loader 加载类，都是可替换的策略（第 30 章的「策略插槽」）。
业务
运费、税费、价格策略；重试和退避策略；不同租户的风控规则。
注意
只有两三种、几乎不变的分支，用 switch 就够了。策略的价值在于「新增一种做法时不改老代码」，没有这个需求就是过度设计。
Map<String, ShippingFee> strategies = Map.of(
        "standard", amount -> amount.compareTo(new BigDecimal("99")) >= 0 ? BigDecimal.ZERO : new BigDecimal("8"),
        "express", amount -> new BigDecimal("20"));

⑫ 状态机 State Machine

问题
对象有明确的阶段，每个阶段允许的操作不同，非法的转换必须被拒绝。
Tomcat
LifecycleState 规定了组件的合法转换；AsyncStateMachine 处理异步请求里「complete 在 service 返回前被调用」这类竞态（第 24 章）。
业务
订单、工单、审批、支付单的状态流转。
注意
状态转换表要集中在一处（枚举或表格），而不是散落在各个 if (status == …) 里。并发修改时要配合乐观锁或 CAS。
enum OrderStatus {
    CREATED, PAID, SHIPPED, COMPLETED, CANCELLED;

    private static final Map<OrderStatus, Set<OrderStatus>> NEXT = new EnumMap<>(Map.of(
            CREATED, EnumSet.of(PAID, CANCELLED),
            PAID, EnumSet.of(SHIPPED, CANCELLED),
            SHIPPED, EnumSet.of(COMPLETED), …));

    OrderStatus to(OrderStatus next) {
        if (!NEXT.get(this).contains(next)) throw new IllegalStateException(this + " 不能变成 " + next);
        return next;
    }
}

创建与资源：工厂、对象池、写时复制

⑦ 工厂 + 反射装配

问题
要创建哪个类，编译时不知道，由配置或者类路径上有什么决定。
Tomcat
Digester 的 ObjectCreateRule 按 XML 里的 className 创建对象（第 15 章）；SCI 按 META-INF/services 创建（第 25 章）。
业务
按配置选择支付网关、存储后端、消息中间件的实现；插件系统。
注意
反射把错误推迟到运行时：启动时就把所有配置的类加载并校验一遍，不要等第一个请求来了才发现类名拼错了。
String configured = "…PatternTour$AlipayGateway";                      // 来自配置文件
var gateway = (PaymentGateway) Class.forName(configured).getConstructor().newInstance();

⑩ 对象池 Object Pool

问题
某种对象创建代价很高（线程、连接、加载了大量数据的解析器），而且可以复用。
Tomcat
第 4 章的 HttpProcessor 池、第 11 章 SingleThreadModel 的实例池、今天的工作线程池；Coyote 的 Request/Response 对象也在连接上回收复用。
业务
数据库连接池、HTTP 客户端连接池、昂贵的渲染器或模型。
注意
普通对象不要池化——JVM 分配小对象比从池里取还快，池化还会带来「忘了归还」「归还前没清理状态」两类 bug。池一定要有界，并想好池空时是等待还是失败。
<R> R with(Function<T, R> work) throws InterruptedException {
    T t = idle.take();                                   // 没有空闲的就等（有界）
    try {
        return work.apply(t);
    } finally {
        idle.add(t);                                     // 一定要还回去
    }
}

⑪ 写时复制 Copy-on-Write

问题
一份数据读得非常频繁、改得很少，读的时候不想加锁，改的时候不能影响正在读的人。
Tomcat
第 6 章的 LifecycleSupport 每次增删监听器都复制数组；管道的阀数组同理。遍历时拿到的是不可变的快照。
业务
路由表、促销规则、功能开关、黑白名单的热更新：构建一份新的不可变配置，用 AtomicReference 原子替换。
注意
写多读少时代价很高（每次写都复制全部数据）；它只保证每个读者看到一致的快照，不保证所有读者看到最新值。
var current = new AtomicReference<>(new PromotionRules(List.of("满100减10"), 1));
PromotionRules seenByRequest = current.get();            // 一个正在处理的请求拿到的快照
current.updateAndGet(old -> {                            // 运营后台改规则：复制一份再替换引用
    var copy = new ArrayList<>(old.rules());
    copy.add("会员95折");
    return new PromotionRules(List.copyOf(copy), old.version() + 1);
});
// 进行中的请求仍然看到 v1，新请求看到 v2

模式从不单独出现

在 Tomcat 里，模式总是成组出现的。以一个容器为例，它身上同时有六个模式，每个解决一个不同的问题：

这给了一个实用的读源码技巧：看到一个陌生的大类，先问「它是哪棵树上的节点、有没有管道、继承了什么模板、有哪些插槽、谁在监听它、对外暴露的是不是外观」， 六个问题问完，类的骨架就清楚了，剩下的才是业务细节。

常见误用

模式误用的症状应该怎么做
策略每个只有一个实现的类都配一个接口和工厂出现第二种做法时再抽（第 30 章的三次法则）
观察者业务流程靠一串事件串起来，没人说得清完整流程主流程显式调用，旁路通知才用事件
责任链链里的处理器互相依赖（「这个阀假设前面那个阀已经设置了某个属性」）把依赖写成显式的上下文字段，并对顺序加测试
模板方法为了复用一个工具方法而继承，形成很深的继承树工具方法放进可组合的辅助类（第 6 章的 LifecycleSupport）
对象池池化普通对象；池无界；归还前不清理状态只池化昂贵资源，有界，借出时重置
单例（本章没讲）用静态单例保存可变的全局状态Tomcat 几乎不用单例：组件由装配层创建并注入（第 29 章原则四）

💡 一个小插曲

第一次运行时外观示例抛了 IllegalAccessException：OrderView 接口是包私有的，而第 2 章的 Facade 在另一个包里用反射调用它的方法。 JDK 动态代理要求被代理的接口对调用方可见——这也是为什么 Tomcat 的外观类都实现 public 的规范接口。

小结

  • 外观、适配器、装饰器都是「包一层」：分别让接口变少、变样、不变但加行为；组合让一个和一组用同一个接口。
  • 责任链处理「一串可增减的步骤」，观察者处理「一对多的通知」，模板方法固定流程，策略替换做法，状态机约束阶段。
  • 工厂 + 反射让配置决定实现，对象池复用昂贵资源，写时复制让读无锁、写不影响读。
  • 模式总是成组出现；读一个大类时，先用六个问题找出它身上的模式。
  • 每个模式都有误用：没有第二个实现就不要抽策略，主流程不要靠事件串联，普通对象不要池化。

动手练习

  1. 把责任链示例里的折扣顺序调换，算出新结果，并写一个测试固定「先打折后满减」的业务规则。
  2. 给装饰器示例加一个「计时装饰器」，和缓存装饰器叠加使用。两种叠加顺序下，计时结果有什么不同？
  3. 用组合模式实现一个规则引擎：Rule 有 And、Or、Not 和叶子规则（金额大于 X、用户等级为 Y），用 sealed 接口限定节点类型。
  4. 在你的项目里找出三个模式的实际使用，按本章的「问题 / 实现 / 注意」格式记录下来，检查是否落入了误用表里的情况。
