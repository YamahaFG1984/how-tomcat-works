整体架构：分层与边界

前 28 章是在「拆」Tomcat：一个零件一个零件地看它怎么工作。设计篇反过来「装」： 把散落在各章的设计决定收拢成几条可以带走的原则，并用它们去设计一个和 Web 毫无关系的系统。 这一章讲宏观——Tomcat 为什么能在 25 年里换掉连接器、换掉线程模型、换掉包名，却没有推倒重来。

本章目标

  • 能画出 Tomcat 的分层图，说出每一层负责什么、隔着什么接口
  • 掌握五条架构原则：按变化切分、窄接口、统一组件模型、配置/装配/运行分离、依赖指向内核
  • 会把这些原则映射到一个普通的业务系统上
  • 知道什么时候不该这样设计

原则一：按「变化的原因」切分

模块边界该画在哪里？最可靠的答案是：把会因为不同原因、在不同时间变化的东西分开。 回顾 Tomcat 二十多年的变化，每一种变化都被关在了一个模块里：

会变的东西历史上的变化被关在哪里对外的接口
网络协议HTTP/1.1 → AJP → HTTP/2 → WebSocketCoyote 的 Processor / UpgradeProtocolAdapter.service()
IO 与线程模型BIO → NIO → NIO2 → APR（已删除）→ 虚拟线程Endpoint、ExecutorProcessor 看到的 socket 包装
部署方式server.xml → 嵌入式 → Spring Boot装配层组件的构造器和 setter
应用代码Servlet 2.3 → 6.1，javax → jakartaWeb 应用（独立类加载器）Servlet API
用户与会话存储内存 → 文件 → JDBC → LDAPRealm、Manager/Store各自的接口

反过来看，第 4 章的 HttpProcessor 就是一个反例：它既解析协议、又管线程（assign/await）、又调用容器。 后来 Coyote 把它拆成了三块，正是因为这三件事是按不同节奏变化的。

🔑 在你的项目里

列出「将来最可能变的东西」：接入方式（HTTP → 消息队列 → gRPC）、外部依赖（换支付渠道、换短信服务商）、业务规则（促销策略）、部署形态（单体 → 拆服务）。 每一项都应该能在一个模块里改完，而不是散落在整个代码库。如果某次需求变更让你改了十几个包，边界就画错了。

原则二：层与层之间只留窄接口

Tomcat 各层之间的接口窄得惊人。把它们列出来，每个只有一两个核心方法：

接口越窄，两侧能独立演化的空间就越大。最好的证明是 Servlet.service()：这个签名从 1997 年用到今天（只是包名从 javax 换成了 jakarta）， 而它两侧，一边从 BIO 连接器换成了 NIO + HTTP/2 + 虚拟线程，另一边从手写 Servlet 发展出了 Spring MVC。 窄接口的另一个好处是可测试：第 21 章的迷你分派器能在内存里测试 Servlet，正是因为 Servlet 只要求一个 request 和一个 response。

🔑 在你的项目里

模块之间的接口，先问「能不能只有一个方法」。服务层暴露 OrderService.place(PlaceOrderCommand)， 比暴露一个有 30 个 setter 的 OrderManager 好得多。参数用不可变的命令对象（record），返回值用结果对象——这就是 Tomcat 的 request/response。

原则三：统一的组件模型

Tomcat 里几乎所有东西都是同一种「组件」：实现 Lifecycle，大多数还是容器树上的一个节点。 这带来了三个好处：

  1. 使用者只需要启动顶层。server.start() 级联启动整棵树，关闭同理——不需要记住几十个组件的启动顺序。
  2. 顺序由结构表达。StandardService 先启动 Engine 再启动 Connector，停止时反过来：不会有请求打到还没准备好、或者正在拆除的容器上。第 25 章 Spring Boot「最后才开端口」是同一个思想。
  3. 通用工具对所有组件都有效。生命周期监听器（第 6 章）、JMX 注册（第 20 章）、后台处理（第 12 章）都是在「组件」这个层次实现的，新组件加进来自动获得这些能力。
🔑 在你的项目里

凡是持有线程、连接、文件句柄、定时器的类，都让它实现统一的 start/stop（Spring 的 SmartLifecycle、Guava 的 Service、或者本章工具包里的 LifecycleBase）， 并组织成一棵树。启动时「先依赖、后被依赖；先内部、后入口」，停止时反过来。消息消费者最后启动、最先停止，和 Connector 一样。

原则四：配置、装配、运行三段分离

第 5～14 章的每个 Bootstrap 都在 main 方法里手工 new 出组件、用 setter 连起来；第 15 章开始，同样的对象图改由 Digester 读 server.xml 生成； 第 25 章，Spring Boot 又用代码生成。运行时的组件一模一样，只是装配者不同：

这条原则的关键是组件里不出现配置解析代码，也不 new 自己的依赖。StandardContext 不读 web.xml（交给 ContextConfig 监听器）， Connector 不找 Engine（由 Service 注入）。好处立竿见影：嵌入式 Tomcat 只是「换一个装配者」，测试时可以用代码装配一个最小的对象图。

🔑 在你的项目里

业务类通过构造器接收依赖（依赖注入），所有 new 具体实现 集中在一个「组合根」（main 方法、Spring 配置类、Guice 模块）。 配置读取也集中在一处，把 Properties/YAML 变成强类型的配置对象（record）再注入，业务代码里不出现 getProperty("…")。

原则五：依赖指向内核，边缘可以替换

核心层（容器树）不知道请求从什么协议来，也不知道用户存在哪里、会话存在哪里。它只定义接口，由边缘去实现：

第 9 章把 StandardManager 换成 PersistentManager、第 10 章把 SimpleRealm 换成 JDBC Realm，都不需要改容器一行代码。 依赖方向决定了谁能被替换：被依赖的那一方（接口）必须稳定，依赖别人的那一方（实现）可以随便换。

🔑 在你的项目里

业务核心（领域模型、用例）定义 OrderRepository、PaymentGateway、Notifier 这些接口； 基础设施层用 JPA、支付宝 SDK、短信服务实现它们；入站一侧，HTTP Controller、MQ 监听器、定时任务都只是把外部输入翻译成用例调用。 检验标准：不启动数据库和 Web 服务器，能不能测试全部业务规则？

① LifecycleBase：状态机写一次

public abstract class LifecycleBase implements Lifecycle {

    private volatile LifecycleState state = LifecycleState.NEW;
    private final List<Consumer<LifecycleEvent>> listeners = new CopyOnWriteArrayList<>();

    @Override
    public final synchronized void start() {
        if (state == LifecycleState.STARTED || state == LifecycleState.STARTING) {
            return;                                     // 重复 start：幂等
        }
        if (state == LifecycleState.NEW) init();        // 没 init 就 start：替使用者补上
        transition(LifecycleState.STARTING);
        try {
            startInternal();                            // 子类只写自己的事
        } catch (RuntimeException e) {
            fail(e);
        }
        transition(LifecycleState.STARTED);
    }

    private void transition(LifecycleState to) {
        LifecycleState from = state;
        if (!from.next().contains(to)) {                // 非法转换给出清晰的错误
            throw new IllegalStateException(name + "：不能从 " + from + " 转到 " + to);
        }
        state = to;
        listeners.forEach(l -> l.accept(new LifecycleEvent(this, from, to)));
    }

    protected abstract void startInternal();
    protected abstract void stopInternal();
}

② CompositeComponent：启动正序，停止倒序

@Override
protected final void startInternal() {
    startSelf();
    for (C c : children) c.start();
}

@Override
protected final void stopInternal() {
    List<C> reversed = new ArrayList<>(children);
    Collections.reverse(reversed);
    for (C c : reversed) {
        try {
            c.stop();
        } catch (RuntimeException e) {
            // 一个子组件停不下来，不能让其余的也停不下来：记录后继续
        }
    }
    stopSelf();
}

③ Pipeline：不可变快照上的阀链

public void invoke(T context) throws Exception {
    Object[] snapshot = valves.toArray();           // 本次调用用的阀列表，之后的修改不影响它
    invoke(snapshot, 0, context);
}

private void invoke(Object[] snapshot, int index, T context) throws Exception {
    if (index == snapshot.length) {
        basic.invoke(context);                      // 基础阀永远在最后
    } else {
        ((Valve<T>) snapshot[index]).invoke(context, c -> invoke(snapshot, index + 1, c));
    }
}

④ 装配器：所有 new 都在这里

什么时候不要这样设计

Tomcat 的分层是为一个有很多种实现、要活几十年、被几百万个应用依赖的系统准备的。每一层间接都有成本：更多的类、更深的调用栈、更难的调试。

信号说明可以简化
每个接口只有一个实现，而且看不到第二个直接用类；等第二个实现出现时再抽接口（第 18 章 Deployer 接口就是反面教材）
只有一种接入方式、一种存储不需要端口与适配器那么多层，Controller 直接调 Service 就好
团队小、生命周期短（活动页、内部工具）可读性和交付速度比可替换性重要
「为了将来可能的扩展」先确认「将来」有没有证据；没有就别为它付今天的成本

原则的价值在于让你知道边界在哪里，而不是一开始就把每条边界都实现出来。代码里可以先只有一个包，只要依赖方向是对的，需要时再拆就不难。

小结

  • Tomcat 分成启动、装配、运行时骨架、边界、核心、可替换组件、管理面几层，越往下越稳定。
  • 原则一：按变化的原因切分，每一种变化只影响一个模块。
  • 原则二：层之间只留窄接口，接口越窄两侧越自由，也越容易测试。
  • 原则三：统一的组件模型（生命周期 + 组合树），启动时先内部后入口，停止时反过来。
  • 原则四：配置、装配、运行分离，组件不解析配置、不 new 依赖，任何装配方式都能用。
  • 原则五：依赖指向内核，边缘可以替换——这就是端口与适配器架构。
  • 这些原则有成本，只在有证据表明需要时才把边界实现出来。
