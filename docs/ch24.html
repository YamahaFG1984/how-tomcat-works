异步 Servlet 与非阻塞 IO

上一章结尾留下了一个问题：NIO 连接器让「等客户端」不再占线程，可请求一旦进入 Servlet， 线程就要一直陪到 service() 返回。如果业务要等数据库、等远程服务、等一条消息，线程就在那里干等。 Servlet 3.0 的 AsyncContext 和 3.1 的 ReadListener/WriteListener 就是为此而生的。 这一章先在第 23 章的迷你连接器上用二十行代码实现「异步」，再看 Tomcat 怎么做，以及它的几个典型用法。

本章目标

  • 说清楚「异步 Servlet」异步的是什么：响应的结束时间和 service() 的返回时间脱钩
  • 会用 startAsync()、complete()、dispatch()、超时和 AsyncListener
  • 理解 Tomcat 内部的异步状态机：CoyoteAdapter 发现请求进入异步模式后不结束响应
  • 会写长轮询和 Server-Sent Events 这类推送接口
  • 知道非阻塞 IO（ReadListener）解决的是另一个问题：慢速上传

问题：线程在等什么

假设一个接口要调用一个耗时 2 秒的远程服务，Tomcat 只有 4 个工作线程。同步写法下，每个请求占用一个线程 2 秒， 4 个线程每 2 秒只能完成 4 个请求，第 5 个请求开始就要排队：

注意「异步」在这里的确切含义：响应什么时候结束不再由 service() 什么时候返回决定。 对客户端来说没有任何区别——它依然发一个普通的 HTTP 请求，等一个普通的响应。

先自己实现：Future 就是异步

回到第 23 章的迷你连接器。Worker 线程调用 adapter.service(req) 拿到响应后马上写出去。 只要把返回值从「响应」改成「响应的 Future」，就能表达「现在还没有结果」： 

CompletableFuture<Adapter.RawResponse> future = adapter.serviceAsync(req);
if (!future.isDone()) {
    // 异步：Worker 线程现在就归还；业务完成时再派一个线程回来写响应
    future.whenComplete((r, e) -> executor.execute(() -> {
        if (respond(req, future)) run();       // 流水线里还有请求，接着处理
    }));
    return;
}
respond(req, future);                          // 同步：和第 23 章一样，当场写响应

同步的 Adapter 返回一个已经完成的 Future，走老路；异步的 Adapter 返回一个以后才完成的 Future，Worker 线程立刻返回线程池。 在 2 个 Worker 线程的服务器上对比： 

Adapter adapter = Adapter.async(req -> {
    if (req.uri().startsWith("/sync")) {
        sleep(2000);                                           // 同步：线程被占用 2 秒
        return CompletableFuture.completedFuture(text("sync…"));
    }
    var future = new CompletableFuture<Adapter.RawResponse>();
    // 相当于 startAsync() 之后把 AsyncContext 交给别的线程：2 秒后由 timer 线程 complete()
    timer.schedule(() -> future.complete(text("async…")), 2, TimeUnit.SECONDS);
    return future;                                             // Worker 线程马上返回
});
var endpoint = new NioEndpoint(port, 2, 10_000, 20_000, adapter);   // 只有 2 个 Worker

/sync  × 10：  总耗时 10.1 秒，完成时间分布（秒→个数）{2=2, 4=2, 6=2, 8=2, 10=2}
/async × 10：  总耗时 2.2 秒， 完成时间分布（秒→个数）{2=10}
/async × 1000：总耗时 3.5 秒， 完成时间分布（秒→个数）{2=864, 3=136}

这就是全部原理。Tomcat 的 AsyncContext 本质上就是这个 Future：Servlet 调用 startAsync() 相当于返回一个未完成的 Future，调用 complete() 相当于完成它。

AsyncContext 的用法

方法作用注意
request.startAsync()进入异步模式，返回 AsyncContext链路上所有 Servlet 和过滤器都必须声明 asyncSupported=true，否则抛 IllegalStateException
ac.complete()结束响应可以在任何线程调用；之后不能再写响应
ac.dispatch(path)把请求以 DispatcherType.ASYNC 分派回容器，在容器线程里继续处理适合「异步取数据，同步渲染页面」
ac.setTimeout(ms)超时时间，默认 30 秒；0 表示永不超时超时后先调用 onTimeout，没人处理就返回 500
ac.addListener(...)onComplete / onTimeout / onError / onStartAsync清理资源（取消定时任务、移除订阅）的唯一可靠时机
ac.start(Runnable)用容器的线程池执行任务只是把阻塞挪到另一个容器线程，不省线程，一般不用
⚠️ 把阻塞挪到另一个线程池不等于异步

常见误用：startAsync() 之后把阻塞的 JDBC 调用提交给一个自定义线程池。容器线程是省下来了， 但业务线程池里每个任务仍然阻塞 2 秒——只是换了个地方排队。真正的收益来自等待本身不占线程： 定时器、消息回调、异步 HTTP 客户端（HttpClient.sendAsync）、响应式数据库驱动。

Tomcat 内部：异步状态机

第 23 章说过，CoyoteAdapter.service() 在 Servlet 返回后会结束响应、回收对象。异步模式下它多了一个判断：

org.apache.coyote.AsyncStateMachine 记录请求处于 STARTING、STARTED、DISPATCHING、COMPLETING 等哪个阶段， 处理诸如「在 service() 还没返回时就调用了 complete()」这样的竞态。 complete() 或 dispatch() 并不在调用者的线程里直接写 socket，而是向 Endpoint 提交一个事件， 由连接器的线程完成收尾——和我们迷你版里 executor.execute(() -> respond(...)) 是同一个思路。

典型用法：长轮询与 Server-Sent Events

异步 Servlet 最有价值的场景是「请求来了，但答案还不知道什么时候有」：

  • 长轮询：客户端问「有新消息吗？」，服务器没有就先不回答，把 AsyncContext 存进一个等待列表；新消息到达时取出所有等待者，逐个写响应并 complete()。
  • Server-Sent Events（SSE）：响应类型为 text/event-stream，连接保持打开，服务器有事件就写一行 data: … 并 flush()。浏览器端用 new EventSource(url) 接收，断线自动重连。
  • 聚合多个下游：并行调用三个异步服务，CompletableFuture.allOf(...) 完成后统一写响应。
resp.setContentType("text/event-stream;charset=UTF-8");
AsyncContext ac = req.startAsync();
ac.setTimeout(0);                                  // 0 = 永不超时，由我们自己 complete
task.set(TIMER.scheduleAtFixedRate(() -> {
    var out = ac.getResponse().getWriter();
    out.printf("data: tick %d %tT%n%n", n.incrementAndGet(), System.currentTimeMillis());
    out.flush();                                   // 立刻推给客户端
    if (out.checkError() || n.get() == 5) {        // 客户端断开或者推完了
        task.get().cancel(false);
        ac.complete();
    }
}, 0, 500, TimeUnit.MILLISECONDS));

需要双向通信时（聊天、协同编辑），SSE 就不够用了，那是第 26 章 WebSocket 的领域。

非阻塞 IO：ReadListener 与 WriteListener

异步 Servlet 解决了「等业务」，但还有一种等待藏在 Servlet 里：读请求体。客户端用很慢的网络上传一个 10 MB 文件， request.getInputStream().read() 会一直阻塞，线程又被占住了。Servlet 3.1 给出了非阻塞的读写方式： 

AsyncContext ac = req.startAsync();                // 非阻塞 IO 必须在异步模式下使用
ServletInputStream in = req.getInputStream();
in.setReadListener(new ReadListener() {
    @Override public void onDataAvailable() throws IOException {
        while (in.isReady()) {                     // 只读「现在就能读到」的部分，读完就返回
            int n = in.read(buf);
            if (n < 0) break;
            total.addAndGet(n);
        }
    }
    @Override public void onAllDataRead() throws IOException {
        ac.getResponse().getWriter().printf("收到 %d 字节…", total.get());
        ac.complete();
    }
    @Override public void onError(Throwable t) { ac.complete(); }
});
// doPost 立即返回：等数据的时候不占线程

规则只有一条：只在 isReady() 为真时读。isReady() 返回 false 时，Tomcat 会把这个连接重新交给 Poller， 数据到了再回调 onDataAvailable()——这正是第 23 章 Worker「读不全就走人」在 Servlet API 层面的暴露。 WriteListener 对称地处理「客户端读得慢，写不出去」的情况。

💡 现实中的取舍

非阻塞 IO 的回调式写法很难和普通的业务代码（解析 JSON、调用 Service）结合，所以直接使用它的应用不多。 它主要被框架使用：Spring WebFlux 跑在 Servlet 容器上时，就是用 ReadListener/WriteListener 桥接到响应式流的。

迷你版只改了第 23 章的两个文件：Adapter 增加一个默认方法 serviceAsync()（同步实现直接包成已完成的 Future）， NioEndpoint 增加上面看到的异步分支。第 23 章的所有示例不受影响。 

@FunctionalInterface
public interface Adapter {

    RawResponse service(RawRequest request) throws Exception;

    /** 同步实现直接返回已完成的 Future；返回未完成的 Future 就是「异步」 */
    default CompletableFuture<RawResponse> serviceAsync(RawRequest request) {
        try {
            return CompletableFuture.completedFuture(service(request));
        } catch (Exception e) {
            return CompletableFuture.failedFuture(e);
        }
    }

    /** 用一个返回 Future 的函数创建异步 Adapter */
    static Adapter async(Function<RawRequest, CompletableFuture<RawResponse>> handler) { … }
}

Tomcat 版里最基本的异步 Servlet：

static final class AsyncServlet extends HttpServlet {
    @Override protected void doGet(HttpServletRequest req, HttpServletResponse resp) {
        String entered = Thread.currentThread().getName();
        resp.setContentType("text/plain;charset=UTF-8");
        AsyncContext ac = req.startAsync();                // 从这里起，doGet 返回也不会结束响应
        ac.setTimeout(10_000);
        TIMER.schedule(() -> {
            try {
                ac.getResponse().getWriter().println("async: 进入 " + entered
                        + "，完成 " + Thread.currentThread().getName());
            } finally {
                ac.complete();                             // 告诉容器：可以结束响应了
            }
        }, 2, TimeUnit.SECONDS);
    }                                                      // 容器线程在这里就归还了
}

// 注册时必须声明支持异步
Wrapper w = Tomcat.addServlet(ctx, name, servlet);
w.setAsyncSupported(true);

设计要点

这一章的代码里有几个可以带到别的项目里的设计决定。每条按「做法 → 取舍 → 替代方案 → 还能用在哪」来写；系统的讨论见设计篇。

1用 Future 表达「结果稍后才有」

迷你版只把返回类型从 RawResponse 改成 CompletableFuture<RawResponse>，同步实现返回已完成的 Future。

取舍
一个接口同时支持同步和异步，老代码不用改；代价是调用方必须处理「还没完成」的分支，异常也要从 Future 里取。
替代方案
回调接口（Servlet 的 AsyncContext 更接近这种）、响应式流（Publisher）。
还能用在
RPC 客户端、缓存加载器（Caffeine 的 AsyncLoadingCache）、任何「可能要等外部资源」的接口：在接口层面就允许异步。
延伸：第 32 章 · 并发、隔离与演进
2完成动作交回框架线程执行

complete() 不在业务线程里直接写 socket，而是向 Endpoint 提交事件，由连接器的线程收尾。

取舍
socket 和请求对象始终只被连接器线程操作，避免了竞态；代价是多一次线程切换。
还能用在
GUI（后台任务完成后用 SwingUtilities.invokeLater 更新界面）、Netty（非 EventLoop 线程的写操作会被提交给 EventLoop）。
延伸：第 32 章 · 并发、隔离与演进
3异步必须全链路声明

只要链路上有一个 Servlet 或过滤器没声明 asyncSupported，startAsync() 就会失败。

取舍
容器能提前发现「中间某个过滤器在 chain.doFilter 返回后还要写响应」这类不兼容；代价是老过滤器要逐个检查和改造。
还能用在
任何「能力需要整条链支持」的场景：事务传播、链路追踪的上下文传递。让每一环显式声明，而不是默认假设。
延伸：第 30 章 · 扩展点设计
4超时是异步的必需品

AsyncContext 默认 30 秒超时，到点调用 onTimeout，没人处理就返回 500。

取舍
保证每个请求最终都会结束，不会因为业务忘了 complete() 而泄漏连接；代价是长连接场景（SSE）要记得显式设为 0 并自己负责结束。
还能用在
CompletableFuture.orTimeout()、消息的处理超时、分布式锁的租期：所有「等待别人」的地方都要有截止时间。

小结

  • 异步 Servlet 让响应的结束和 service() 的返回脱钩：容器线程只负责发起和收尾，等待期间不占线程。
  • 原理就是 Future：迷你版中 Adapter 返回未完成的 Future，Worker 立即归还，Future 完成时再派线程写响应。
  • startAsync() 之后用 complete() 结束或 dispatch() 回到容器；要设置超时并用 AsyncListener 清理资源。
  • Tomcat 用 AsyncStateMachine 管理异步状态，complete() 会向 Endpoint 提交 socket 事件，由连接器线程收尾。
  • 把阻塞调用挪到另一个线程池并不省线程；收益来自等待本身不占线程（定时器、回调、异步客户端）。
  • ReadListener/WriteListener 处理慢速上传和下载，只在 isReady() 为真时读写。
