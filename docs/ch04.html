第 4 章

Tomcat 默认连接器

第 3 章的连接器能用，但一次只能处理一个请求，处理完就挂断连接。 Tomcat 4 的默认连接器（org.apache.catalina.connector.http）解决了这两个问题： 它用一个处理器池并发处理请求，并实现了 HTTP/1.1 的持久连接、分块传输和 100 Continue。 这一章最精彩的部分是两个线程如何用 wait/notifyAll 交接 socket。

本章目标

  • 理解 HTTP/1.1 的三个新特性：持久连接、分块编码、100 Continue
  • 知道一个 Tomcat 连接器必须满足的三个条件，以及它如何调用容器的 invoke
  • 看懂处理器池（minProcessors / maxProcessors）的工作方式
  • 彻底弄懂 assign / await 之间的线程交接
  • 用 ThreadPoolExecutor + SynchronousQueue 在 Java 17 里实现同样的连接器

HTTP/1.1 的三个新特性

① 持久连接（Persistent Connection）

HTTP/1.1 之前，服务器每发完一个资源就关闭连接。一个网页往往引用了好几张图片、CSS、JS，每个资源都要重新经历一次 TCP 三次握手，非常慢。HTTP/1.1 默认保持连接：同一个 TCP 连接上可以依次发多个请求。客户端也可以显式发 Connection: keep-alive，或者用 Connection: close 要求用完即关。

② 分块编码（Chunked Encoding）

连接不再「发完就关」，接收方就无法用「连接断开」来判断一个响应在哪里结束，所以发送方必须提前给出 Content-Length。可是很多时候服务器边算边发，根本不知道总长度。HTTP/1.1 的办法是 Transfer-Encoding: chunked：每一块前面先写这一块的长度（十六进制）和 CRLF，最后用一个长度为 0 的块表示结束。

③ 100 Continue

客户端要上传一个很大的请求体，但不确定服务器肯不肯收。它可以先只发请求头，并带上 Expect: 100-continue，等服务器回一句 HTTP/1.1 100 Continue 再发请求体，免得白白传了几百 MB 被拒绝。

Connector 接口与容器

一个 Tomcat 连接器必须满足三个条件：

  1. 实现 org.apache.catalina.Connector 接口；
  2. 创建的请求对象实现 org.apache.catalina.Request 接口；
  3. 创建的响应对象实现 org.apache.catalina.Response 接口。

Connector 接口里最重要的四个方法是 setContainer、getContainer、createRequest、createResponse。连接器做完解析后，通过调用容器的 invoke 方法把请求交出去：

public void invoke(org.apache.catalina.Request request,
                   org.apache.catalina.Response response);

HttpConnector 同时实现了 Lifecycle 接口（第 6 章详讲），使用时要先 initialize() 再 start()，两个方法在整个生命周期里各只能调用一次。initialize() 内部调用私有方法 open()，从一个服务器套接字工厂（org.apache.catalina.net.ServerSocketFactory）取得 ServerSocket——这样换成 SSL 套接字时不需要改连接器代码。

处理器池

第 3 章的连接器每次只有一个 HttpProcessor。默认连接器维护一个处理器池，每个 HttpProcessor 都有自己的线程，所以能同时处理多个请求：

private Stack processors = new Stack();
protected int minProcessors = 5;
private int maxProcessors = 20;
private int curProcessors = 0;

// start() 里：预先创建 minProcessors 个处理器
while (curProcessors < minProcessors) {
    if ((maxProcessors > 0) && (curProcessors >= maxProcessors))
        break;
    HttpProcessor processor = newProcessor();   // 构造并启动它的线程，curProcessors++
    recycle(processor);                         // processors.push(processor)
}
ⓘ 关键：assign 必须立刻返回

连接器线程调用 processor.assign(socket) 之后必须马上回到 accept()，不能等这个请求处理完——否则又退化成第 3 章的串行处理了。这就需要两个线程之间的交接机制。

assign 与 await：两个线程的交接

每个 HttpProcessor 实现了 Runnable，被创建时就启动了自己的「处理器线程」。它的 run 方法是一个循环：等 socket → 处理 → 把自己放回池里。

public void run() {
    while (!stopped) {
        Socket socket = await();        // ⏳ 在这里等连接器线程送来 socket
        if (socket == null)
            continue;
        try {
            process(socket);
        } catch (Throwable t) {
            log("process.invoke", t);
        }
        connector.recycle(this);        // 放回处理器栈
    }
    synchronized (threadSync) {
        threadSync.notifyAll();         // 告诉 threadStop() 我已经退出了
    }
}

assign 运行在连接器线程上，await 运行在处理器线程上。它们通过一个布尔变量 available 加上 wait() / notifyAll() 来配合：

连接器线程：assign(socket)
synchronized void assign(Socket socket) {
    // 上一个 socket 还没被取走就等
    while (available) {
        try { wait(); }
        catch (InterruptedException e) { }
    }
    this.socket = socket;
    available = true;
    notifyAll();        // 叫醒处理器线程
}
处理器线程：await()
private synchronized Socket await() {
    // 没有 socket 可拿就等
    while (!available) {
        try { wait(); }
        catch (InterruptedException e) { }
    }
    Socket socket = this.socket;   // 先拷到局部变量
    available = false;
    notifyAll();        // 叫醒可能在 assign 里等的连接器线程
    return socket;
}

原书留了两个思考题，答案很值得记住：

  • 为什么 await 要先把 this.socket 拷到局部变量再返回？ 因为一旦 available = false 并 notifyAll()，连接器线程就可能马上把下一个 socket 写进 this.socket。局部变量保证当前线程处理的是自己拿到的那一个。
  • 为什么 await 也要 notifyAll()？ 如果连接器线程在 available 还为 true 时又来了一个 socket，它会卡在 assign 的 while (available) wait() 里。处理器线程取走 socket 后必须叫醒它。
⚠ wait 一定要放在 while 循环里

wait() 可能发生「虚假唤醒」（spurious wakeup），被叫醒也不代表条件已经满足。所以总是写成 while (!条件) wait();，而不是 if。这是 Java 并发编程里最经典的规矩之一。

process：一个连接上的请求循环

几个关键变量：

  • ok：处理过程中没有出错；finishResponse：是否需要调用 response.finishResponse()。
  • keepAlive：是否持久连接。HTTP/1.0 设为 false；请求头里有 Connection: close，或 Servlet 设置了 Connection: close 响应头时也设为 false。
  • http11：客户端是否支持 HTTP/1.1，决定能否发 100 Continue、能否分块。
  • sendAck：请求头里有 Expect: 100-continue。

parseHeaders 比第 3 章多处理了 authorization、accept-language、host、connection、expect、transfer-encoding 等头。为了少创建字符串，它把标准头名预先存成 char[]（DefaultHeaders 类），直接比较字符数组。

} else if (header.equals(DefaultHeaders.CONNECTION_NAME)) {
    if (header.valueEquals(DefaultHeaders.CONNECTION_CLOSE_VALUE)) {
        keepAlive = false;
        response.setHeader("Connection", "close");
    }
} else if (header.equals(DefaultHeaders.EXPECT_NAME)) {
    if (header.valueEquals(DefaultHeaders.EXPECT_100_VALUE))

    else
        throw new ServletException(sm.getString("httpProcessor.parseHeaders.unknownExpectation"));

public void start() {
    var counter = new AtomicInteger();
    processors = new ThreadPoolExecutor(minProcessors, maxProcessors, 60, TimeUnit.SECONDS,
            new SynchronousQueue<>(),
            r -> new Thread(r, "HttpProcessor[" + port + "][" + counter.getAndIncrement() + "]"));
    processors.prestartAllCoreThreads();
    thread = new Thread(this, "HttpConnector[" + port + "]");
    thread.start();
}

}
💡 为什么是 SynchronousQueue 而不是 LinkedBlockingQueue？

ThreadPoolExecutor 的规则是「核心线程满了先排队，队列满了才扩到最大线程数」。如果用无界的 LinkedBlockingQueue，队列永远不会满，线程数就永远停在 5，maxProcessors 形同虚设。SynchronousQueue 容量为 0，没有空闲线程时 offer 立即失败，线程池就会去新建线程——这才是原书「不够就新建、到上限就拒绝」的行为。

🔎 原书没提的一个问题：空闲连接

每个持久连接都独占一个处理器线程，哪怕客户端已经不说话了。如果不设超时，20 个浏览器标签页就能把 maxProcessors = 20 占满，后来的请求全被丢弃。Java 17 版用 socket.setSoTimeout(20_000) 让空闲连接超时断开，这正是 Tomcat connectionTimeout 参数（默认 20000 毫秒）的作用。

分块响应

ChunkedHttpResponse 继承第 3 章的 HttpResponse：默认仍然把正文全部缓冲、用 Content-Length 发出；一旦 Servlet 调用 flushBuffer()（表示「我要边算边发」），就改用分块编码：

@Override
public void flushBuffer() throws IOException {
    if (!allowChunking) return;          // HTTP/1.0 不认识分块，只能全部缓冲
    flushWriter();
    if (!isCommitted()) {
        writeHead(true);                 // 响应头里写 Transfer-Encoding: chunked
        chunking = true;
    }
    writeChunk();
    output().flush();
}

private void writeChunk() throws IOException {
    int size = body().size();
    if (size == 0) return;               // 长度为 0 的块是结束标记，不能乱发
    output().write((Integer.toHexString(size) + "\r\n").getBytes(ISO_8859_1));
    body().writeTo(output());
    output().write("\r\n".getBytes(ISO_8859_1));
    body().reset();
}

ⓘ 如果你用的是 Java 21

把线程池换成 Executors.newVirtualThreadPerTaskExecutor()，就能用本章这种最直白的阻塞式写法支撑上万并发连接——虚拟线程阻塞在 IO 上时不占用操作系统线程。不过要注意：虚拟线程没有「上限」，maxProcessors 的限流作用需要用 Semaphore 另行实现。

小结

  • HTTP/1.1 默认持久连接；因此需要 Content-Length 或分块编码来标识响应边界；Expect: 100-continue 让客户端先确认再发大请求体。
  • Tomcat 连接器实现 Connector 接口，创建实现了 catalina.Request/Response 的对象，并调用 container.invoke()。
  • 默认连接器有一个处理器池（min 5、max 20），每个处理器有自己的线程；超过上限的请求被直接丢弃。
  • assign 和 await 用 available 标志加 wait/notifyAll 在两个线程间交接 socket。
  • Java 17 里，ThreadPoolExecutor + SynchronousQueue 能等价地替代这一整套手写机制。
