虚拟线程：同步代码，异步的效率

回顾前几章的演进：第 4 章一个连接一个线程，简单但线程不够用；第 23 章用 NIO 让等客户端不占线程； 第 24 章用异步 Servlet 让等业务不占线程，代价是代码变成了回调。Java 21 的虚拟线程给出了第三条路： 代码仍然按同步阻塞的方式写，而阻塞时由 JDK 自动把线程「挪开」。Tomcat 11 只需要一个连接器属性就能用上它。

本章目标

  • 理解虚拟线程和平台线程的区别：M:N 调度、挂载与卸载
  • 知道什么是「钉住」（pinning），以及 JDK 24 做了什么改进
  • 会在 Tomcat 11 里开启虚拟线程，并理解它替换了连接器的哪一部分
  • 比较线程池、异步 Servlet、虚拟线程三种模型的适用场景
  • 知道去掉线程池之后，并发限制要放到哪里
💡 本章需要 JDK 21+

配套工程整体用 --release 17 编译。本章用到虚拟线程 API 的代码放在单独的 src/main/java21 目录， 由 pom.xml 里的 java21 profile 在 JDK 21 及以上自动编译；用 JDK 17 构建时这部分会被跳过，其余章节不受影响。

平台线程与虚拟线程

在 Java 21 之前，每个 java.lang.Thread 都对应一个操作系统线程（现在叫平台线程）。 它的栈由操作系统分配，默认 512 KB～1 MB，创建和切换都要进内核。几千个还行，几十万个就不现实了。 虚拟线程也是 java.lang.Thread，但由 JDK 自己调度：

挂载与卸载

关键在于虚拟线程阻塞时发生了什么。JDK 把所有阻塞操作（Thread.sleep、socket 读写、BlockingQueue.take、Lock……）都改造过： 在虚拟线程里调用时，它们不会让载体线程睡着，而是把虚拟线程的栈帧复制到堆上（卸载），载体线程转去执行别的虚拟线程； 等阻塞的条件满足（数据到了、时间到了），虚拟线程被重新放进调度队列，由任意一个空闲的载体线程接着执行（挂载）。

本章的实验正好捕捉到了这个过程：同一个虚拟线程，睡之前在 ForkJoinPool-1-worker-2 上，睡醒后跑到了 worker-1 上。 这和第 23 章的 SocketWrapper 是同一个思想——把「执行到哪儿了」从线程身上拿走——只是这次由 JDK 替所有代码做了。

钉住：虚拟线程卸载不了的时候

有两种情况虚拟线程阻塞时无法卸载，只能连同载体线程一起阻塞，叫做钉住（pinning）：

  • 在 synchronized 块或方法里阻塞（JDK 21～23）。原因是对象监视器的实现记录的是持有它的载体线程。JDK 24 的 JEP 491 重写了这部分，synchronized 里阻塞也能正常卸载了。
  • 在本地方法（JNI）或外部函数调用期间阻塞——这一条至今仍然成立。

在 JDK 21～23 上，排查钉住可以加 JFR 事件 jdk.VirtualThreadPinned（默认阈值 20 ms）。 建议是：在会阻塞的临界区里优先用 ReentrantLock；升级到 JDK 24+ 后这个问题基本消失。

Tomcat 11 里的虚拟线程

回到第 23 章的三类线程：Acceptor 和 Poller 不变，变的是 Worker。开启 useVirtualThreads="true" 后， 连接器不再使用 ThreadPoolExecutor，而是换成一个为每个任务新建虚拟线程的执行器： 

<Connector port="8080" protocol="HTTP/1.1" useVirtualThreads="true" />

Servlet 代码一行都不用改。Spring Boot 3.2+ 对应的开关是 spring.threads.virtual.enabled=true，它做的就是给 Tomcat 设置这个属性。

三种模型的比较

线程池（第 23 章）异步 Servlet（第 24 章）虚拟线程（本章）
代码风格同步阻塞回调 / Future同步阻塞
等待时占用一个平台线程什么都不占几 KB 堆内存
并发上限maxThreads取决于业务的异步能力基本只受内存和下游资源限制
需要什么什么都不需要下游必须提供异步 APIJDK 21+；临界区避免钉住
调试栈清晰栈被回调打断栈清晰（jcmd Thread.dump_to_file 能导出虚拟线程）
适合CPU 密集、并发量可预估推送、长轮询、已有响应式栈IO 密集、大量阻塞调用的普通业务
⚠️ 线程池曾经在悄悄替你限流

maxThreads=200 除了限制线程数，还隐含了「最多 200 个请求同时访问数据库」。换成虚拟线程后， 1 万个并发请求会同时冲向只有 20 个连接的连接池，变成 1 万个线程排队等连接，或者把下游服务压垮。 去掉线程池之后，要在真正稀缺的资源前面显式限流：连接池本身、Semaphore、限流器。 另外，用 ThreadLocal 缓存大对象（例如每线程一个 SimpleDateFormat、缓冲区）的老技巧也不再划算——线程不再复用，缓存每次都是新的。

② 三个实验

// 必须在第一个虚拟线程创建之前设置：载体线程只用 2 个，让钉住的效果更明显
System.setProperty("jdk.virtualThreadScheduler.parallelism", "2");

time("平台线程池（200 个线程）", Executors.newFixedThreadPool(200), 2000, VirtualThreadsDemo::sleepTask);
time("虚拟线程（每任务一个）  ", Executors.newVirtualThreadPerTaskExecutor(), 2000, VirtualThreadsDemo::sleepTask);

Thread vt = Thread.ofVirtual().name("demo-vt").start(() -> {
    System.out.println("  睡之前：" + Thread.currentThread());
    sleep(100);
    System.out.println("  睡之后：" + Thread.currentThread());
});

time("synchronized 里 sleep   ", Executors.newVirtualThreadPerTaskExecutor(), 8, i -> {
    Object lock = new Object();                  // 每个任务一把锁，没有任何竞争
    synchronized (lock) {
        sleep(500);                              // JDK 21–23：虚拟线程被钉在载体线程上
    }
});

private static void time(String label, ExecutorService executor, int n, Task task) {
    try (executor) {                             // Java 19+：close() 等待所有任务完成
        IntStream.range(0, n).forEach(i -> executor.submit(() -> task.run(i)));
    }
}

设计要点

这一章的代码里有几个可以带到别的项目里的设计决定。每条按「做法 → 取舍 → 替代方案 → 还能用在哪」来写；系统的讨论见设计篇。

1把复杂度下沉到平台

第 23、24 章手写的「保存状态、归还线程、稍后恢复」，虚拟线程由 JDK 在所有阻塞点统一完成。

取舍
业务代码保持同步写法，可读、可调试；代价是依赖平台的正确实现，以及钉住这类「抽象泄漏」需要了解底层才能排查。
替代方案
在应用层用响应式框架（Reactor、RxJava）。
还能用在
设计内部框架时：能在框架层解决的横切问题（重试、超时、上下文传递），不要让每个业务方各写一遍。
延伸：第 29 章 · 整体架构：分层与边界
2只替换一个组件来引入新能力

Tomcat 只把 Worker 的执行器换成虚拟线程版本，Acceptor、Poller、Processor、容器都没动。

取舍
一个开关就能启用或回退，风险可控；前提是当初把「执行器」抽象成了可替换的组件（Executor 接口）。
还能用在
把线程池、HTTP 客户端、序列化器做成可注入的依赖，将来换实现时只动装配代码。
延伸：第 30 章 · 扩展点设计
3限流要限在稀缺资源上

线程池大小曾经同时起到「限制线程数」和「限制下游并发」两个作用；去掉线程池后，后者要显式实现。

取舍
显式限流更精确（数据库 20、某个慢服务 5），但需要逐一识别稀缺资源；隐式限流简单却粗糙。
还能用在
任何用并发换吞吐的地方：批处理任务、爬虫、消息消费者——用 Semaphore 或令牌桶保护下游，而不是靠线程数。
延伸：第 32 章 · 并发、隔离与演进
4一份代码兼容多个 JDK 版本

Maven profile 按 JDK 版本额外编译一个源码目录，基线版本不受影响。

取舍
能提前使用新特性又不抛弃老用户；代价是构建配置更复杂，要在 CI 里同时测试两个版本。
替代方案
多版本 jar（Multi-Release JAR，META-INF/versions/21/）、反射调用新 API。
还能用在
开源库的平滑升级：Tomcat 11 自己也用分版本的兼容层（JreCompat 一族）在 Java 17 基线上使用新 JDK 的特性。

小结

  • 虚拟线程是 JDK 调度的轻量线程，M:N 挂载在少量载体线程（ForkJoinPool）上，阻塞时卸载、就绪后重新挂载。
  • 在 synchronized 里（JDK 21～23）或本地调用中阻塞会钉住载体线程；JDK 24 的 JEP 491 解决了前者。
  • Tomcat 11 用 useVirtualThreads="true" 把 Worker 线程池换成每任务一个虚拟线程，Servlet 代码不变。
  • 虚拟线程适合 IO 密集的同步代码；CPU 密集任务没有收益。
  • 去掉线程池之后，要在连接池、Semaphore 等稀缺资源前显式限流，并重新审视 ThreadLocal 缓存。

动手练习

  1. 在 EmbeddedVirtualThreads 的 Servlet 里加一个 Semaphore(10) 保护「数据库调用」（sleep(200)），用 LoadClient 发 200 个请求，计算并验证总耗时。
  2. 用 -Djdk.tracePinnedThreads=full（JDK 21～23 可用）运行 VirtualThreadsDemo，看看钉住时打印的栈。
  3. 写一个 CPU 密集的任务（例如计算 30 万以内的质数个数），分别用平台线程池和虚拟线程跑 100 个，比较耗时并解释结果。
  4. 用 jcmd <pid> Thread.dump_to_file -format=json dump.json 导出 Tomcat 虚拟线程模式下的线程转储，找到正在 sleep 的虚拟线程。
