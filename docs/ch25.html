可插拔性：注解、SCI 与 Spring Boot 的启动

原书里，Web 应用的一切都写在 web.xml 中，第 15 章的 Digester 把它变成 Wrapper。 Servlet 3.0（2009 年）引入了「可插拔性」：Servlet 可以用注解声明，第三方 jar 可以自带配置片段， 甚至可以在启动时用代码注册组件。今天的 Spring Boot 应用干脆没有 web.xml，main 方法里一行 SpringApplication.run() 就启动了 Tomcat。这一章讲清楚这些机制，并写一个能跑的「迷你 Spring Boot」。

本章目标

  • 知道一个 Web 应用的配置可以来自四个地方：web.xml、web-fragment.xml、注解、编程式注册
  • 理解 ContextConfig 如何扫描、排序、合并它们，以及 metadata-complete 的作用
  • 掌握 ServletContainerInitializer + @HandlesTypes 这个「插件发现」机制
  • 说出 Spring Boot 启动嵌入式 Tomcat 的过程，以及它为什么不用容器自带的注解扫描

配置的四个来源

第 15 章的 ContextConfig 只做一件事：解析 web.xml。Servlet 3.0 之后，它要从四个地方收集配置，合并成一份「有效配置」，再交给 StandardContext：

来源谁写适合对应的 Tomcat 代码
web.xml应用开发者需要集中查看、由运维覆盖的配置ContextConfig.webConfig() 用 Digester 解析
web-fragment.xml库的作者库自带的 Servlet、过滤器，用户加个 jar 就生效JarScanner 扫描 WEB-INF/lib，按 <ordering> 排序后合并
注解应用开发者配置和代码放在一起，少写 XML用 BCEL 风格的字节码解析器读 class 文件，不加载类
SCI 编程式注册框架作者要根据条件、配置决定注册什么WebappServiceLoader 按 META-INF/services 发现

合并规则与 metadata-complete

三者冲突时，web.xml 优先：同名的 Servlet，web.xml 里的设置覆盖注解里的。 web.xml 根元素上的 metadata-complete="true" 表示「我这份 web.xml 已经是完整的了」， 容器就跳过注解扫描和 web-fragment.xml。这能明显缩短大应用的启动时间——扫描几百个 jar 的字节码并不便宜。 但它不会关闭 SCI：本章的实验会验证这一点。要控制 SCI，得用 <absolute-ordering> 排除 jar， 或者 Tomcat 的 containerSciFilter。

这正是 Spring MVC 在传统 WAR 部署下的启动方式：spring-web.jar 里的 SpringServletContainerInitializer 标注了 @HandlesTypes(WebApplicationInitializer.class)， 容器把应用里所有 WebApplicationInitializer 的实现交给它，其中一个实现（Spring Boot 的 SpringBootServletInitializer）再去调用 SpringApplication。Tomcat 自己的 WebSocket 支持（第 26 章）也是一个 SCI：WsSci。

🔑 为什么扫描字节码而不是加载类？

加载类会执行静态初始化块，可能触发连锁加载、产生副作用，甚至因为缺少可选依赖而失败。 Tomcat 用自带的字节码解析器（org.apache.tomcat.util.bcel）直接读 class 文件的常量池和注解表， 只有确定需要时才加载。我们的 ClassScanner 为了简单用了 Class.forName(name, false, loader)（不初始化）， 但仍然会触发类加载，大项目里不要这样做。

Spring Boot 怎样启动 Tomcat

传统部署是「Tomcat 里装应用」：先有容器，容器发现应用。Spring Boot 反过来，是「应用里装 Tomcat」： 先有 Spring 的 ApplicationContext，它在刷新过程中创建并启动一个嵌入式 Tomcat。

几个值得注意的设计决定：

  • 不用容器的注解扫描。嵌入式 Context 不做 @WebServlet 扫描（只有加了 @ServletComponentScan 才会，而且是 Spring 自己扫）。 Servlet、过滤器都是 Spring bean，通过 ServletContextInitializer 注册——这样它们能享受依赖注入、条件装配、@Order 排序。
  • 只有一个 SCI。TomcatStarter 是 Boot 交给 Tomcat 的唯一入口，Boot 不依赖 META-INF/services 的 SCI 发现，避免类路径上随便一个 jar 改变应用的行为。
  • 端口最后才打开。Tomcat 启动时连接器被暂时移除，等整个 ApplicationContext 刷新完成才加回来并启动。否则负载均衡器可能在应用还没准备好时就把流量打过来。
  • 非守护线程保活。Tomcat 的线程都是守护线程，main 返回后 JVM 会退出，所以 Boot 启动一个名为 container-0 的非守护线程调用 await()。

① MiniBoot：一个方法的 Spring Boot

MiniBoot.run(主类) 复刻了上图左侧和中间的流程：扫描主类所在的包，创建 Tomcat， 用 addContext（不带 ContextConfig，所以 Tomcat 不扫描注解）加一个 Context， 再注册一个自己的 SCI，在里面用编程式 API 注册扫描到的组件： 

public static Tomcat run(Class<?> primary, String... args) throws Exception {
    List<Class<?>> classes = ClassScanner.scan(primary.getClassLoader(), primary.getPackageName());

    var tomcat = new Tomcat();
    tomcat.setBaseDir(Files.createTempDirectory("miniboot").toString());
    tomcat.setPort(port);
    Context ctx = tomcat.addContext("", docBase);                // 不带 ContextConfig：Tomcat 不扫描
    ctx.addServletContainerInitializer(new MiniBootStarter(classes), null);   // ≈ TomcatStarter
    tomcat.start();

    // Tomcat 的线程都是守护线程，main 返回后 JVM 会退出
    Thread await = new Thread(() -> tomcat.getServer().await(), "container-0");
    await.setDaemon(false);
    await.start();
    return tomcat;
}

for (Class<?> c : classes) {
    WebServlet s = c.getAnnotation(WebServlet.class);
    if (s == null) continue;
    String name = s.name().isEmpty() ? c.getName() : s.name();
    var reg = sc.addServlet(name, c.asSubclass(Servlet.class));   // 编程式注册
    reg.addMapping(s.urlPatterns().length > 0 ? s.urlPatterns() : s.value());
    reg.setLoadOnStartup(s.loadOnStartup());
    reg.setAsyncSupported(s.asyncSupported());
    for (WebInitParam p : s.initParams()) reg.setInitParameter(p.name(), p.value());
}
// …@WebListener、@WebFilter 同理；AppInitializer 的实现类实例化后调用 onStartup(sc)

② Tomcat 原生的可插拔性

第二个示例反过来：让 Tomcat 自己扫描。它在启动前用代码拼出一个 Web 应用目录—— WEB-INF/classes 里放带 @WebServlet 的类和一个 PluginModule 实现， WEB-INF/lib 里用 JarOutputStream 现场打一个 plugin.jar，内含 SCI 声明、 web-fragment.xml 和插件类。然后像第 15 章一样给 Context 装上 ContextConfig： 

@HandlesTypes(PluginModule.class)
public class PluginInitializer implements ServletContainerInitializer {

    @Override
    public void onStartup(Set<Class<?>> classes, ServletContext sc) {
        System.out.println("[PluginInitializer] 容器传入的 @HandlesTypes 类：" + classes);
        if (classes == null) return;                         // 一个实现类都没有时是 null
        for (Class<?> c : classes) {
            if (c.isInterface() || Modifier.isAbstract(c.getModifiers())) continue;
            ((PluginModule) c.getDeclaredConstructor().newInstance()).register(sc);
        }
    }
}

try (var jar = new JarOutputStream(Files.newOutputStream(lib.resolve("plugin.jar")))) {
    put(jar, "META-INF/services/jakarta.servlet.ServletContainerInitializer",
            "modern.ch25.plugin.PluginInitializer\n");
    put(jar, "META-INF/web-fragment.xml", """
            <web-fragment xmlns="https://jakarta.ee/xml/ns/jakartaee" version="6.1">
              <name>plugin</name>
              <servlet>…FragmentServlet…</servlet>
              <servlet-mapping>…/fragment…</servlet-mapping>
            </web-fragment>
            """);
    // …再把 modern/ch25/plugin/*.class 放进去
}

Context ctx = tomcat.addContext("/app", app.toString());
var config = new ContextConfig();                      // 解析 web.xml、扫描注解、运行 SCI
config.setDefaultWebXml(Constants.NoDefaultWebXml);
ctx.addLifecycleListener(config);

设计要点

这一章的代码里有几个可以带到别的项目里的设计决定。每条按「做法 → 取舍 → 替代方案 → 还能用在哪」来写；系统的讨论见设计篇。

1用 ServiceLoader 约定发现插件

jar 在 META-INF/services/接口名 里写上实现类名，宿主不需要知道插件的存在。

取舍
零配置、加 jar 即生效；代价是「隐式」：类路径上多一个 jar 就可能改变应用行为，排查时要知道去看 services 文件。
替代方案
显式注册（Spring Boot 选择的方式）、配置文件列出插件类名。
还能用在
JDBC 驱动（java.sql.Driver）、SLF4J 绑定、Spring Boot 的 AutoConfiguration.imports：任何「库自带扩展」的场景。
延伸：第 30 章 · 扩展点设计
2声明式与编程式两条路

同一件事（注册 Servlet）既可以用 web.xml / 注解声明，也可以用 ServletContext.addServlet 写代码。

取舍
声明式一目了然、工具友好；编程式能根据条件和配置动态决定。代价是两条路都要维护，还要定义冲突时谁优先（web.xml 优先）。
还能用在
Spring 的 XML / 注解 / Java Config、Gradle 的 DSL 与插件 API：先提供编程式 API，再在其上构建声明式语法。
延伸：第 29 章 · 整体架构：分层与边界
3控制反转的反转

传统部署是容器加载应用；Spring Boot 让应用创建容器，并且只给容器一个入口（TomcatStarter）。

取舍
应用掌握启动顺序（例如等所有 bean 就绪再开端口）、部署变成一个 jar；代价是一个 JVM 只跑一个应用，失去了容器级的多应用管理（第 18、19 章的那些能力）。
还能用在
需要嵌入数据库（H2）、消息队列（嵌入式 Kafka/Artemis）做测试或单机部署的场景：把「服务器」当作一个可以 new 出来的库。
延伸：第 29 章 · 整体架构：分层与边界
4准备就绪之后再接流量

Spring Boot 启动 Tomcat 时先摘掉连接器，等整个应用上下文刷新完才装回去。

取舍
不会有请求打到半初始化的应用上；代价是启动流程多了一个特殊步骤，自定义启动逻辑时要理解它。
还能用在
Kubernetes 的 readiness 探针、消息消费者在依赖就绪后才开始拉取：把「进程活着」和「可以服务」分成两个状态。

小结

  • Servlet 3.0 之后，应用配置来自 web.xml、web-fragment.xml、注解、SCI 编程式注册四个来源，由 ContextConfig 合并，web.xml 优先。
  • metadata-complete="true" 跳过注解扫描和 web-fragment，但不影响 SCI。
  • SCI 通过 META-INF/services 发现，@HandlesTypes 让容器把应用中指定类型的实现交给它，是库「自我装配」的标准方式。
  • Spring Boot 让应用创建嵌入式 Tomcat，只注册一个 SCI（TomcatStarter），用 Spring bean 注册 Servlet 和过滤器，并在上下文就绪后才打开端口。

动手练习

  1. 给 MiniBoot 增加 @Order 支持：AppInitializer 和 @WebFilter 按注解里的数字排序注册，验证过滤器执行顺序随之改变。
  2. 模仿 Spring Boot「最后才开端口」：在 MiniBoot.run 里先 tomcat.getService().removeConnector(...)，模拟一段 3 秒的初始化，再加回连接器并启动它。启动期间用 curl 观察连接被拒绝。
  3. 在 EmbeddedPluggability 的 web.xml 里加一个同名的 modern.ch25.webapp.AnnotatedServlet 映射到 /xml，观察 web.xml 和注解的映射是合并还是覆盖。
  4. 给 web.xml 加上 <absolute-ordering/>（空的），看看插件 jar 的 SCI 和 web-fragment 是否还会生效。
