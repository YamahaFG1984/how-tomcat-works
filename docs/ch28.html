运维：调优、监控与加固

前面 27 章讲 Tomcat 怎么工作，这一章讲怎么让它在生产环境里好好工作。内容分四块：线程和 JVM 参数怎么定， 出了问题看哪些指标，重载为什么会泄漏内存，以及上线前的安全清单。每一块都对应前面的某几章——运维的知识， 本质上是把原理换成了「旋钮」和「仪表盘」。

本章目标

  • 会用利特尔法则估算线程数，知道哪些连接器参数必须显式设置
  • 知道「四个黄金信号」分别对应 Tomcat 的哪些 MBean 属性，能把它们导出给 Prometheus
  • 理解类加载器泄漏的引用链，认识 Tomcat 的泄漏检测和防护机制
  • 能对照清单完成一次 Tomcat 安全加固

调优：线程数从哪里来

maxThreads 设多少？拍脑袋的答案是 200（默认值），算出来的答案来自利特尔法则： 系统中同时在处理的请求数 = 到达速率 × 每个请求的停留时间。

除了线程数，以下参数都应该显式写在配置里，哪怕取值和默认值一样——它本身就是一份文档：

参数Tomcat 11 默认建议原理在哪一章
maxThreads / minSpareThreads200 / 10按上图估算；虚拟线程模式下不再适用第 23、27 章
acceptCount / maxConnections100 / 8192前面有负载均衡器时可以调小，让过载更早暴露第 23 章
connectionTimeout60000 ms10～20 秒，防慢速攻击第 23 章
keepAliveTimeout同 connectionTimeout大于负载均衡器的空闲超时，否则会出现偶发的 502第 4、23 章
maxHttpHeaderSize8 KB按需调整，不要随意放大第 3 章
maxPostSize / maxParameterCount2 MB / 1000限制表单大小和参数个数，防资源耗尽第 3、22 章

JVM 参数

  • 堆：容器环境用 -XX:MaxRAMPercentage=75 代替固定的 -Xmx，让堆随容器内存限制变化。
  • GC：JDK 17/21 默认的 G1 适合大多数场景；对延迟敏感的服务可以试 ZGC（JDK 21 起有分代 ZGC，-XX:+UseZGC -XX:+ZGenerational，JDK 23 起分代成为默认）。
  • 出事时留证据：-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=…，以及 -Xlog:gc*:file=gc.log。
  • JPMS 开放：Tomcat 的 catalina.sh 默认加了若干 --add-opens，泄漏检测依赖它们（后面会看到）。嵌入式部署要自己加。

监控：四个黄金信号

Google SRE 的「四个黄金信号」——延迟、流量、错误、饱和度——在 Tomcat 里都有现成的数据源，它们就是第 20 章的 MBean：

流量type=GlobalRequestProcessorrequestCount、bytesSent计数器，取变化率得到每秒请求数

延迟同上processingTime、maxTime累计时间 / 请求数 = 平均值；分位数要靠访问日志或 Micrometer 的直方图

✅ 「服务器卡住了」先打线程转储

所有工作线程都忙、请求排队时，连打三次线程转储（间隔几秒），看这些 http-nio-…-exec-* 线程停在哪里。 对照第 23 章那张调用栈：停在 SocketInputStream.read / JDBC 驱动里说明在等下游，停在 synchronized 上说明有锁竞争， 停在业务代码的循环里说明是 CPU 问题。

重载与内存泄漏

第 8 章的热重载原理很漂亮：丢掉旧的类加载器，新建一个，旧的类连同静态字段一起被 GC 回收。 但只要有任何一个活得比应用久的对象还引用着旧类加载器加载的任何一个对象，整个类加载器—— 以及它加载的所有类、所有静态字段——都回收不了。重载几次之后，Metaspace 和堆就被撑爆了。

泄漏来源Tomcat 的检测 / 防护应用该怎么做
ThreadLocal 留在容器线程上停止时扫描所有线程并报 SEVERE；ThreadLocalLeakPreventionListener 逐步替换线程池里的线程用完 remove()，或者在过滤器的 finally 里清理
应用启动的线程没停报 WARNING（clearReferencesStopThreads 可以强行停止，有风险）在 ServletContextListener.contextDestroyed 里停掉自己的线程池
JDBC 驱动注册在 DriverManager 里停止时自动注销并警告驱动放在 Tomcat 的 lib 而不是 WEB-INF/lib
JDK 内部的单例抓住了上下文类加载器JreMemoryLeakPreventionListener 在启动时用系统类加载器预先触发这些单例—
RMI、Timer、关闭钩子、MBean部分检测在 contextDestroyed 里对称地注销
🔑 最好的防护：生产环境不做热重载

泄漏检测能发现问题，但不能保证清理干净。今天更常见的做法是不可变部署：每次发布启动一个新进程（新容器）， 流量切过去之后直接结束旧进程。进程退出，所有内存自然归还操作系统。热重载留给开发环境。

优雅停机

发布时直接 kill -9 会让正在处理的请求失败。优雅的顺序是：先让负载均衡器摘除节点（就绪探针返回失败）， 然后停止接收新连接，等在途请求处理完（有超时），最后关闭。Tomcat 的 Service 有 gracefulStopAwaitMillis 属性控制等待时间； Spring Boot 对应 server.shutdown=graceful。这正是第 11 章 unload() 等待 countAllocated 归零、第 16 章关闭钩子调用 stop() 的组合。

⚠️ 一个单位的坑

第一版用的是很多老教程里的 %Dms，结果一个睡了 300 ms 的请求在日志里显示 308683ms。 Tomcat 10 把 %D 改成了微秒，与 Apache httpd 保持一致；毫秒用 %{ms}T。升级大版本时，日志解析和告警规则都要跟着检查。

③ 复现类加载器泄漏

ClassLoaderLeakDemo 用一个父加载器为 platform 类加载器的 URLClassLoader 加载插件（看不到应用类路径，像 WebappClassLoader 一样独立）， 在一个「容器线程」上调用插件，让它往 ThreadLocal 里放一个 10 MB 的对象，然后丢掉类加载器、触发 GC，用 WeakReference 判断它是否被回收： 

public class LeakyPlugin implements Consumer<String> {
    private static final ThreadLocal<Payload> CACHE = new ThreadLocal<>();
    @Override public void accept(String command) {
        switch (command) {
            case "start" -> CACHE.set(new Payload());
            case "stop" -> CACHE.remove();
        }
    }
    static final class Payload { final byte[] data = new byte[10 * 1024 * 1024]; }
}

// ClassLoaderLeakDemo
var loader = new URLClassLoader(new URL[] {dir.toUri().toURL()}, ClassLoader.getPlatformClassLoader());
var plugin = (Consumer<String>) loader.loadClass("modern.ch28.leak.LeakyPlugin").getConstructor().newInstance();
threads.submit(() -> plugin.accept("start")).get();                    // 请求在容器线程上执行
if (cleanUp) threads.submit(() -> plugin.accept("stop")).get();        // 应用停止时清理
loader.close();
return new WeakReference<>(loader);                                    // 之后只剩弱引用

设计要点

这一章的代码里有几个可以带到别的项目里的设计决定。每条按「做法 → 取舍 → 替代方案 → 还能用在哪」来写；系统的讨论见设计篇。

1可观测性从第一天就内建

Tomcat 的每个核心组件都把运行状态注册为 MBean（第 20 章），所以今天接 Prometheus 只需要一个翻译层。

取舍
组件要多维护一套计数器和描述符；回报是任何监控系统都能接入，而不用改核心代码。
还能用在
自研中间件、任务调度器：在核心对象里维护计数器并统一注册（Micrometer 的 MeterRegistry），而不是在出事后到处加日志。
延伸：第 32 章 · 并发、隔离与演进
2安全的默认值 + 显式的配置

listings=false、readonly=true、HttpOnly 都是默认开启的；但错误页详情、关闭端口、AJP 的历史默认值曾经不安全。

取舍
默认安全会让「开箱即用」的体验差一点（例如看不到详细错误）；默认方便则把风险留给不看文档的用户。Tomcat 在 Ghostcat 之后把 AJP 改成了默认安全。
还能用在
任何对外暴露的组件：默认只监听本机、默认需要认证、默认关闭调试接口，需要时显式打开。
延伸：第 30 章 · 扩展点设计
3资源的获取和释放要对称

每一种泄漏都是「启动时注册了、停止时没注销」：ThreadLocal、线程、驱动、钩子、MBean。

取舍
要求每个组件都有明确的 stop 逻辑（第 6 章生命周期）；没有它，长期运行的进程只能靠重启来回收资源。
还能用在
插件系统、热加载的规则引擎、测试框架：用 try-with-resources 或生命周期回调成对地管理资源，并在测试里断言卸载后对象可被回收。
延伸：第 32 章 · 并发、隔离与演进
4检测不了就重来

泄漏检测只能尽力而为，所以现代部署倾向于用进程级的「整体替换」代替进程内的热重载。

取舍
重启比重载慢、需要多一份实例做滚动发布；换来的是确定性——进程退出后不会有任何残留。
还能用在
配置变更、依赖升级、长时间运行的批处理 worker 定期回收：与其修补状态，不如丢弃重建。

小结

  • 线程数用利特尔法则估算，并受下游容量约束；连接器的关键参数应显式配置。
  • 四个黄金信号都能从 Tomcat 的 MBean 读到：GlobalRequestProcessor 给出流量、错误、延迟，ThreadPool 给出饱和度。
  • 访问日志记录每个请求的耗时（Tomcat 10 起 %D 是微秒），线程转储用来定位卡顿。
  • 重载泄漏的本质是一条从长寿对象指向旧类加载器的引用链；Tomcat 能检测 ThreadLocal 和线程泄漏，但需要 --add-opens。
  • 加固：删除默认应用、限制管理入口、关闭关闭端口和 AJP、隐藏错误详情、限制请求大小、及时升级。

动手练习

  1. 给 MetricsServlet 增加一个请求耗时直方图：写一个过滤器记录每个请求的耗时，按 10/50/100/500/1000 ms 分桶，输出 Prometheus 的 _bucket 格式。
  2. 修改 LeakyServlet：实现一个 ServletContextListener，在 contextDestroyed 里停止后台线程；再写一个过滤器在 finally 里 BUFFER.remove()，确认 Tomcat 不再报警。
  3. 用 jcmd <pid> GC.class_histogram | grep WebappClassLoader 观察 ClassLoaderLeakDemo 风格的泄漏在真实 Tomcat 中多次 reload 后的类加载器数量。
  4. 给 EmbeddedOps 实现优雅停机：收到关闭信号后先让 /health 返回 503，等 5 秒，再调用 tomcat.stop()。
