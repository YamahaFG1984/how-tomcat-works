第 8 章

载入器

前几章我们用一个普通的 URLClassLoader 加载 Servlet。真正的 Servlet 容器不能这么做： 它要防止 Web 应用看到不该看的类，要让每个应用拥有独立的类空间，还要在类文件被重新编译后自动重新加载。 这些都由 Web 应用载入器 WebappLoader 和它内部的 WebappClassLoader 完成。

本章目标

  • 复习 Java 的类加载器层次和双亲委派模型，理解它为什么关乎安全
  • 理解 Tomcat 为什么需要自己的类加载器：隔离、缓存、自动重载
  • 掌握 Loader / Reloader 接口、WebappLoader、WebappClassLoader 的分工
  • 读懂 WebappClassLoader 的加载顺序：何时问父加载器，何时自己加载

Java 的类加载器

每次创建一个类的实例，JVM 都要先把这个类加载进内存，这件事由类加载器完成。从 J2SE 1.2 起，JVM 有三个类加载器，它们是父子关系：

你可以继承 java.lang.ClassLoader 写自己的类加载器。Tomcat 需要自定义类加载器的理由有三：

  • 指定加载规则：Servlet 只能使用 WEB-INF/classes 和 WEB-INF/lib 里的类，不能随意访问 JVM CLASSPATH 上的其他类（比如容器自己的内部类）。
  • 缓存已加载的类，也缓存「找不到」的类名，避免重复查找。
  • 预加载和自动重载：类文件被重新编译后，不重启 Tomcat 就能生效。

本章两个术语：仓库（repository）是类加载器会去搜索的位置；资源（resources）指类加载器中的一个 DirContext 对象，它的文档根目录指向 Context 的 docBase。

Loader 与 Reloader 接口

注意区分：Tomcat 的 Loader 是「Web 应用载入器」，不是类加载器。它内部持有一个类加载器，通过 getClassLoader() 取得。

public interface Loader {
    public ClassLoader getClassLoader();
    public Container getContainer();
    public void setContainer(Container container);
    public DefaultContext getDefaultContext();
    public void setDefaultContext(DefaultContext defaultContext);
    public boolean getDelegate();                 // 是否先委派给父加载器
    public void setDelegate(boolean delegate);
    public String getInfo();
    public boolean getReloadable();               // 是否支持自动重载
    public void setReloadable(boolean reloadable);
    public void addPropertyChangeListener(PropertyChangeListener listener);
    public void addRepository(String repository);
    public String[] findRepositories();
    public boolean modified();                    // 仓库里有类被改过吗？
    public void removePropertyChangeListener(PropertyChangeListener listener);
}

// 支持自动重载的类加载器必须实现它
public interface Reloader {
    public void addRepository(String repository);
    public String[] findRepositories();
    public boolean modified();
}

Loader 只负责发现修改，自己不做重载，而是调用 Context 的 reload()（第 12 章）。StandardContext 默认不开启重载，需要在 server.xml 里写：

<Context path="/myApp" docBase="myApp" debug="0" reloadable="true"/>

WebappLoader 启动时做了什么

WebappLoader 实现了 Lifecycle，由关联的容器启停。它的 start() 完成五件事：

  1. 创建类加载器：没有 setClassLoader，而是用 loaderClass 属性（默认 WebappClassLoader 的类名）通过反射创建，想换成自己的类加载器就继承 WebappClassLoader 并调用 setLoaderClass。
  2. 设置仓库：把 WEB-INF/classes 交给 addRepository，把 WEB-INF/lib 交给 setJarPath。
  3. 设置类路径：把类路径字符串存进 ServletContext 属性，供 Jasper JSP 编译器使用。
  4. 设置权限：启用了安全管理器时，授予访问 WEB-INF/classes、WEB-INF/lib 的权限。
  5. 启动自动重载线程：如果 reloadable，每隔 checkInterval（默认 15）秒检查一次。
public void run() {
    while (!threadDone) {
        threadSleep();                       // 睡 checkInterval 秒
        if (!started)
            break;
        try {
            if (!classLoader.modified())     // 有类被修改吗？
                continue;
        } catch (Exception e) {
            log(sm.getString("webappLoader.failModifiedCheck"), e);
            continue;
        }
        notifyContext();                     // 通知 Context 重载
        break;
    }
}

private void notifyContext() {
    WebappContextNotifier notifier = new WebappContextNotifier();
    (new Thread(notifier)).start();          // 另开一个线程！
}

protected class WebappContextNotifier implements Runnable {
    public void run() {
        ((Context) container).reload();
    }
}
ⓘ Tomcat 5 的变化

Tomcat 5 起 WebappLoader 不再自己开线程，而是由 ContainerBase 里唯一一个后台线程定期调用各容器的 backgroundProcess()，再由 StandardContext 调用 loader.backgroundProcess() 检查修改。这样一整个 Tomcat 只需要一个后台线程（第 12 章）。

WebappClassLoader

WebappClassLoader 继承 URLClassLoader，设计上兼顾了性能和安全。

安全：有些类必须交给父加载器

// 这些类绝不允许 Web 应用自己加载
private static final String[] triggers = {
    "javax.servlet.Servlet"                // Servlet API
};

// 这些包（及其子包）的类必须先委派给父加载器
private static final String[] packageTriggers = {
    "javax",                               // Java 扩展
    "org.xml.sax",                         // SAX 1 & 2
    "org.w3c.dom",                         // DOM 1 & 2
    "org.apache.xerces",                   // Xerces 1 & 2
    "org.apache.xalan"                     // Xalan
};

道理很简单：如果某个 Web 应用在 WEB-INF/lib 里放了一个自己的 servlet-api.jar，而容器又用它加载了 javax.servlet.Servlet，那么这个应用里的 Servlet 和容器认识的 Servlet 就是「两个不同的类」，强转时会抛 ClassCastException。

性能：两级缓存

每个可被加载的类（无论来自目录还是 JAR）在 Tomcat 里叫一个资源，用 ResourceEntry 表示：

public class ResourceEntry {
    public long lastModified = -1;           // 修改时间：判断是否需要重载
    public byte[] binaryContent = null;      // 类的字节码
    public Class loadedClass = null;
    public URL source = null;
    public URL codeBase = null;
    public Manifest manifest = null;
    public Certificate[] certificates = null;
}

已加载的资源放在 HashMap resourceEntries 中；找不到的类名放在 HashMap notFoundResources 中，下次直接抛 ClassNotFoundException。此外 java.lang.ClassLoader 自身也会记住加载过的类（findLoadedClass）。

加载顺序

🔑 为什么 Web 应用要「子优先」？

两个 Web 应用可能依赖同一个库的不同版本（比如一个用 Jackson 2.9，一个用 2.17）。如果先问父加载器，大家只能共用父加载器里那一个版本。子优先让每个应用优先使用自己 WEB-INF/lib 里的版本，而 Servlet API、JDK 核心类这些「必须统一」的类则通过 packageTriggers 强制交给父加载器。

Java 17 版自己实现了一个精简的 WebappClassLoader 和 WebappLoader，接在前几章的迷你容器上，完整演示「隔离 + 子优先 + 自动重载」；另外用 Tomcat 11 部署同一个 myApp 做对照。

① WebappClassLoader：七步加载

static {
    registerAsParallelCapable();         // Java 7：按类名分别加锁，可以并行加载不同的类
}

record ResourceEntry(Class<?> loadedClass, Path source, long lastModified) { }

private final Map<String, ResourceEntry> resourceEntries = new ConcurrentHashMap<>();
private final Set<String> notFoundResources = ConcurrentHashMap.newKeySet();

@Override
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        ResourceEntry entry = resourceEntries.get(name);                         // ①
        if (entry != null) return entry.loadedClass();
        Class<?> clazz = findLoadedClass(name);                                  // ②
        if (clazz != null) return clazz;
        if (notFoundResources.contains(name)) throw new ClassNotFoundException(name);   // ③

        boolean delegateFirst = delegate || PACKAGE_TRIGGERS.stream().anyMatch(name::startsWith);
        if (delegateFirst) {                                                     // ④
            try { return getParent().loadClass(name); } catch (ClassNotFoundException ignored) { }
        }
        try {                                                                    // ⑤ 子优先
            clazz = findClass(name);
            resourceEntries.put(name, new ResourceEntry(clazz, sourceOf(name), lastModified(sourceOf(name))));
            return clazz;
        } catch (ClassNotFoundException ignored) { }
        if (!delegateFirst) {                                                    // ⑥
            try { return getParent().loadClass(name); } catch (ClassNotFoundException ignored) { }
        }
        notFoundResources.add(name);                                             // ⑦
        throw new ClassNotFoundException(name);
    }
}

public boolean modified() {
    for (ResourceEntry entry : resourceEntries.values()) {
        if (entry.source() != null && lastModified(entry.source()) != entry.lastModified()) {
            return true;
        }
    }
    return false;
}

其中 PACKAGE_TRIGGERS = List.of("java.", "javax.", "jakarta.", "org.xml.sax.", "org.w3c.dom.")。注意 Tomcat 10 起 Servlet API 在 jakarta 包里，所以触发列表里一定要有它。

② 用一个「过滤型」父加载器实现隔离

WebappClassLoader 的父加载器是 SharedClassLoader：它以 JDK 的平台类加载器为父，只额外放行 jakarta.*。于是 Web 应用能看到 JDK 和 Servlet API，却看不到容器自己的类：

public SharedClassLoader() {
    super("shared", ClassLoader.getPlatformClassLoader());   // Java 9 的平台类加载器
}

@Override
protected Class<?> findClass(String name) throws ClassNotFoundException {
    if (name.startsWith("jakarta.")) {
        return application.loadClass(name);                   // Servlet API 放行
    }
    throw new ClassNotFoundException(name);                   // 容器内部类：看不见
}

④ Context.reload()

public synchronized void reload() {
    System.out.println("===== 检测到类被修改，重新加载 Context =====");
    try {
        stop();        // Wrapper 调用 Servlet.destroy()，载入器关闭旧的类加载器
        start();       // 载入器创建新的类加载器，Servlet 在下次请求时用新类重新加载
    } catch (LifecycleException e) {
        e.printStackTrace();
    }
}
💡 同名的类，为什么能加载两次？

JVM 用「类名 + 加载它的类加载器」来唯一确定一个类。旧类加载器里的 HelloServlet 和新类加载器里的 HelloServlet 是两个不同的类。旧的类加载器、旧的类、旧的 Servlet 实例没有引用之后会一起被垃圾回收——前提是没有东西还引用着它们（比如 ThreadLocal、JDBC 驱动注册表），否则就会造成著名的「重载内存泄漏」。

⚠ 嵌入式 Tomcat 没有这层隔离

嵌入式运行时，Tomcat 自己和你的代码都在同一个 CLASSPATH 上，WebappClassLoader 的父加载器就是应用类加载器，所以 HelloServlet 在 Tomcat 11 版本里输出的是「能看到容器的内部类」。这也是 Spring Boot 这类「一个 JAR 一个应用」的部署方式不再强调类隔离的原因。

设计要点

这一章的代码里有几个可以带到别的项目里的设计决定。每条按「做法 → 取舍 → 替代方案 → 还能用在哪」来写；系统的讨论见设计篇。

1每个应用一个类加载器

每个 Context 有自己的 WebappClassLoader，只能看到自己的 WEB-INF/classes 和 lib。

取舍
同名类的不同版本可以共存，丢掉加载器就能卸载整个应用；代价是内存占用，以及类加载器泄漏（ThreadLocal、JDBC 驱动注册、静态缓存）。
替代方案
单一 classpath（简单，但无法隔离和热重载）；JPMS 模块层。
还能用在
IDE 插件、Jenkins 插件、规则引擎热加载：每个插件一个类加载器。
延伸：第 32 章 · 并发、隔离与演进
2有选择地打破双亲委派

先查 WEB-INF，再查父加载器；但 java.* 和 Servlet API 永远交给父加载器。

取舍
应用自带的库优先（避免和容器的库冲突），白名单保证核心类不能被应用替换。
替代方案
标准的父优先委派。
还能用在
插件系统里，「共享 API 父优先、插件实现子优先」几乎是标准答案。
延伸：第 32 章 · 并发、隔离与演进
3Loader 管策略，ClassLoader 管机制

WebappLoader 负责组装仓库、启动/停止、检测修改；WebappClassLoader 只负责查找和定义类。

取舍
两个类各自简单；ClassLoader 可以被替换而不影响重载策略。
还能用在
把「何时、如何配置」和「具体执行」拆开：调度器 vs 任务、连接池管理 vs 连接。
延伸：第 29 章 · 整体架构：分层与边界
4重载 = 整体替换

检测到修改后：停止 Context → 丢弃旧加载器 → 新建加载器 → 启动 Context。

取舍
不尝试在运行中修改已加载的类（JVM 也不允许），换来逻辑简单、状态干净；代价是重载期间请求要等待，Session 要序列化保存。
替代方案
JRebel 等字节码热替换（复杂）。
还能用在
不可变部署、蓝绿发布、配置热更新时「构建新对象再原子切换引用」。
延伸：第 32 章 · 并发、隔离与演进

小结

  • JVM 用双亲委派保证核心类不会被冒名顶替；Tomcat 为了隔离、缓存和重载，需要自己的类加载器。
  • Loader（WebappLoader）是 Web 应用载入器，内部持有类加载器（WebappClassLoader）；它负责发现修改，重载由 Context 执行。
  • WebappClassLoader 的仓库是 WEB-INF/classes 和 WEB-INF/lib；默认子优先，但 Servlet API 和 JDK 类必须交给父加载器。
  • 它缓存已加载的类和找不到的类名，并记录修改时间供 modified() 判断。
  • 重载 = 丢弃旧类加载器、创建新类加载器；同名类因为类加载器不同而成为不同的类。

动手练习

  1. 在 Java 17 版里把 delegate 设为 true，再在 webroot 外（应用类路径上）放一个同名的 HelloServlet，观察到底加载了哪一个。
  2. 用 java.nio.file.WatchService 改写 WebappLoader：不再定时轮询，而是在 WEB-INF/classes 有文件变化时立刻触发重载。想一想：一次 javac 会写多个文件，怎样避免连续触发多次重载？
  3. 给 HelloServlet 加一个 static ThreadLocal<byte[]>，在请求线程里放入 1MB 数据且不清除。反复重载十几次后用 jcmd <pid> GC.class_histogram 观察 HelloServlet 类的数量，理解「重载内存泄漏」。
