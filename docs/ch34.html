动手：插件化任务调度器

检验是否真正掌握了一种设计，最好的办法是把它用在一个完全不同的问题上。这一章做一个和 Web 毫无关系的小系统： 定时执行任务的调度器，任务类型由插件提供。它只有七百多行（含注释），却用上了设计篇的几乎每一条原则—— 组件树和生命周期、拦截器链、事件监听、SPI 与隔离的插件类加载器、配置驱动的装配、有界线程池、JMX、优雅停机。 读完后你可以把它当作模板，用在自己的项目里。

本章目标

  • 把一份需求翻译成 Tomcat 式的结构：哪些是组件、哪些是扩展点、哪些是装配
  • 读懂一个完整的小系统里各种设计决定是如何互相配合的
  • 验证重试、超时、不重叠、拒绝、优雅停机这些非功能行为
  • 按照练习清单把它扩展成一个真正可用的工具

需求

需求说明
按计划执行任务「每 N 秒一次」或「启动时一次」
任务类型可插拔内置几种；第三方把插件放进目录即可新增类型，插件之间、插件和宿主之间依赖隔离
配置驱动任务、参数、线程数、拦截器都写在配置文件里，改配置不改代码
可靠性失败重试（指数退避）；单次执行超时；同一个任务不重叠执行；线程池满了拒绝而不是无限排队
可观测每个任务的执行次数、失败次数、跳过次数、上次耗时可以通过 JMX 查看；支持暂停、恢复、手动触发
优雅停机Ctrl+C 或正常结束时，不再触发新任务，等待在途任务完成（有超时），停机过程中不再重试

明确不做的：cron 表达式、持久化、多实例下的分布式锁——它们是本章最后的练习。

① SPI：插件只需要实现两个方法

public interface TaskType {

    String name();

    Task create(Map<String, String> params);

    /** 后加的方法用 default 实现，老插件不用改（第 30 章标准 6） */
    default String description() {
        return name();
    }
}

@FunctionalInterface
public interface Task {
    void run(TaskContext ctx) throws Exception;
}

一个完整的插件（放进 plugins/ 目录，配上 META-INF/services/modern.scheduler.spi.TaskType）：

public class DiskReportTaskType implements TaskType {
    @Override public String name() { return "disk-report"; }

    @Override
    public Task create(Map<String, String> params) {
        var path = new File(params.getOrDefault("path", "."));
        return ctx -> {
            long percent = path.getUsableSpace() * 100 / path.getTotalSpace();
            ctx.log("可用 " + percent + "%，由 " + getClass().getClassLoader() + " 加载");
        };
    }
}

② trigger：只判断、只投递

/** ticker 线程上调用：只做判断和投递，几微秒就返回 */
void trigger(Job job) {
    if (!job.getState().isAvailable() || job.isPaused()) return;
    if (!job.running.compareAndSet(false, true)) {         // 上一次还没跑完：跳过，而不是排队
        job.skipped.incrementAndGet();
        fire(new JobEvent(JobEvent.Type.SKIPPED_OVERLAP, job.getName(), 0, 0, null));
        return;
    }
    try {
        workers.execute(() -> execute(job));
    } catch (RejectedExecutionException e) {               // 线程池和队列都满了
        job.running.set(false);
        fire(new JobEvent(JobEvent.Type.REJECTED, job.getName(), 0, 0, e));
    }
}

③ 拦截器：重试和超时

public static Pipeline.Valve<Execution> retry(int maxAttempts, Duration firstBackoff, Scheduler scheduler) {
    return (ex, next) -> {
        long backoff = firstBackoff.toMillis();
        while (true) {
            try {
                next.invoke(ex);
                return;
            } catch (Exception e) {
                // 次数用完、被中断、或者调度器正在停机：不再重试——停机时要尽快收尾
                if (ex.attempt() >= maxAttempts || e instanceof InterruptedException
                        || !ex.job().getState().isAvailable()) throw e;
                scheduler.fire(new JobEvent(JobEvent.Type.RETRYING, …));
                Thread.sleep(backoff);
                backoff *= 2;
                ex.nextAttempt();
            }
        }
    };
}

/** 超时：共享的看门狗到点中断工作线程；加锁保证任务结束后绝不会误中断这个（要还给线程池的）线程 */
public static Pipeline.Valve<Execution> timeout(Duration limit, ScheduledExecutorService watchdog) {
    return (ex, next) -> {
        Thread worker = Thread.currentThread();
        Object lock = new Object();
        boolean[] done = {false};
        var alarm = watchdog.schedule(() -> {
            synchronized (lock) { if (!done[0]) worker.interrupt(); }
        }, limit.toMillis(), TimeUnit.MILLISECONDS);
        try {
            next.invoke(ex);
        } catch (InterruptedException e) {
            throw new TimeoutException("超过 " + limit.toMillis() + " ms 被中断");
        } finally {
            synchronized (lock) { done[0] = true; }
            alarm.cancel(false);
            Thread.interrupted();                         // 清掉可能残留的中断标志
        }
    };
}
🔑 拦截器的顺序就是语义

配置里写的是 logging, retry, timeout：timeout 在 retry 里面，所以每次尝试各有 800 ms； 如果写成 logging, timeout, retry，就变成「所有重试加起来」只有 800 ms。logging 在最外层，所以它只记录最终结果， 重试过程由 RETRYING 事件交给监听器报告。这正是第 31 章「责任链：顺序就是语义」的例子。

④ 停机：先停组件，再停线程

@Override
protected void startSelf() {          // 先准备好线程，子组件（Job）启动时才能登记调度
    ticker = Executors.newSingleThreadScheduledExecutor(named("scheduler-ticker"));
    workers = new ThreadPoolExecutor(workerThreads, workerThreads, 0, TimeUnit.MILLISECONDS,
            new ArrayBlockingQueue<>(queueCapacity), named("job-worker"), new ThreadPoolExecutor.AbortPolicy());
}

@Override
protected void stopSelf() {           // 子组件都停了之后（不再触发）：先停止投递，再等在途任务
    ticker.shutdownNow();
    workers.shutdown();
    if (!workers.awaitTermination(shutdownGrace.toMillis(), TimeUnit.MILLISECONDS)) {
        workers.shutdownNow();        // 宽限期过了：中断剩余任务
    }
    watchdog.shutdownNow();
}

CompositeComponent 保证了顺序：先倒序停止所有 Job（它们变成不可用，trigger 和重试都会看到），然后才调用 stopSelf 收拾线程池。 这和第 29 章「先关大门，再停核心」、第 11 章「卸载前等待在途请求」是同一件事。

对照需求逐条检查：

  • 插件：disk-report 来自插件目录，由 PluginClassLoader(disk-report) 加载。
  • 重试：flaky 前两次失败、第三次成功，统计里 failures=0——重试成功不算失败。
  • 超时：stuck 三次尝试各被中断，总耗时 2709 ms ≈ 3 × 800 + 100 + 200 的退避。
  • 不重叠：slow 每 300 ms 触发一次但每次要 700 ms，4 秒里执行 4 次、跳过 8 次。
  • 可观测：统计是通过平台 MBeanServer 读出来的，JConsole 里同样能看到并调用 pause、runNow。
  • 优雅停机：正在重试的 flaky 放弃了后续重试，正在执行的 slow 跑完后才进入 STOPPED。

扩展练习

下面的练习按难度排列。每一个都能在不修改已有类（或只改装配器）的前提下完成——这本身就是对设计的检验。

  1. 新任务类型：写一个 http-check 插件，用 HttpClient 请求一个 URL，状态码不是 2xx 就抛异常。打成 jar 放进插件目录。
  2. 新拦截器：metrics 拦截器把每次执行的耗时记到直方图里，并像第 28 章那样以 Prometheus 格式输出。
  3. 新调度规则：支持 cron 0 */5 * * * *。只需要扩展 Schedule 和 scheduleJob——想想怎样把「下一次执行时间」的计算做成策略。
  4. 舱壁：允许 job.x.pool = slow-pool，让慢任务使用单独的线程池（第 32 章实验 ③）。
  5. 配置热更新：监视配置文件，变化时构建新的 Job 集合，对比后增删 Job（addChild 会立即启动，removeChild 会停止）。哪些修改可以不重启就生效？
  6. 管理控制台：用嵌入式 Tomcat 加一个 HTTP 管理页面：列出任务、显示统计、一键暂停和触发。参考第 19、20 章，管理入口记得用 RemoteAddrValve 保护（第 28 章）。
  7. 执行历史：加一个监听器，把每次执行结果写进 SQLite 或文件；思考它应该同步还是异步写，写失败了要不要影响任务。
  8. 多实例：部署两份调度器时，同一个任务只能有一个实例执行。用数据库行锁或 Redis 实现一个「分布式不重叠」拦截器。

小结

  • 同一个骨架（组件树 + 生命周期 + 管道 + 装配）既能撑起 Tomcat，也能撑起一个调度器或订单服务。
  • 扩展点按形态选择：任务类型是策略 + 发现机制，重试和超时是拦截链，告警是监听器。
  • 非功能行为都要「事先想好满了怎么办」：不重叠是丢弃，线程池满是拒绝，超时是中断，停机时放弃重试。
  • 线程分工沿用 Poller/Worker：调度线程只投递，执行线程做慢事，看门狗统一处理超时。
  • 扩展练习都不需要修改已有的核心类——这是检验一个设计好坏最直接的方法。
