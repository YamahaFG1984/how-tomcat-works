并发、隔离与演进

前三章讲的是「功能怎么组织」。一个服务器能不能用上二十年，更多取决于另一类问题：成百上千个线程同时跑时会不会出错， 一个应用崩了会不会拖垮别的应用，出了问题能不能看清楚，以及当初的设计被证明是错的时候，能不能改掉而不伤害用户。 这一章把 Tomcat 在这几方面的做法整理成规则，用四个小实验验证它们，最后给出整个设计篇的评审清单。

本章目标

  • 能画出 Tomcat 的「线程归属图」，说出哪些对象被哪些线程访问、靠什么保证安全
  • 掌握六条并发规则：线程封闭、启动后不变、并发容器、写时复制、单线程拥有者、显式状态机
  • 理解从请求、应用、资源到进程的几层隔离，以及舱壁模式
  • 从 Tomcat 被推翻的设计中总结演进的方法
  • 拿到一份可以直接用于设计评审的清单

并发：谁的线程碰谁的对象

Tomcat 的并发设计并不依赖到处加锁，而是先回答一个问题：每个对象会被哪些线程访问？答案决定了用什么手段保护它。

由此得到六条规则，每条在 Tomcat 里都有对应的实现：

② 启动后不变Context 配置完成后才标记为可用；运行时只读12配置对象用 record，启动时构建，之后只读

实验：线程封闭与写时复制

第一个实验模拟第 11 章的经典错误：在 Servlet 的实例字段里计数。16 个线程各处理 5 万个请求：

static final class CounterServlet {
    int hits;                                     // 共享的实例字段：所有请求线程都在改它

    void service(int[] perRequest) {
        hits++;                                   // 读-改-写，不是原子的
        perRequest[0]++;                          // 请求自己的对象：只有当前线程能看到
    }
}

① 线程封闭：16 个线程 × 每个 50000 次请求
  请求对象里的计数合计 800000（正确），共享字段 hits = 700000（丢了 100000 次更新）

丢失的数量每次运行都不一样，在某些机器上甚至可能碰巧是 0——这正是并发 bug 难以复现的原因。第二个实验：通知过程中一个「一次性」监听器把自己移除，这在第 6 章的场景里很常见： 

② 通知过程中，有一个监听器把自己移除（一次性监听器很常见）
  ArrayList            ConcurrentModificationException（只通知到 1 个）
  CopyOnWriteArrayList 通知了 3 个监听器，剩余 2 个

这甚至不需要多线程：同一个线程在遍历时修改了列表。写时复制让遍历基于一个不可变的快照，修改只影响下一次遍历——这就是 Tomcat 4 的 LifecycleSupport 每次增删监听器都复制数组的原因。

隔离：失败的影响范围

隔离设计回答的问题是：某个东西坏了，会连累多少其他东西？ Tomcat 从小到大有好几层隔离：

其中最容易被忽视的是资源隔离。所有工作共用一个线程池时，一类慢请求就能把池占满，让本来很快的请求也排起长队。 解决办法叫「舱壁」（bulkhead，船舱的隔板）：给不同类别的工作各自的线程池。Tomcat 里可以用多个 Service 或多个 Connector 实现， 业务代码里就是给慢接口、第三方调用单独的执行器。 

③ 舱壁：20 个慢报表（各 300ms）先提交，随后 5 个快查询（各 5ms）
  共用一个 4 线程池：快查询平均等待 1502 ms
  报表 2 线程 + 查询 2 线程：快查询平均等待 4 ms

总线程数一样（都是 4 个），只是分了一下组，快查询的等待时间从 1.5 秒降到 4 毫秒。代价是资源可能闲置：报表很少时，那 2 个报表线程就空着。

后台工作：一个线程驱动整棵树

会话过期检查、类文件修改检测、自动部署扫描——这些周期性工作在 Tomcat 4 里由各个组件自己开线程完成（第 8 章的 WebappLoader、第 9 章的 StandardManager 都实现了 Runnable）。 一个 Host 部署 50 个应用，就多出上百个后台线程。Tomcat 5 起改成 Engine 上的一个线程定期调用 backgroundProcess()，沿着组件树递归（第 12 章）： 

④ 50 个组件的周期性任务，运行 1 秒
  每个组件一个线程：后台线程 50 个
  一个后台线程递归驱动：后台线程 1 个，每个组件被处理了约 20 次

这是规则 ⑤「单线程拥有者」的一个应用。代价是一个组件的后台任务卡住，会拖延其他组件；所以每个 backgroundProcess() 都必须短小、不能阻塞。

可观测性是设计出来的

第 20、28 章讲了怎么用 JMX 和指标。这里只强调它们背后的设计决定，这些决定都要在写第一行代码时就做：

  • 给线程起名字。http-nio-8080-exec-3、http-nio-8080-Poller、Catalina-utility-1（Tomcat 9 起执行后台任务的线程）：线程转储里一眼就知道谁是谁。本章实验 ④ 也是靠线程名统计的。
  • 状态变化发事件。生命周期事件既是扩展点，也是诊断入口：「这个 Context 卡在 STARTING」本身就是有用的信息。
  • 每个组件维护自己的计数器。请求数、错误数、处理时间在 RequestInfo 里随手累加，成本极低，用的时候直接读。
  • 错误信息带上下文。Tomcat 的错误日志会写出应用名、线程名、类名（第 28 章的泄漏日志就是例子），而不只是一个异常栈。

演进：Tomcat 推翻过的设计

原书写的是 Tomcat 4/5。对照今天的 Tomcat 11，很多设计被改掉了。改掉不丢人，丢人的是改不掉。下面这条时间线标出了主要的变化：

被推翻的设计原书章节换成了什么为什么
每连接一线程的 BIO 连接器3、4Coyote + NIO（第 23 章）线程不够用，慢客户端能拖垮服务器
ValveContext 外部迭代器5阀持有 next 引用每个请求一个有状态对象，没有必要
容器各自的 Mapper5、12、13连接器里一次查完的全局 Mapper逐层映射慢，且没人需要替换它
started 布尔值6LifecycleState 枚举 + LifecycleBase布尔值表达不了「启动中」「失败」等阶段
自定义 Logger 接口7commons-logging，再到 JULI日志是通用设施，不该自己定义
每个组件一个后台线程8、9backgroundProcess()线程数随应用数线性增长
SingleThreadModel11无（要求 Servlet 无状态）给了虚假的线程安全保证
javax.servlet 包名全书jakarta.servletJava EE 移交 Eclipse 基金会后的商标限制

Tomcat 是怎么「改掉」的

  1. 先废弃，再删除。在一个大版本里标记 @Deprecated 并在日志里警告，下一个大版本才删除。用户至少有一个版本周期来迁移。
  2. 大的破坏性变更集中在大版本。javax → jakarta 这种影响所有用户的变更单独占一个大版本（Tomcat 10），并且旧版本（9.0）继续维护多年。
  3. 提供迁移工具。Tomcat 提供了 jakartaee-migration 工具，能把 javax 版本的 WAR 自动转换；把它的 jar 放进 Tomcat 10+ 的 lib 后，放进 webapps-javaee 目录的旧应用会在部署时自动转换。
  4. 新接口带默认实现。Servlet API 往接口加方法时提供 default 实现，老的实现类不用改。
  5. 窄接口让替换成为可能。连接器从 BIO 换成 NIO、再加上虚拟线程，应用代码一行没变——这是第 29 章原则二的回报。
🔑 演进的前提是知道谁在用

能安全地删掉一个东西，前提是知道谁依赖它。公开的扩展点越多，这个问题越难回答（第 30 章）。 所以「少暴露」本身就是为演进做准备：内部的东西随便改，公开的东西要走废弃流程。在 Java 里，可以用模块系统（module-info.java 只 exports API 包）把这条线画得更清楚。

舱壁实验的核心只是两种提交方式的对比：

ExecutorService shared = Executors.newFixedThreadPool(4);
runMix(shared, shared);                                   // 报表和查询共用

ExecutorService reports = Executors.newFixedThreadPool(2);
ExecutorService queries = Executors.newFixedThreadPool(2);
runMix(reports, queries);                                 // 各用各的

private static long runMix(ExecutorService reportPool, ExecutorService queryPool) throws Exception {
    for (int i = 0; i < 20; i++) reportPool.submit(() -> sleep(300));
    List<Future<Long>> fast = new ArrayList<>();
    for (int i = 0; i < 5; i++) {
        long submitted = System.nanoTime();
        fast.add(queryPool.submit(() -> {
            long waited = (System.nanoTime() - submitted) / 1_000_000;   // 排队等了多久
            sleep(5);
            return waited;
        }));

小结

  • 并发设计从「谁碰谁」开始：线程封闭、启动后不变、并发容器、写时复制、单线程拥有者、显式状态机，各管一类情况。
  • 隔离分请求、权限、应用、资源、进程几层；舱壁模式用分开的线程池保护快请求。
  • 周期性工作交给一个后台线程沿组件树驱动，每个任务必须短小。
  • 可观测性靠设计：线程命名、生命周期事件、组件内计数器、带上下文的错误信息。
  • Tomcat 推翻过很多设计；先废弃后删除、破坏性变更集中在大版本、提供迁移工具、窄接口，让它改得动。

动手练习

  1. 用三种方法修复实验 ① 的丢失更新：synchronized、AtomicInteger、LongAdder，比较 16 线程下的耗时。
