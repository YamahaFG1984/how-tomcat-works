第 18 章

部署器

到上一章为止，每个 Context 都是在代码里或 server.xml 里写死的。可我们用 Tomcat 时， 只要把一个目录或者 WAR 包丢进 webapps，它就自动跑起来了——甚至不用重启。 这一章揭开这个「自动部署」的机制：Host 的监听器 HostConfig 负责发现应用， Deployer（StandardHostDeployer）负责把它们装进 Host。

本章目标

  • 理解 HostConfig 如何在 Host 启动时扫描 appBase 并部署应用
  • 区分三种部署形式：描述符、WAR、目录，并理解它们的处理顺序
  • 理解「热部署」（live deploy）在 Tomcat 4 和 Tomcat 5 中的不同实现
  • 理解 Deployer 接口：install / remove / start / stop

谁把 Context 加进了 Host？

第 15 章的代码是这样「部署」应用的：new StandardContext()、setPath、setDocBase、host.addChild(context)。真实的 Tomcat 里没有这样的代码。答案在 Catalina 的 Digester 规则里——HostRuleSet 在创建 Host 的同时，给它加了一个生命周期监听器：

digester.addObjectCreate(prefix + "Host", "org.apache.catalina.core.StandardHost", "className");
digester.addSetProperties(prefix + "Host");
digester.addRule(prefix + "Host", new CopyParentClassLoaderRule(digester));
digester.addRule(prefix + "Host",
    new LifecycleListenerRule(digester, "org.apache.catalina.startup.HostConfig", "hostConfigClass"));

public void lifecycleEvent(LifecycleEvent event) {
    host = (Host) event.getLifecycle();
    if (host instanceof StandardHost) {
        setDeployXML(((StandardHost) host).isDeployXML());     // 是否部署描述符（默认 true）
        setLiveDeploy(((StandardHost) host).getLiveDeploy());  // 是否定期检查新应用（默认 true）
        setUnpackWARs(((StandardHost) host).isUnpackWARs());   // WAR 是否解压
    }
    if (event.getType().equals(Lifecycle.START_EVENT))
        start();
    else if (event.getType().equals(Lifecycle.STOP_EVENT))
        stop();
}

protected void start() {
    if (host.getAutoDeploy()) {
        deployApps();
    }
    if (isLiveDeploy()) {
        threadStart();          // Tomcat 4：每 checkInterval（15）秒再扫描一次
    }
}

三种部署形式

protected void deployApps() {
    if (!(host instanceof Deployer))
        return;
    File appBase = appBase();
    if (!appBase.exists() || !appBase.isDirectory())
        return;
    String files[] = appBase.list();
    deployDescriptors(appBase, files);   // ① *.xml
    deployWARs(appBase, files);          // ② *.war
    deployDirectories(appBase, files);   // ③ 子目录
}

每个已处理的条目都记在 deployed 列表里，三个方法都会跳过 META-INF、WEB-INF、已部署过的条目，以及上下文路径已被占用的应用。上下文路径由文件名推出：

形式文件上下文路径说明
① 描述符manager.xml/manager文件里是一个 <Context docBase="..."/> 元素，应用可以放在 appBase 之外；ROOT.xml → ""
② WARshop.war/shopunpackWARs 为 true 时先解压成 shop/ 目录再部署，否则直接以 jar:file:…!/ 部署
③ 目录app1//app1必须包含可读的 WEB-INF 目录，否则视为普通目录跳过；ROOT/ → ""
🔑 为什么顺序很重要？

原书留了一个问题：三个方法的调用顺序重要吗？答案是重要。描述符优先，可以覆盖同名的 WAR 或目录（例如给它加 privileged="true" 或换 docBase）；WAR 先于目录处理，并把解压出的目录记为已部署，否则 shop.war 解压出的 shop/ 会被当作另一个应用再部署一次。

<Context path="/manager" docBase="../server/webapps/manager" debug="0" privileged="true">
  <!-- Link to the user database we will get roles from -->
  <ResourceLink name="users" global="UserDatabase" type="org.apache.catalina.UserDatabase"/>
</Context>

Manager 和 Admin 应用的文件不在 webapps 下（Tomcat 4 中位于 server/webapps），而是通过描述符的 docBase 指过去，并标记为 privileged（第 19 章会用到这个属性）。

for (int i = 0; i < files.length; i++) {
    if (files[i].equalsIgnoreCase("META-INF") || files[i].equalsIgnoreCase("WEB-INF")) continue;
    if (deployed.contains(files[i])) continue;
    File dir = new File(appBase, files[i]);
    if (dir.isDirectory()) {
        deployed.add(files[i]);
        File webInf = new File(dir, "/WEB-INF");
        if (!webInf.exists() || !webInf.isDirectory() || !webInf.canRead())
            continue;                                 // 不是 Web 应用
        String contextPath = "/" + files[i];
        if (files[i].equals("ROOT"))
            contextPath = "";
        if (host.findChild(contextPath) != null)
            continue;
        URL url = new URL("file", null, dir.getCanonicalPath());
        ((Deployer) host).install(contextPath, url);
    }
}

热部署

Tomcat 5 的 checkContextLastModified() 检查每个已部署应用的 web.xml、WEB-INF 内容以及 WAR 文件的时间戳，有变化就重启或重新部署该应用。

Deployer 接口

public interface Deployer {
    public static final String PRE_INSTALL_EVENT = "pre-install";
    public static final String INSTALL_EVENT = "install";
    public static final String REMOVE_EVENT = "remove";

    public void install(String contextPath, URL war) throws IOException;   // 目录或 WAR
    public void install(URL config, URL war) throws IOException;           // 描述符
    public Context findDeployedApp(String contextPath);
    public String[] findDeployedApps();
    public void remove(String contextPath) throws IOException;
    public void start(String contextPath) throws IOException;
    public void stop(String contextPath) throws IOException;
}

StandardHost 实现了 Deployer，但它把所有工作委托给一个辅助对象：private Deployer deployer = new StandardHostDeployer(this);

if (!contextPath.equals("") && !contextPath.startsWith("/"))
    throw new IllegalArgumentException(sm.getString("standardHost.pathFormat", contextPath));
if (findDeployedApp(contextPath) != null)
    throw new IllegalStateException(sm.getString("standardHost.pathUsed", contextPath));
...
Class clazz = Class.forName(host.getContextClass());          // 默认 StandardContext
Context context = (Context) clazz.newInstance();
context.setPath(contextPath);
context.setDocBase(docBase);
if (context instanceof Lifecycle) {
    clazz = Class.forName(host.getConfigClass());             // 默认 ContextConfig
    LifecycleListener listener = (LifecycleListener) clazz.newInstance();
    ((Lifecycle) context).addLifecycleListener(listener);
}
host.fireContainerEvent(PRE_INSTALL_EVENT, context);
host.addChild(context);                                       // Host 已启动时，addChild 会启动 Context
host.fireContainerEvent(INSTALL_EVENT, context);

安装描述符的 install(URL config, URL war) 则用一个 Digester 解析描述符里的 <Context> 元素（Deployer 自己压在栈底）；start / stop 找到 Context 后调用它的生命周期方法，可以单独启停某一个应用而不影响其他应用。

② 解压 WAR 时防止 zip slip

WAR 就是 ZIP。恶意构造的 WAR 可以包含名为 ../../etc/cron.d/evil 的条目，天真的解压代码会把文件写到目标目录之外——这就是著名的「zip slip」漏洞。和第 1 章防路径穿越的套路一样：先规范化，再检查是否仍在目标目录里。

③ StandardHostDeployer

public synchronized StandardContext install(String contextPath, Path docBase) throws LifecycleException {
    if (!contextPath.isEmpty() && !contextPath.startsWith("/"))
        throw new IllegalArgumentException("上下文路径必须是 \"\" 或以 / 开头: " + contextPath);
    if (findDeployedApp(contextPath) != null)
        throw new IllegalStateException("上下文路径已被占用: " + contextPath);
    var context = new StandardContext();
    context.setPath(contextPath);
    context.setDocBase(docBase.toString());
    context.addLifecycleListener(new ContextConfig());                          // 第 15 章
    context.setLoader(new WebappLoader(context.getDocBase(), context::reload));  // 第 8 章
    host.addChild(context);
    if (host.isStarted()) {
        context.start();                                  // Host 已经在运行：立即启动
    }
    return context;
}

④ Tomcat 11 的 HostConfig

tomcat.getEngine().setBackgroundProcessorDelay(1);   // 每秒一次 periodic 事件 → HostConfig.check()
Host host = tomcat.getHost();
host.setAppBase(appBase.toString());
host.setAutoDeploy(true);

// 描述符放在 $CATALINA_BASE/conf/<Engine 名>/<Host 名>/，不在 appBase 里
Path xmlBase = base.resolve("conf").resolve(tomcat.getEngine().getName()).resolve(host.getName());
Files.writeString(xmlBase.resolve("hello.xml"), "<Context docBase=\"" + myApp + "\"/>\n");
💡 一个实际踩到的坑

第一次运行时 hello.xml 没有被部署。原因：描述符目录是 conf/<Engine 名>/<Host 名>，独立部署的 Tomcat 中 Engine 叫 Catalina，而嵌入式 Tomcat 类创建的 Engine 叫 Tomcat。把路径改成用 tomcat.getEngine().getName() 计算后就好了。

ⓘ 原书之后的变化
  • Tomcat 5 起，描述符从 appBase 移到了 conf/Catalina/localhost/（xmlBase）；应用内也可以放 META-INF/context.xml。
  • Deployer 接口和 StandardHostDeployer 后来被移除（Tomcat 6 中已不存在），部署逻辑全部收进 HostConfig；Manager 应用通过 HostConfig 的 JMX 操作来部署/卸载（第 19、20 章）。
  • Tomcat 7 增加了「并行部署」：shop##002.war 与 shop##001.war 共享 /shop，新会话进入新版本，老会话继续留在旧版本直到结束。
  • Host 的 deployOnStartup、autoDeploy、unpackWARs 仍是 server.xml 里最常配置的属性；生产环境通常关闭 autoDeploy。

小结

  • HostRuleSet 给每个 Host 加上 HostConfig 监听器；Host 启动时 HostConfig 扫描 appBase 部署应用。
  • 部署顺序：描述符 → WAR → 目录；上下文路径由文件名决定，ROOT 对应 ""。
  • 热部署：Tomcat 4 用 HostConfig 自己的线程，Tomcat 5 用 Host 的 backgroundProcess() 发出 check 事件。
  • Deployer 的 install 创建 StandardContext、挂上 ContextConfig、加入 Host；start / stop / remove 可以单独管理某个应用。
  • 解压 WAR 时要防范 zip slip。
