第 3 章

连接器

Catalina 由两大模块组成：连接器（connector）和容器（container）。 连接器负责把一条 HTTP 请求变成一个功能完整的 HttpServletRequest 对象——请求头、Cookie、参数都要能取到。 这一章我们写一个简化版的 Tomcat 4 默认连接器，让第 2 章跑不起来的 ModernServlet 也能正常工作。

本章目标

  • 理解连接器和容器的分工，以及 HttpConnector / HttpProcessor 的拆分
  • 学会解析请求行：查询串、绝对 URI、URL 中的 jsessionid、URI 规范化
  • 学会解析请求头和 Cookie，理解参数为什么要「懒解析」
  • 理解 StringManager 如何按包管理多语言错误消息

连接器要做什么

Servlet 2.3/2.4 规范要求连接器必须创建 HttpServletRequest 和 HttpServletResponse。连接器并不知道被调用的 Servlet 是直接实现了 Servlet、继承了 GenericServlet 还是继承了 HttpServlet，所以它总是提供 HTTP 版本的请求和响应对象。

从本章开始，示例程序被分成三个模块：

📡

HttpConnector

只负责「等」：创建 ServerSocket，accept 到 socket 就交出去。

⚙

HttpProcessor

只负责「拆」：读请求行和请求头，填充 HttpRequest，再分派给处理器。

📦

HttpRequest

实现 HttpServletRequest，保存请求头、Cookie、参数。

✉

HttpResponse

实现 HttpServletResponse，可以设置响应头，getWriter 不再丢数据。

StringManager：按包管理错误消息

Tomcat 有几百个类，错误消息既要给管理员看（写日志），又要给 Servlet 程序员看（放进 ServletException）。如果全塞进一个大 properties 文件，维护起来是噩梦。Tomcat 的做法是：每个包一个 properties 文件，由一个 StringManager 实例负责读取。

private static Hashtable managers = new Hashtable();

public synchronized static StringManager getManager(String packageName) {
    StringManager mgr = (StringManager) managers.get(packageName);
    if (mgr == null) {
        mgr = new StringManager(packageName);    // 构造器是 private 的
        managers.put(packageName, mgr);
    }
    return mgr;
}

// 用法

sm.getString("httpConnector.alreadyInitialized");
// → "HTTP connector has already been initialized"

HttpConnector：在自己的线程里等待

public class HttpConnector implements Runnable {
    boolean stopped;
    private String scheme = "http";

    public void run() {
        ServerSocket serverSocket = null;
        int port = 8080;
        try {
            serverSocket = new ServerSocket(port, 1, InetAddress.getByName("127.0.0.1"));
        } catch (IOException e) {
            e.printStackTrace();
            System.exit(1);
        }
        while (!stopped) {
            Socket socket = null;
            try {
                socket = serverSocket.accept();
            } catch (Exception e) {
                continue;
            }
            HttpProcessor processor = new HttpProcessor(this);   // 每个请求一个处理器
            processor.process(socket);
        }
    }

    public void start() {
        Thread thread = new Thread(this);
        thread.start();
    }
}

启动类 Bootstrap 只有两行：new HttpConnector()，然后 start()。注意本章还没有关闭机制，只能直接关掉控制台或者 kill 进程（第 14 章才会有优雅的关闭）。

HttpProcessor：一次请求的完整流程

public void process(Socket socket) {
    SocketInputStream input = null;
    OutputStream output = null;
    try {
        input = new SocketInputStream(socket.getInputStream(), 2048);
        output = socket.getOutputStream();
        request = new HttpRequest(input);
        response = new HttpResponse(output);
        response.setRequest(request);
        response.setHeader("Server", "Pyrmont Servlet Container");
        parseRequest(input, output);
        parseHeaders(input);
        if (request.getRequestURI().startsWith("/servlet/")) {
            ServletProcessor processor = new ServletProcessor();
            processor.process(request, response);
        } else {
            StaticResourceProcessor processor = new StaticResourceProcessor();
            processor.process(request, response);
        }
        socket.close();
    } catch (Exception e) {
        e.printStackTrace();
    }
}

SocketInputStream：只能往前读

前两章只是 input.read(buffer) 读一次。本章的 SocketInputStream（直接复制自 Tomcat 4 的同名类）包装了 socket 的输入流，提供两个关键方法：

  • readRequestLine(HttpRequestLine)：读出第一行，填充方法、URI、协议。
  • readHeader(HttpHeader)：每调用一次读出一个请求头；读到空行时返回的 HttpHeader 的 nameEnd 和 valueEnd 都是 0。
🔎 为什么用 char[] 而不是 String？

原书的 HttpRequestLine 和 HttpHeader 内部都是 char[] 加一个 xxxEnd 下标，处理完调用 recycle() 复用。2004 年的 JVM 垃圾回收很慢，Tomcat 想尽量少创建对象。今天的分代/区域化 GC 回收短命小对象几乎没有成本，Java 17 版直接用 record HttpRequestLine(String method, String uri, String protocol)，代码简单得多。

解析请求行

请求行的第二部分不只是路径，还可能夹带查询串、会话 ID，甚至是一个绝对 URL。parseRequest 要把它们一一拆开：

  1. 拆查询串：找第一个 ?，后面的部分调用 request.setQueryString()。
  2. 处理绝对 URI：不以 / 开头就找 ://，截掉协议和主机名。
  3. 取 URL 里的会话 ID：会话 ID 通常放在 Cookie 里，但浏览器禁用 Cookie 时会被改写进 URL（;jsessionid=…）。找到就记下来并从 URI 中删掉。
  4. 规范化：normalize() 把 \ 换成 /，合并 //，处理 /./ 和 /../。如果想用 /../ 跳出根目录，或者包含 %2e、%2f、%5c、%25 这类编码过的特殊字符，就返回 null，请求被判为非法。
input.readRequestLine(requestLine);
String method = new String(requestLine.method, 0, requestLine.methodEnd);
String protocol = new String(requestLine.protocol, 0, requestLine.protocolEnd);

int question = requestLine.indexOf("?");
if (question >= 0) {
    request.setQueryString(new String(requestLine.uri, question + 1,
        requestLine.uriEnd - question - 1));
    uri = new String(requestLine.uri, 0, question);
} else {
    request.setQueryString(null);
    uri = new String(requestLine.uri, 0, requestLine.uriEnd);
}

String match = ";jsessionid=";

        rest = rest.substring(semicolon2);
    } else {
        request.setRequestedSessionId(rest);
        rest = "";
    }
    request.setRequestedSessionURL(true);

}

⚠ 规范化是安全问题，不是格式问题

Web 服务器历史上最常见的漏洞之一就是路径穿越。攻击者会想尽办法绕过检查：/..\..\、/%2e%2e/、/%252e%252e/（双重编码）……这也是为什么 normalize 会拒绝所有编码过的 . / \ %。

解析请求头和 Cookie

parseHeaders 循环调用 readHeader，把每个头加进 HttpRequest 的 headers 表。有三个头需要特别处理：

请求头处理对应的 Servlet API
cookie用 RequestUtil.parseCookieHeader 拆成多个 Cookie；名为 jsessionid 的 Cookie 会覆盖 URL 里的会话 IDgetCookies()、getRequestedSessionId()
content-length转成整数，非法就抛 ServletExceptiongetContentLength()
content-type原样保存getContentType()
// 输入："userName=budi; password=pwd;"
public static Cookie[] parseCookieHeader(String header) {
    if ((header == null) || (header.length() < 1))
        return (new Cookie[0]);
    ArrayList cookies = new ArrayList();
    while (header.length() > 0) {
        int semicolon = header.indexOf(';');
        if (semicolon < 0) semicolon = header.length();
        if (semicolon == 0) break;
        String token = header.substring(0, semicolon);
        header = semicolon < header.length() ? header.substring(semicolon + 1) : "";
        int equals = token.indexOf('=');
        if (equals > 0) {
            String name = token.substring(0, equals).trim();
            String value = token.substring(equals + 1).trim();
            cookies.add(new Cookie(name, value));
        }
    }
    return ((Cookie[]) cookies.toArray(new Cookie[cookies.size()]));
}

参数的懒解析

解析参数要做大量字符串操作和 URL 解码，很费 CPU。如果 Servlet 根本不调用 getParameter，这些工作就白做了。所以 HttpProcessor 不解析参数，而是交给 HttpRequest 在第一次被问到时再解析：

Servlet 规范规定参数是只读的，所以 Tomcat 用了一个特殊的 HashMap 子类 ParameterMap：它有一个 locked 标志，上锁之后调用 put、putAll、remove、clear 都会抛 IllegalStateException。

原书：可上锁的 ParameterMap
public final class ParameterMap extends HashMap {
    private boolean locked = false;
    public void setLocked(boolean locked) { ... }

    public Object put(Object key, Object value) {
        if (locked)
            throw new IllegalStateException(
                sm.getString("parameterMap.locked"));
        return super.put(key, value);
    }
    // putAll、remove、clear 同理
}
Java 17：不可变视图
Map<String, String[]> results = new LinkedHashMap<>();
RequestUtil.parseParameters(results, queryString, charset);
if (isPostForm) {
    byte[] body = getInputStream()
        .readNBytes((int) contentLength);   // Java 11
    RequestUtil.parseParameters(results, ..., charset);
}
// 任何修改都抛 UnsupportedOperationException
parameters = Collections.unmodifiableMap(results);

HttpResponse 与「不丢最后一行」

第 2 章 getWriter() 返回的 PrintWriter 只在 println 时刷新。本章用一条输出链解决它：

public PrintWriter getWriter() throws IOException {
    ResponseStream newStream = new ResponseStream(this);
    newStream.setCommit(false);
    OutputStreamWriter osr = new OutputStreamWriter(newStream, getCharacterEncoding());
    writer = new ResponseWriter(osr);
    return writer;
}

public void finishResponse() {
    // sendHeaders();          ← 注意：这一行在原书源码里是被注释掉的
    if (writer != null) {
        writer.flush();
        writer.close();
    }
}
🔑 读源码时发现的小秘密

HttpResponse 里明明写好了 sendHeaders()（输出状态行、Content-Type、Content-Length 和自定义头），但 finishResponse() 里调用它的那一行被注释掉了。所以本章 Servlet 的输出依然没有状态行，setHeader("Server", ...) 也没有真正发出去。第 4 章的 Tomcat 默认连接器才把这件事做完整。Java 17 版在本章就补上了。

请求头的分派

private void parseHeaders(SocketInputStream input) throws IOException, ServletException {
    for (HttpHeader header; (header = input.readHeader()) != null; ) {
        String name = header.name();
        String value = header.value();
        request.addHeader(name, value);
        switch (name) {
            case "cookie" -> {
                for (Cookie cookie : RequestUtil.parseCookieHeader(value)) {
                    if (cookie.getName().equalsIgnoreCase("jsessionid")
                            && !request.isRequestedSessionIdFromCookie()) {
                        request.setRequestedSessionId(cookie.getValue());
                        request.setRequestedSessionCookie(true);
                        request.setRequestedSessionURL(false);
                    }
                    request.addCookie(cookie);
                }
            }
            case "content-length" -> {
                try {
                    request.setContentLength(Long.parseLong(value));
                } catch (NumberFormatException e) {
                    throw new ServletException(sm.getString("httpProcessor.parseHeaders.contentLength"));
                }
            }
            case "content-type" -> request.setContentType(value);
            default -> { }
        }
    }
}

按「段」规范化 URI

原书用三个 while + indexOf 循环分别处理 //、/./、/../。按 / 切成段再用一个栈处理，逻辑一目了然：

var segments = new ArrayList<String>();
for (String seg : normalized.split("/")) {
    switch (seg) {
        case "", "." -> { }                          // "//" 和 "/./" 直接跳过
        case ".." -> {
            if (segments.isEmpty()) return null;     // 想跳出根目录
            segments.remove(segments.size() - 1);    // 弹出上一段
        }
        default -> segments.add(seg);
    }
}
return "/" + String.join("/", segments);

设计要点

这一章的代码里有几个可以带到别的项目里的设计决定。每条按「做法 → 取舍 → 替代方案 → 还能用在哪」来写；系统的讨论见设计篇。

1连接器只负责把字节变成对象

连接器创建并填充 Request/Response，然后调用 container.invoke()，从此不再关心业务。

取舍
两边要约定一个稳定的接口；好处是后面换连接器（BIO→NIO→NIO2）完全不影响容器。
还能用在
RPC 框架的 transport 层 vs 业务层、Netty 的 codec handler vs 业务 handler：协议编解码和业务处理永远分开。
延伸：第 29 章 · 整体架构：分层与边界
2懒解析：用到才解析

请求参数和 Cookie 在第一次调用 getParameter() 时才解析，parsed 标志保证只解析一次。

取舍
不用的请求不付成本；但解析时机会带来副作用——先读了 getInputStream()，表单参数就再也拿不到了。
替代方案
在连接器里全部提前解析（简单，但浪费）。
还能用在
昂贵的派生数据按需计算并缓存；如果对象会被多线程访问，缓存要考虑可见性。
延伸：第 32 章 · 并发、隔离与演进
3热点路径手写解析器

SocketInputStream 按字节扫描请求行和头部，复用 char[] 缓冲区，不用 BufferedReader.readLine()。

取舍
少创建对象、能精确控制编码（HTTP 头是 ISO-8859-1）；代价是代码复杂、边界条件多。
替代方案
标准库或成熟的解析库。
还能用在
只在压测证明的热点上手写，其余地方用标准库；手写的部分配上大量边界测试。
延伸：第 32 章 · 并发、隔离与演进
4错误消息集中在资源包里

每个包一个 StringManager + LocalStrings.properties，代码里只写键。

取舍
消息可以翻译、可以统一修改；读代码时要多跳一次文件。
还能用在
大型项目的错误码表 + 国际化文案；日志和异常消息也能从中受益。

小结

  • 连接器负责创建 HttpServletRequest / HttpServletResponse；它被拆成「等连接」的 HttpConnector 和「拆报文」的 HttpProcessor。
  • 请求行要拆出查询串、处理绝对 URI、取出 URL 中的 jsessionid，并做安全的规范化。
  • 请求头逐个读取，cookie、content-length、content-type 需要额外处理。
  • 参数懒解析、只解析一次、解析完只读。
  • StringManager 每个包一个单例，从 LocalStrings*.properties 读取多语言消息。
  • 本章连接器每次只能处理一个请求，用完就关连接——下一章的 Tomcat 默认连接器解决这两个问题。
