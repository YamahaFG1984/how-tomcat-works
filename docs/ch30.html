扩展点设计

Tomcat 最了不起的地方，不是它自己做了什么，而是它让别人能做什么：Spring、安全框架、监控代理、云厂商的定制版， 全都是在不改 Tomcat 一行代码的前提下接进来的。这一章把 Tomcat 的扩展点归纳成四种形态， 总结一个好扩展点的标准，再说说扩展点的代价——Tomcat 自己就删掉过好几个。

本章目标

  • 能列出 Tomcat 的主要扩展点，并归入拦截链、事件监听、策略插槽、发现机制四种形态
  • 知道遇到一个扩展需求时该选哪种形态
  • 掌握好扩展点的七条标准，并能在代码里实现它们
  • 会用子优先的类加载器隔离插件
  • 知道什么时候不该加扩展点

四种形态

怎么选

常见的误用是「用监听器改流程」：例如在 BEFORE_START 事件里抛异常阻止组件启动。能做到，但调用者很难理解启动为什么失败。 反过来，「用拦截链做通知」会让每个阀都背上「记得调用 next」的义务。形态选对了，扩展者的心智负担就小。

好扩展点的七条标准

  1. 窄而稳定的接口。Valve.invoke(request, response) 只有一个核心方法。方法越少，实现者越容易写对，接口也越不需要改。
  2. 有默认实现。没配置 Realm、Manager、Loader 时，Context 会创建默认的。扩展是可选的，不是使用的前提。
  3. 明确的调用约定：在哪个线程调用、调用几次、以什么顺序、能不能阻塞。Servlet 规范花了大量篇幅写这些，第 24 章的 ReadListener 就规定了只能在 isReady() 为真时读。
  4. 和生命周期集成。Tomcat 在启动 Context 时检查 if (realm instanceof Lifecycle)，是就一起启动。扩展不需要自己找时机初始化。
  5. 错误隔离策略要想清楚，并写进约定。拦截链里一个阀出错，整个请求失败（它在主路径上）。监听器则要分情况： LifecycleListener 抛异常会让组件启动失败——因为 ContextConfig 这样的监听器本身就承担着配置工作，失败了就不该继续； 而会话的创建、销毁、属性变化这类通知，Tomcat 会捕获监听器的异常、记日志后继续——一个统计在线人数的监听器出 bug，不该让用户的会话无法失效。 关键是「这个扩展失败了，主流程还有没有意义」。
  6. 为演化留余地。给扩展者一个抽象基类（ValveBase、RealmBase、HttpServlet），接口加方法时在基类里提供默认实现；Java 8 之后也可以直接用 default 方法。
  7. 可诊断。能列出「现在装了哪些扩展」：Tomcat 的每个阀、每个 Realm 都是 MBean，可以在 JConsole 里看到。扩展一多，「这个请求到底经过了哪些阀」就是最常见的问题。

写这个示例时踩到了两个坑，都是 Tomcat 早已处理过的：一是第一版用普通的 URLClassLoader（父优先），由于插件类恰好也在宿主的类路径上， 被父加载器抢先加载了——插件根本没有被隔离；二是 ServiceLoader 在子加载器上查找时，会把父加载器的服务声明也找出来， 导致宿主的渠道被每个插件重复发现一遍。修复后，发现时只接受「由这个加载器自己定义」的实现。

扩展点的代价

每个公开的扩展点都是一个承诺：有人依赖它，你就不能随便改。Tomcat 的历史里删掉过不少扩展点，每一个都付出了迁移成本：

被移除的扩展点出现在为什么移除教训
ValveContext第 5 章每次请求要创建的有状态迭代器，阀直接持有 next 更简单扩展接口里不要暴露实现细节
容器级的 Mapper 接口第 5、12 章映射逻辑后来集中到连接器的全局 Mapper，没人需要替换它没有第二个实现的接口只是负担

SingleThreadModel第 11 章给了虚假的线程安全保证扩展点的语义如果有坑，越早删越好
🔑 什么时候加扩展点：三次法则

第一次遇到需求，直接写；第二次遇到相似的需求，忍住，复制一下；第三次，再抽象出扩展点——这时你手里有三个真实的例子，知道哪些部分真的会变。 在那之前，保留一个内部的接缝就够了：比如把创建逻辑集中在一个工厂方法里，以后要开放时只改一处，而不是一开始就对外公开一个接口。

Publisher 是一个消息发布器：把消息通过某个「渠道」（控制台、短信、Webhook）发出去。它身上集中了四种扩展点，每一种都对应 Tomcat 的同类机制： 

public final class Publisher extends LifecycleBase {

    private final Map<String, Channel> channels = new ConcurrentHashMap<>();            // ④ 发现机制填充
    private final List<Consumer<PublishEvent>> listeners = new CopyOnWriteArrayList<>(); // ② 事件监听
    private final Pipeline<Message> pipeline = new Pipeline<>(this::deliver);         // ① 拦截链
    private volatile Formatter formatter = new PlainFormatter();                       // ③ 策略插槽 + 默认值

    /** ③ 按类名创建策略（server.xml 里 className 属性的做法） */
    public void setFormatterClass(String className) throws ReflectiveOperationException {
        if (className != null && !className.isBlank()) {
            setFormatter((Formatter) Class.forName(className.trim()).getConstructor().newInstance());
        }
    }

    /** ④ 只接受「由这个加载器自己定义」的实现，避免把宿主的服务重复发现一遍 */
    public void discoverChannels(ClassLoader loader, String source) {
        ServiceLoader.load(Channel.class, loader).stream()
                .filter(p -> p.type().getClassLoader() == loader)
                .map(ServiceLoader.Provider::get)
                .forEach(c -> channels.putIfAbsent(c.name(), c));
    }

    /** 标准 4：策略自己有生命周期，就跟着启停 */
    @Override protected void startInternal() { if (formatter instanceof Lifecycle l) l.start(); }

    /** 标准 5：监听器之间互相隔离 */
    private void fire(PublishEvent event) {
        for (var l : listeners) {
            try {
                l.accept(event);
            } catch (RuntimeException e) {
                System.out.println("      （监听器出错已忽略：" + e.getMessage() + "）");
            }
        }
    }

    /** 标准 7：可诊断 */
    public Map<String, String> describe() { … }
}

扩展接口本身：supports 是「后来才加」的方法，用 default 实现保持老插件兼容（标准 6）：

public interface Channel {

    String name();

    void send(Message message) throws Exception;

    /** 后来才加的方法：用 default 实现保持向后兼容，老插件不用重新编译 */
    default boolean supports(Message message) {
        return true;
    }
}

插件类加载器：

@Override
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            if (isShared(name)) {
                c = getParent().loadClass(name);              // java.* 和 API 包：父优先
            } else {
                try {
                    c = findClass(name);                      // 其余：子优先
                } catch (ClassNotFoundException e) {
                    c = getParent().loadClass(name);
                }
            }
        }
        if (resolve) resolveClass(c);
        return c;
    }
}

那个有 bug 的监听器每次都抛异常，但发布照常进行，其他监听器照常收到事件——发布事件是纯通知，所以选择了隔离（标准 5）。 修复前的输出（普通 URLClassLoader）里，console 和 sms 各被发现了两次，WebhookChannel 由 AppClassLoader 加载。

小结

  • Tomcat 的扩展点可以归为四种形态：拦截链（Valve、Filter）、事件监听（各种 Listener）、策略插槽（Realm、Manager、Loader）和发现机制（className、SCI）。
  • 需要改变流程用拦截链，只需要知道用监听，替换整块能力用策略插槽；实现来自第三方时再加发现机制。
  • 好扩展点的七条标准：窄接口、有默认值、调用约定明确、集成生命周期、错误隔离、为演化留余地、可诊断。
  • 第三方插件用子优先的类加载器隔离，共享 API 必须父优先。
  • 每个公开扩展点都是长期承诺；用三次法则决定何时开放，在那之前只保留内部接缝。

动手练习

  1. 给 Publisher 加一个「重试阀」：渠道抛异常时最多重试 3 次，每次间隔翻倍。思考：它应该放在敏感词阀的前面还是后面？
  2. 给拦截链加上排序：Valve 增加 default int order() { return 0; }，Pipeline 按它排序。这对已有的 lambda 阀有什么影响？
  3. 写一个依赖不同版本 Gson（或任意库）的插件，验证 PluginClassLoader 能让它和宿主使用各自的版本。
  4. 回顾你项目里的一个「扩展点」（策略接口、钩子、插件），用七条标准逐条打分，找出最需要改进的一条。
