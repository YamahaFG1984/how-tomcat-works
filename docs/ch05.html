第 5 章

容器

连接器把请求交给容器的 invoke 方法之后，发生了什么？ 这一章揭开 Catalina 第二大模块的结构：四种层级的容器（Engine、Host、Context、Wrapper）， 以及贯穿所有容器的管道（Pipeline）与阀（Valve）机制。 理解了管道和阀，你就理解了 Tomcat 处理请求的主干流程。

本章目标

  • 认识四种容器以及它们的父子关系
  • 理解管道、阀、基础阀、ValveContext 是如何配合的
  • 理解 Wrapper 如何加载 Servlet，Context 如何把请求分派给 Wrapper
  • 对比 Tomcat 4 的 ValveContext 和现代 Tomcat 的 getNext() 责任链

四种容器

容器是处理 Servlet 请求、填充响应对象的模块，由 org.apache.catalina.Container 接口表示。Catalina 中有四种不同层级的容器：

容器代表接口标准实现详见
Engine整个 Servlet 引擎EngineStandardEngine第 13 章
Host一个虚拟主机HostStandardHost第 13 章
Context一个 Web 应用ContextStandardContext第 12 章
Wrapper一个 ServletWrapperStandardWrapper第 11 章

四个接口都继承 Container，四个标准实现都继承抽象类 ContainerBase（位于 org.apache.catalina.core）。一个能工作的 Catalina 部署不需要四种容器齐全：本章第一个应用只有一个 Wrapper，第二个应用是一个 Context 加两个 Wrapper。

Container 接口提供了管理子容器的方法：addChild、removeChild、findChild(name)、findChildren()；以及关联辅助组件的 getter/setter：Loader（第 8 章）、Logger（第 7 章）、Manager（第 9 章）、Realm（第 10 章）、Resources。

管道与阀

容器最巧妙的设计是：它不把「收到请求后做什么」写死在代码里，而是交给一条管道。管道里有若干个阀，每个阀完成一项任务；管道末尾总有一个基础阀（basic valve），负责真正的处理。管理员可以通过编辑 server.xml 往管道里加阀，不用改代码。

容器的 invoke 只有一行——把活交给管道：

public void invoke(Request request, Response response) throws IOException, ServletException {
    pipeline.invoke(request, response);
}

为什么需要 ValveContext

最直观的管道实现是一个 for 循环：

for (int n = 0; n < valves.length; n++) {
    valves[n].invoke(...);
}
basicValve.invoke(...);

但这样阀只能在「之前」做事，没法在后续步骤完成之后再做点什么（比如统计耗时、记录响应状态码），也无法中途拦截请求。Tomcat 的设计者引入了 ValveContext：管道创建一个 ValveContext 并调用它的 invokeNext；ValveContext 调用第一个阀，并把自己传进去；阀在合适的时机调用 context.invokeNext() 把请求传给下一个阀。

protected class StandardPipelineValveContext implements ValveContext {
    protected int stage = 0;

    public void invokeNext(Request request, Response response)
            throws IOException, ServletException {
        int subscript = stage;
        stage = stage + 1;
        if (subscript < valves.length) {
            valves[subscript].invoke(request, response, this);     // 把自己传给阀
        } else if ((subscript == valves.length) && (basic != null)) {
            basic.invoke(request, response, this);                 // 附加阀都走完了，轮到基础阀
        } else {
            throw new ServletException(sm.getString("standardPipeline.noValve"));
        }
    }
}
🔑 这就是「洋葱模型」

阀在 invokeNext() 之前写的代码按顺序执行，之后写的代码按相反顺序执行；不调用 invokeNext() 就等于拦截了请求。Servlet 的 FilterChain.doFilter()、Spring 的拦截器、Koa/Hono 的中间件都是同一个思想。

Tomcat 5 把内部类换成了独立的 StandardValveContext，逻辑完全一样，只是多了一个 set(basic, valves) 方法以便复用。

Wrapper 与 Context 接口

  • Wrapper 代表一个 Servlet 定义，负责它的生命周期（调用 init、service、destroy）。最重要的两个方法：load() 加载并初始化 Servlet，allocate() 返回一个已初始化的实例（还要考虑 SingleThreadModel，见第 11 章）。对 Wrapper 调用 addChild 会抛 IllegalArgumentException。
  • Context 代表一个 Web 应用，通常有一个或多个 Wrapper 子容器。重要方法有 addWrapper、createWrapper、addServletMapping 等（第 12 章）。

应用 2：Context + 两个 Wrapper

大多数 Web 应用不止一个 Servlet，需要用 Context 管理多个 Wrapper。多了 Wrapper，就需要一个组件决定「这个请求交给哪个 Wrapper」——Tomcat 4 中这个组件叫 Mapper（Tomcat 5 起取消了 Mapper 接口，改用别的方式查找子容器）。

整个流程可以归纳为四句话：

  1. 容器有一条管道，容器的 invoke 调用管道的 invoke。
  2. 管道依次调用所有附加阀，最后调用基础阀。
  3. Wrapper 的基础阀负责加载 Servlet 并调用它。
  4. 有子容器的 Context，其基础阀用 Mapper 找到子容器，调用子容器的 invoke——于是回到第 1 步。
public Container map(Request request, boolean update) {
    String contextPath = ((HttpServletRequest) request.getRequest()).getContextPath();
    String requestURI = ((HttpRequest) request).getDecodedRequestURI();
    String relativeURI = requestURI.substring(contextPath.length());
    Wrapper wrapper = null;
    String name = context.findServletMapping(relativeURI);
    if (name != null)
        wrapper = (Wrapper) context.findChild(name);
    return (wrapper);
}

② 管道：CopyOnWriteArrayList + 模式匹配

private final List<Valve> valves = new CopyOnWriteArrayList<>();   // 读多写少，运行时增删阀也安全

@Override
public void addValve(Valve valve) {
    if (valve instanceof Contained c) {        // Java 16 模式匹配，不用再强转
        c.setContainer(container);
    }
    valves.add(valve);
}

@Override
public void invoke(HttpRequest request, HttpResponse response) throws Exception {
    new StandardValveContext(List.copyOf(valves), basic).invokeNext(request, response);
}

private static final class StandardValveContext implements ValveContext {
    private final List<Valve> valves;
    private final Valve basic;
    private int stage;

    @Override
    public void invokeNext(HttpRequest request, HttpResponse response) throws Exception {
        int subscript = stage++;
        if (subscript < valves.size()) {
            valves.get(subscript).invoke(request, response, this);
        } else if (subscript == valves.size() && basic != null) {
            basic.invoke(request, response, this);
        } else {
            throw new ServletException("No valve");
        }
    }
}

③ Wrapper：线程安全的懒加载

原书的 allocate() 用一个普通字段缓存实例，多个线程同时第一次访问时可能加载出多个实例。Java 17 版用 volatile + 双重检查锁定：

private volatile Servlet instance;

public Servlet allocate() throws ServletException {
    Servlet servlet = instance;
    if (servlet == null) {
        synchronized (this) {
            servlet = instance;
            if (servlet == null) {
                instance = servlet = loadServlet();   // 加载、实例化、init(null)
            }
        }
    }
    return servlet;
}

其他：SimpleLoader 写成了 record；Context 不再有单独的 Mapper，映射逻辑直接写在 SimpleContext.map() 里（和 Tomcat 5 之后一致）；SimpleContextValve 真正实现了原书只算不用的 /WEB-INF、/META-INF 访问禁止。

④ Tomcat 11 的阀：从 ValveContext 到 getNext()

从 Tomcat 5.5/6 开始，ValveContext 被删掉了。每个阀直接持有下一个阀的引用，形成一条单向链表：

设计要点

这一章的代码里有几个可以带到别的项目里的设计决定。每条按「做法 → 取舍 → 替代方案 → 还能用在哪」来写；系统的讨论见设计篇。

1组合模式：四种容器一棵树

Engine、Host、Context、Wrapper 都实现 Container，用 addChild/findChild 组成树，任何一层都能当顶层用。

取舍
接口统一、可以只部署其中几层（本章就只用了 Context + Wrapper）；代价是接口偏「胖」，Wrapper 的 addChild 只能抛异常。
替代方案
每层一个不相关的类，靠具体类型连接。
还能用在
组织架构、菜单、规则树、文件系统：凡是「部分—整体」层级结构都可以用。
延伸：第 29 章 · 整体架构：分层与边界
2管道 + 阀：可插拔的横切逻辑

每个容器有一条管道，附加阀按顺序执行，最后是基础阀；日志、鉴权、统计都以阀的形式插入。

取舍
不改容器代码就能增加功能；代价是调用链变长、顺序敏感、调试时栈很深。
替代方案
AOP、装饰器、子类覆盖。
还能用在
Servlet Filter、Netty ChannelPipeline、OkHttp Interceptor、Spring HandlerInterceptor 都是同一个思路。
延伸：第 30 章 · 扩展点设计
3基础阀固定在链尾

附加阀可以任意增删，基础阀由容器自己设置，总在最后执行。

取舍
保证核心逻辑一定存在（除非前面的阀主动短路）；是模板方法思想在链上的变体。
还能用在
设计中间件链时，把「必须执行的终点」和「可选的中间件」分开管理。
延伸：第 31 章 · 设计模式实战
4被推翻的设计：ValveContext

Tomcat 4 用 ValveContext 记录当前执行到第几个阀；Tomcat 5 起阀直接持有 next 引用。

取舍
ValveContext 是有状态的外部迭代器，必须每个请求一份；链表版无状态、更简单，也更快。
还能用在
引入辅助对象之前先问：它保存的状态是否真的必要？能不能用不可变结构代替？
延伸：第 32 章 · 并发、隔离与演进

小结

  • 四种容器：Engine ⊃ Host ⊃ Context ⊃ Wrapper；部署时不必四种齐全。
  • 容器的 invoke 把请求交给管道；管道依次调用附加阀，最后调用基础阀。
  • ValveContext.invokeNext() 让阀可以在后续处理前后各做一些事，形成嵌套调用。
  • Wrapper 的基础阀调用 Servlet；Context 的基础阀找到 Wrapper 并调用它的 invoke。
  • 子容器没有 Loader 时使用父容器的 Loader。
  • 现代 Tomcat 去掉了 ValveContext 和 Mapper，阀通过 getNext() 串成链表，但整体架构未变。

动手练习

  1. 写一个 lambda 阀：如果请求头里没有 X-Token: secret，直接 response.sendError(403) 并且不调用 invokeNext。验证 Servlet 不会被执行。
  2. 把这个阀分别加到 Context 和某一个 Wrapper 的管道上，比较两种做法的影响范围。
  3. 给 SimpleContext.map() 增加前缀匹配：addServletMapping("/api/*", "Modern") 让 /api/ 下的所有路径都交给 Modern。
  4. 在 Tomcat 11 版本里，用 context.getPipeline().getFirst() 和 getNext() 把整条阀链打印出来，看看 Tomcat 自己还装了哪些阀。
