第 33 章 · 综合与练习

综合：一个请求的完整旅程

32 章下来，Tomcat 被拆成了几十个零件。这一章把它们重新装回去：先跟着 Tomcat 从 main 方法启动到开始接客， 再跟着一个带认证的请求从网卡走到 Servlet 再走回来，每一步都标出它属于哪一章。 配套的程序会在 Engine、Host、Context、Wrapper 四层管道上各装一个追踪阀，让请求自己把旅程打印出来。

本章目标

  • 能按顺序讲出 Tomcat 从启动到就绪的每一步
  • 能按顺序讲出一个请求经过的每一个组件，并指出它在哪一章
  • 拿到一张「类 → 章节」的速查表
  • 知道怎样开始阅读真正的 Tomcat 源码

旅程一：从 main 到就绪

这正是第 29 章的两条原则在起作用：配置（server.xml）→ 装配（Digester）→ 运行（start），以及「先把里面准备好再开门」——Connector 永远最后启动。 关闭的顺序反过来：关闭钩子或关闭端口触发 server.stop()，先停 Connector（不再接收新请求），再逐层停止容器，最后销毁。

让请求自己说出来

源码java17/src/main/java/modern/ch33/JourneyTracer.java

JourneyTracer 在 Engine、Host、Context、Wrapper 的管道上各装了一个 TraceValve：调用 getNext() 之前打印「→」，之后打印「←」， 用一个 ThreadLocal 记录缩进深度。再加上 BASIC 认证、请求和会话监听器、一个同时拦截 REQUEST 和 FORWARD 的过滤器、一次 forward： 

static final class TraceValve extends ValveBase {
    @Override
    public void invoke(Request request, Response response) throws IOException, ServletException {
        trace(chapter, "→ " + level + " 管道：" + describe(request));
        DEPTH.set(DEPTH.get() + 1);
        try {
            getNext().invoke(request, response);       // 最后一个阀之后是这一层的基础阀，它负责找下一层容器
        } finally {
            DEPTH.set(DEPTH.get() - 1);
            trace(chapter, "← " + level + "（状态码 " + response.getStatus() + "）");
        }
    }
}

tomcat.getEngine().getPipeline().addValve(new TraceValve("[13]", "Engine"));
tomcat.getHost().getPipeline().addValve(new TraceValve("[13]", "Host"));
ctx.getPipeline().addValve(new TraceValve("[12]", "Context"));
ctx.getPipeline().addValve(new BasicAuthenticator());           // 认证器排在追踪阀之后
orders.getPipeline().addValve(new TraceValve("[11]", "Wrapper"));

./run.sh ch33.JourneyTracer

从这段输出里能读出好几个前面章节的结论：

  1. 映射在进入容器之前就完成了。Engine 阀第一次被调用时，Host、Context、Wrapper 已经确定——这是 CoyoteAdapter 里的 Mapper 做的（第 23 章），原书第 12、13 章那种逐层映射已经被替换了。
  2. 阀的顺序有意义。Context 层的追踪阀排在认证器前面，所以它看到的用户还是 null；到了 Wrapper 层，认证已经完成，用户是 tom。
  3. 短路发生在最早能判断的地方。没有凭据时，认证器直接返回 401，Wrapper、过滤器、Servlet 都没有执行。
  4. forward 不经过 Wrapper 管道。分派由 ApplicationDispatcher 直接分配目标 Servlet 并构建过滤器链（第 21 章），所以第二次只看到了 AuditFilter（FORWARD），没有看到 Wrapper 追踪阀。
  5. 从头到尾是同一个线程。所有输出都来自 exec-2：同步处理中，线程封闭让请求对象不需要任何同步（第 32 章）。

接下来：读真正的 Tomcat 源码

本书的迷你实现都是为了让你能读懂真实的源码。建议的路线：

  1. 拿到源码：git clone https://github.com/apache/tomcat.git，切到 11.0.x 分支。它用 Ant 构建（ant），但只读代码的话，用 IDE 直接打开即可；或者在本工程里让 IDE 下载 tomcat-embed-core 的源码 jar。
  2. 用调试器代替通读：在本章的 JourneyTracer 里，于 CoyoteAdapter.service、StandardContextValve.invoke、StandardWrapperValve.invoke、ApplicationFilterChain.internalDoFilter 下断点，发一个请求，单步走一遍。
  3. 按本书的顺序读：连接器（org.apache.coyote、org.apache.tomcat.util.net）→ 容器（org.apache.catalina.core）→ 组件（loader、session、realm）→ 启动（startup）。每读一个类，先回到对应章节看一眼迷你版。
  4. 读测试：test/ 目录里的测试（例如 TestStandardContext、TestMapper）往往比注释更能说明边界情况。
  5. 读变更：每个版本的 changelog 和安全公告说明了「为什么改」，是学习设计演进的最好材料（第 32 章）。

小结

  • 启动：脚本 → Bootstrap（类加载器）→ Catalina（Digester 装配）→ init → start（先容器后连接器）→ await。
  • 请求：Acceptor → Poller → Worker → Processor → CoyoteAdapter（Mapper）→ Engine → Host → Context → Wrapper → 过滤器链 → Servlet，然后原路返回。
  • 映射在进入容器前一次完成；阀的顺序决定了每一层能看到什么；短路发生在最早能判断的地方；forward 只经过过滤器。
  • 速查表把 Tomcat 11 的主要类对应到本书章节，读源码时可以随时回查。

动手练习

  1. 给 JourneyTracer 加一个 AccessLogValve 到 Host 管道，观察它的输出出现在追踪日志的什么位置，解释原因。
  2. 让 OrderServlet 在 id 为 0 时抛出异常，并配置一个错误页。追踪 ERROR 分派经过了哪些阀和过滤器。
  3. 把 OrderServlet 改成异步（startAsync 后在另一个线程里 dispatch），观察追踪日志里线程名和嵌套结构的变化。
  4. 按「源码」一节的方法，在 Mapper.internalMapWrapper 下断点，验证第 12 章讲的四条映射规则在真实代码里的顺序。
