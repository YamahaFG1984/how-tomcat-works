第 9 章

Session 管理

HTTP 是无状态的：服务器分不清两个请求是不是同一个人发的。Servlet 用 HttpSession 解决这个问题， 而在 Catalina 里，负责创建、查找、销毁会话的组件叫管理器（Manager）。 它总是挂在 Context 上，还可以把会话保存到文件或数据库，让服务器重启后用户不用重新登录。

本章目标

  • 理解 request.getSession() 背后发生了什么，以及 JSESSIONID Cookie 的往返
  • 认识 Session、StandardSession、StandardSessionFacade 三者的关系
  • 理解 StandardManager 如何清理过期会话、如何在重启前后保存和恢复会话
  • 了解持久化管理器的「换出」「备份」以及 FileStore、JDBCStore

从 getSession() 说起

Servlet 调用 request.getSession()，默认连接器里的 HttpRequestBase 会这样处理：

private HttpSession doGetSession(boolean create) {
    if (context == null)
        return (null);                          // 还不知道属于哪个应用
    if ((session != null) && !session.isValid())
        session = null;
    if (session != null)
        return (session.getSession());          // 本次请求已经拿过了

    Manager manager = context.getManager();     // 通过 Context 找到管理器
    if (manager == null)
        return (null);                          // 这个应用不支持会话

    if (requestedSessionId != null) {           // 浏览器带来了会话 ID（Cookie 或 URL 里的 jsessionid）
        session = manager.findSession(requestedSessionId);
        if ((session != null) && !session.isValid())
            session = null;
        if (session != null)
            return (session.getSession());
    }
    if (!create)
        return (null);
    session = manager.createSession();          // 新建一个
    return (session.getSession());
}

管理器默认把会话放在内存里，也可以持久化到文件或数据库。相关类型都在 org.apache.catalina.session 包里。

expire() 做的事：标记 expiring → setValid(false) → 从管理器移除 → 逐个解除属性绑定 → 通知会话监听器（SESSION_DESTROYED_EVENT）→ 通知应用里的 HttpSessionListener.sessionDestroyed → 回收对象。

ManagerBase

所有活动会话放在一个 HashMap sessions 里，键是会话 ID。add、remove、findSession 都是对它加锁后的简单操作；createSession 调用受保护方法 generateSessionId() 生成唯一 ID。

StandardManager：内存 + 关机存盘

StandardManager 运行时把会话放在内存里。它实现了 Lifecycle：stop() 时调用 unload()，把仍然有效的会话序列化到 Context 工作目录下的 SESSIONS.ser；start() 时调用 load() 读回来。所以正常关闭再启动 Tomcat，用户的登录状态不会丢。

管理器还负责销毁过期会话。Tomcat 4 中 StandardManager 实现了 Runnable，后台线程每隔 checkInterval（默认 60）秒调用一次 processExpires()：如果「现在 − 最后访问时间」超过 maxInactiveInterval，就调用会话的 expire()。

public void run() {
    while (!threadDone) {
        threadSleep();          // 睡 checkInterval 秒
        processExpires();
    }
}
ⓘ 超时时间到底是多少？

StandardManager 自己的 maxInactiveInterval 默认是 60 秒，但别被骗了：ContainerBase.setManager() 会调用管理器的 setContainer()，后者把它覆盖为 context.getSessionTimeout() * 60。StandardContext 的 sessionTimeout 默认 30（分钟），也就是 web.xml 里的 <session-timeout>。Tomcat 5 起不再有独立线程，processExpires() 由 StandardContext 的 backgroundProcess() 周期性调用。

PersistentManagerBase：换出与备份

持久化管理器和 StandardManager 的主要区别是多了一个 Store（存储）。会话可以被：

public void run() {                          // Tomcat 4
    while (!threadDone) {
        threadSleep();
        processExpires();
        processPersistenceChecks();          // = processMaxIdleSwaps + processMaxActiveSwaps + processMaxIdleBackups
    }
}

public Session findSession(String id) throws IOException {
    Session session = super.findSession(id); // 先在内存里找
    if (session != null)
        return (session);
    session = swapIn(id);                    // 再去 Store 里找
    return (session);
}

DistributedManager（仅 Tomcat 4）用于集群：创建会话时把它序列化，通过 ClusterSender 发给其他节点；后台线程用 ClusterReceiver 接收其他节点的通知。现代 Tomcat 中这项工作由 DeltaManager / BackupManager（org.apache.catalina.ha）承担。

Store

public interface Store {
    public Manager getManager();
    public void setManager(Manager manager);
    public int getSize() throws IOException;
    public String[] keys() throws IOException;                 // 所有会话 ID
    public Session load(String id) throws ClassNotFoundException, IOException;
    public void save(Session session) throws IOException;
    public void remove(String id) throws IOException;
    public void clear() throws IOException;
}
  • StoreBase（抽象）：提供公共功能，包括清理存储中过期会话的 processExpires()；不实现 save/load。
  • FileStore：每个会话一个文件，名为「会话 ID + .session」，用 ObjectOutputStream / ObjectInputStream 读写。
  • JDBCStore：存进数据库，需要设置 driverName 和 connectionURL。

① 用 HttpServletRequestWrapper 实现 getSession

原书在连接器的请求类里实现 getSession，再在阀里 request.setContext()。Java 17 版换了一个更「Servlet 风格」的做法：基础阀用 Servlet API 自带的装饰器 HttpServletRequestWrapper 包一层，只覆盖会话相关的方法。

public class SessionRequest extends HttpServletRequestWrapper {

    @Override
    public HttpSession getSession(boolean create) {
        if (session != null && session.isValid()) {
            return session.getSession();
        }
        session = manager.findSession(getRequestedSessionId());   // 浏览器带来的 ID 还有效吗？
        if (session != null) {
            return session.getSession();
        }
        if (!create) {
            return null;
        }
        session = manager.createSession();
        var cookie = new Cookie("JSESSIONID", session.getId());
        cookie.setPath(contextPath);       // /myApp
        cookie.setHttpOnly(true);          // JavaScript 读不到，防止 XSS 偷走会话
        response.addCookie(cookie);
        return session.getSession();
    }
}

② 会话 ID：SecureRandom + HexFormat

private final Map<String, StandardSession> sessions = new ConcurrentHashMap<>();   // 代替 synchronized + HashMap
private final SecureRandom random = new SecureRandom();

public StandardSession createSession() {
    byte[] bytes = new byte[16];                      // 128 位随机数
    random.nextBytes(bytes);
    var session = new StandardSession(this, HexFormat.of().withUpperCase().formatHex(bytes),   // Java 17
                                      maxInactiveInterval);
    sessions.put(session.getId(), session);
    return session;
}
⚠ 会话 ID 就是登录凭证

谁拿到了会话 ID，谁就「是」这个用户。所以 ID 必须用密码学安全的随机数生成（SecureRandom），长度足够（Tomcat 11 默认 16 字节），并且 Cookie 要带 HttpOnly，HTTPS 站点还要带 Secure。登录成功后还应调用 request.changeSessionId()（Servlet 3.1 新增），防止「会话固定」攻击。

③ 过期清理：ScheduledExecutorService

public void processExpires() {
    long now = System.currentTimeMillis();
    sessions.values().stream().filter(s -> s.isExpired(now)).forEach(StandardSession::expire);
}

@Override
public void start() {
    load();
    expirer = Executors.newSingleThreadScheduledExecutor(...);
    expirer.scheduleWithFixedDelay(this::processExpires, checkInterval, checkInterval, TimeUnit.SECONDS);
}

④ 安全的反序列化

原书用 ObjectInputStream 直接读 SESSIONS.ser。Java 反序列化是历史上最严重的漏洞来源之一：精心构造的字节流可以在 readObject 过程中执行任意代码。Java 9 引入了 ObjectInputFilter，可以只放行预期的类：

private static final ObjectInputFilter FILTER = ObjectInputFilter.Config.createFilter(
        "modern.ch09.session.StandardSession;java.lang.*;java.util.**;!*");   // 末尾 !* 拒绝其他一切

try (var in = new ObjectInputStream(Files.newInputStream(pathname))) {
    in.setObjectInputFilter(FILTER);
    int count = in.readInt();
    for (int i = 0; i < count; i++) {
        var session = (StandardSession) in.readObject();
        session.setManager(this);                      // transient 字段读回后重新建立
        sessions.put(session.getId(), session);
    }
}
💡 一个真实的小插曲

写这段代码时，过滤器一开始写的是 java.util.*，结果恢复会话时被拒绝了：* 只匹配 java.util 包本身，而会话属性表 ConcurrentHashMap 在 java.util.concurrent 子包里。改成 java.util.**（包含子包）才通过。白名单宁可写严，被拒绝了再放宽。

小结

  • 管理器挂在 Context 上；请求通过 Context 找到管理器，按请求带来的会话 ID 查找或新建会话。
  • StandardSession 同时实现 HttpSession、Session 和 Serializable；交给 Servlet 的是外观 StandardSessionFacade。
  • StandardManager 把会话放在内存，后台清理过期会话，停止时存盘、启动时恢复。
  • 持久化管理器借助 Store（FileStore / JDBCStore）实现会话的换出、换入和备份；DistributedManager 用于集群复制。
  • 现代实践：安全随机 ID、HttpOnly/Secure/SameSite Cookie、登录后更换会话 ID、反序列化白名单。

动手练习

  1. 在 SessionServlet 里存一个没有实现 Serializable 的对象，停止服务器，观察 Java 17 版的 unload() 发生了什么。参考 Tomcat 的做法，改成「跳过不可序列化的属性并打印警告」。
  2. 给 Java 17 版实现一个 FileStore：每个会话一个 <id>.session 文件；再实现「活动会话数超过 maxActiveSessions 时把最久未访问的会话换出到 FileStore」。
  3. 实现 HttpSessionListener 通知：会话创建和销毁时调用应用注册的监听器，并用它统计在线人数。
  4. 给会话 Cookie 加上 SameSite=Lax（提示：jakarta 6 的 Cookie.setAttribute("SameSite", "Lax")，同时修改第 3 章 HttpResponse 的 addCookie 输出所有属性）。
