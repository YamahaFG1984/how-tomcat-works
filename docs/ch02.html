第 2 章

一个简单的 Servlet 容器

第 1 章的服务器只会发文件。这一章让它学会「运行代码」：遇到 /servlet/XXX 这样的地址， 就去加载名为 XXX 的类，创建请求对象和响应对象，调用它的 service 方法。 这就是 Servlet 容器最核心的工作。我们会写两个版本，第二个版本用外观模式堵上第一个版本的安全漏洞。

本章目标

  • 掌握 Servlet 接口的五个方法，以及 init → service → destroy 的生命周期
  • 理解一个 Servlet 容器为每个请求要做的四件事
  • 学会用 URLClassLoader 从指定目录动态加载类
  • 理解为什么要用外观类（Facade）包装请求和响应对象

Servlet 接口

Servlet 编程靠的是 javax.servlet 和 javax.servlet.http 两个包（从 Jakarta EE 9 起改名为 jakarta.servlet，见本章末尾）。其中最重要的就是 Servlet 接口，所有 Servlet 都必须直接或间接实现它。它只有五个方法：

public void init(ServletConfig config) throws ServletException
public void service(ServletRequest request, ServletResponse response)
    throws ServletException, java.io.IOException
public void destroy()
public ServletConfig getServletConfig()
public java.lang.String getServletInfo()

其中 init、service、destroy 是生命周期方法，由容器在不同时刻调用：

本章用来测试的 PrimitiveServlet 极其简单：每个生命周期方法被调用时往控制台打一行字，service 再往浏览器写两行。

import javax.servlet.*;
import java.io.IOException;
import java.io.PrintWriter;

public class PrimitiveServlet implements Servlet {
    public void init(ServletConfig config) throws ServletException {
        System.out.println("init");
    }
    public void service(ServletRequest request, ServletResponse response)
            throws ServletException, IOException {
        System.out.println("from service");
        PrintWriter out = response.getWriter();
        out.println("Hello. Roses are red.");
        out.print("Violets are blue.");
    }
    public void destroy() { System.out.println("destroy"); }
    public String getServletInfo() { return null; }
    public ServletConfig getServletConfig() { return null; }
}

容器要为 Servlet 做什么

站在容器的角度，一个功能完整的 Servlet 容器对每个 Servlet 请求要做这些事：

  1. Servlet 第一次被请求时，加载 Servlet 类并调用它的 init（只做一次）。
  2. 为每个请求创建一个 ServletRequest 实例和一个 ServletResponse 实例。
  3. 调用 Servlet 的 service 方法，把这两个对象传进去。
  4. 容器关闭时调用 Servlet 的 destroy，并卸载 Servlet 类。

本章的容器是简化版：它每次请求都重新加载一次 Servlet 类，也不调用 init 和 destroy，只完成第 2、3 步。

Request 与 Response：实现接口，但大部分是空的

因为 service 方法要求传入 ServletRequest 和 ServletResponse，容器自己的 Request、Response 必须实现这两个接口。可接口里有几十个方法，本章根本用不上，原书的做法是把它们全部写成「空实现」：

public class Request implements ServletRequest {
    private InputStream input;
    private String uri;

    public void parse() { ... }        // 和第 1 章一样
    public String getUri() { return uri; }

    /* ServletRequest 的实现：几乎全是 return null */
    public Object getAttribute(String attribute) { return null; }
    public Enumeration getAttributeNames() { return null; }
    public String getParameter(String name) { return null; }
    public String getProtocol() { return null; }
    ... // 还有二十多个
}

Response 唯一认真实现的是 getWriter：

public PrintWriter getWriter() throws IOException {
    // autoflush 为 true：println() 会刷新，但 print() 不会
    writer = new PrintWriter(output, true);
    return writer;
}
⚠ 最后一行丢了

正因为 print() 不会自动刷新，PrimitiveServlet 的最后一句 out.print("Violets are blue.") 留在 PrintWriter 的缓冲区里，socket 就被关掉了。所以浏览器里只能看到 “Hello. Roses are red.”。原书说这个问题第 3 章再修；Java 17 版本在本章就修好了（见下文）。

ServletProcessor1：用类加载器载入 Servlet

这是本章最关键的类。它要做三件事：从 URI 中取出 Servlet 类名、创建一个能在 webroot 里找类的类加载器、加载类并调用 service。

public void process(Request request, Response response) {
    String uri = request.getUri();
    String servletName = uri.substring(uri.lastIndexOf("/") + 1);
    URLClassLoader loader = null;
    try {
        URL[] urls = new URL[1];
        URLStreamHandler streamHandler = null;
        File classPath = new File(Constants.WEB_ROOT);
        String repository = (new URL("file", null,
            classPath.getCanonicalPath() + File.separator)).toString();
        urls[0] = new URL(null, repository, streamHandler);
        loader = new URLClassLoader(urls);
    } catch (IOException e) {
        System.out.println(e.toString());
    }
    Class myClass = null;
    try {
        myClass = loader.loadClass(servletName);
    } catch (ClassNotFoundException e) {
        System.out.println(e.toString());
    }
    Servlet servlet = null;
    try {
        servlet = (Servlet) myClass.newInstance();
        servlet.service((ServletRequest) request, (ServletResponse) response);
    } catch (Throwable e) {
        System.out.println(e.toString());
    }
}
ⓘ 两个 URL 构造器的小坑

URL 有 URL(URL context, String spec, URLStreamHandler h) 和 URL(String protocol, String host, String file) 两个三参数构造器。直接写 new URL(null, s, null) 编译器不知道该选哪个，所以原书先声明了一个 URLStreamHandler streamHandler = null 来消除歧义。这段代码是从 Tomcat 的 ClassLoaderFactory 和 StandardClassLoader 里抄来的。类加载器在第 8 章会详细讲。

运行原书应用 1：

java -classpath ./lib/servlet.jar:./ ex02.pyrmont.HttpServer1
# 浏览器访问 http://localhost:8080/index.html 或 http://localhost:8080/servlet/PrimitiveServlet

这个容器只能运行 PrimitiveServlet；访问 ModernServlet 会抛异常，因为它继承的 HttpServlet 要求请求对象是 HttpServletRequest，而我们的 Request 只实现了 ServletRequest。

应用 2：用外观类堵住漏洞

应用 1 有个严重的问题：它把 Request 向上转型成 ServletRequest 交给 Servlet。一个了解容器内部的 Servlet 程序员完全可以再向下转型回来：

public void service(ServletRequest req, ServletResponse res) {
    ex02.pyrmont.Request internal = (ex02.pyrmont.Request) req;   // 转回去！
    internal.parse();                // 调用了只有容器才该调用的方法
    ((ex02.pyrmont.Response) res).sendStaticResource();
}

parse 和 sendStaticResource 不能设成 private，因为容器的其他类要调用它们。把类设成包级私有也是个办法，但更优雅的方法是外观模式（Facade）：

public class RequestFacade implements ServletRequest {
    private ServletRequest request = null;

    public RequestFacade(Request request) {
        this.request = request;          // 拿到 Request，但只以接口类型保存
    }

    public Object getAttribute(String attribute) {
        return request.getAttribute(attribute);
    }
    public Enumeration getAttributeNames() {
        return request.getAttributeNames();
    }
    ... // 每个接口方法都转发一次
}

ServletProcessor2 和 ServletProcessor1 唯一的区别，就是把外观对象传给 Servlet：

Servlet servlet = null;
RequestFacade requestFacade = new RequestFacade(request);
ResponseFacade responseFacade = new ResponseFacade(response);
servlet = (Servlet) myClass.newInstance();
servlet.service((ServletRequest) requestFacade, (ServletResponse) responseFacade);
🔑 真实的 Tomcat 也这样做

直到今天的 Tomcat 11，org.apache.catalina.connector.Request 交给你的 Servlet 之前，依然会先包一层 RequestFacade。你在 Servlet 里打印 request.getClass()，看到的就是 org.apache.catalina.connector.RequestFacade。

Java 17 对照版

源码java17/src/main/java/modern/ch02/modern/common/Facade.javamodern/common/ServletRequestStub.javajava17/webroot/*.java

Java 17 版保留了原书的全部结构（两个服务器、两个处理器、静态资源处理器、从 webroot 动态加载 Servlet），同时做了四处现代化改造。

① javax.servlet → jakarta.servlet

2017 年 Oracle 把 Java EE 交给 Eclipse 基金会，改名 Jakarta EE，但不允许继续使用 javax 这个包名。从 Jakarta EE 9（Tomcat 10）开始，所有 Servlet API 都搬到了 jakarta.servlet。代码逻辑不变，只改 import。

原书（Servlet 2.3 / Tomcat 4）
import javax.servlet.*;

public class PrimitiveServlet implements Servlet {
    public void init(ServletConfig config) ...
}
Java 17（Servlet 6.1 / Tomcat 11）
import jakarta.servlet.*;

public class PrimitiveServlet implements Servlet {
    @Override
    public void init(ServletConfig config) ...
}

② 接口默认方法代替几十个空方法

jakarta 版 ServletRequest 已经有 39 个抽象方法了。与其在 Request 里手写 39 个 return null，不如写一个继承它的接口，用 default 方法统一抛出「不支持」异常——modern.common.ServletRequestStub 就是这样一个接口（由脚本生成）。容器的 Request 只覆盖真正支持的方法：

public interface ServletRequestStub extends ServletRequest {
    @Override default Object getAttribute(String arg0) { throw unsupported("getAttribute"); }
    @Override default String getParameter(String arg0) { throw unsupported("getParameter"); }
    @Override default String getProtocol() { throw unsupported("getProtocol"); }
    ... // 共 39 个
}

public class Request implements ServletRequestStub {
    private final String uri;
    private final String protocol;
    private final Map<String, Object> attributes = new HashMap<>();

    public static Request parse(InputStream input) throws IOException { ... }
    public String uri() { return uri; }                     // 容器内部方法

    @Override public String getProtocol() { return protocol; }
    @Override public Object getAttribute(String name) { return attributes.get(name); }
    @Override public void setAttribute(String name, Object value) { attributes.put(name, value); }
    ...
}
💡 抛异常比 return null 更好

返回 null 的空方法会让调用者在很远的地方碰到 NullPointerException，很难追查。直接抛 UnsupportedOperationException("本章的简化实现不支持 getParameter()")，一眼就知道问题出在哪。

③ 动态代理自动生成外观

手写外观类要给每个接口方法写一个转发方法。JDK 的 java.lang.reflect.Proxy 可以在运行时生成一个只实现指定接口的类，效果完全一样：

public static <T> T of(Class<T> iface, T target) {
    Object proxy = Proxy.newProxyInstance(iface.getClassLoader(), new Class<?>[] {iface},
            (self, method, args) -> {
                if (method.getDeclaringClass() == Object.class) {
                    return switch (method.getName()) {            // Java 14 switch 表达式
                        case "equals" -> self == args[0];
                        case "hashCode" -> System.identityHashCode(self);
                        default -> iface.getSimpleName() + "Facade";
                    };
                }
                try {
                    return method.invoke(target, args);           // 其余调用一律转发
                } catch (InvocationTargetException e) {
                    throw e.getCause();
                }
            });
    return iface.cast(proxy);
}
原书 ServletProcessor2
RequestFacade requestFacade =
    new RequestFacade(request);
ResponseFacade responseFacade =
    new ResponseFacade(response);
servlet.service((ServletRequest) requestFacade,
                (ServletResponse) responseFacade);
Java 17 ServletProcessor2
ServletRequest requestFacade =
    Facade.of(ServletRequest.class, request);
ServletResponse responseFacade =
    Facade.of(ServletResponse.class, response);
servlet.service(requestFacade, responseFacade);
response.finish(200, "OK");

为了亲眼看到外观的作用，java17/webroot/ 里多放了一个「捣蛋」Servlet——PeekServlet，它用 Java 16 的模式匹配 instanceof 尝试把请求转回容器内部类型：

out.println("request 的真实类型: " + request.getClass().getName());
if (request instanceof modern.ch02.Request internal) {
    out.println("得手了！可以直接调用容器内部方法，例如 uri() = " + internal.uri());
} else {
    out.println("转型失败：拿到的只是一个外观（facade）");
}

④ 缓冲输出，修好「最后一行丢失」

Java 17 版的 getWriter() 不再直接写 socket，而是写进内存缓冲区。service() 返回后，处理器调用 response.finish()，一次性写出状态行、Content-Length 和正文：

private final ByteArrayOutputStream body = new ByteArrayOutputStream();

@Override
public PrintWriter getWriter() {
    if (writer == null) {
        writer = new PrintWriter(new OutputStreamWriter(body, StandardCharsets.UTF_8));
    }
    return writer;
}

public void finish(int status, String reason) throws IOException {
    if (writer != null) writer.flush();        // print() 留在缓冲区里的内容也会被写出
    String head = "HTTP/1.1 " + status + " " + reason + "\r\n"
            + "Content-Type: " + (contentType != null ? contentType : "text/plain; charset=UTF-8") + "\r\n"
            + "Content-Length: " + body.size() + "\r\n"
            + "Connection: close\r\n\r\n";
    output.write(head.getBytes(StandardCharsets.ISO_8859_1));
    body.writeTo(output);
}

其他小改动：Class.newInstance()（Java 9 起废弃）换成 getDeclaredConstructor().newInstance()；URLClassLoader 的父加载器显式设为应用类加载器，这样 webroot 里的 Servlet 能找到 jakarta.servlet 的类；两个服务器的主循环合并为一个，通过 Processor 函数式接口注入不同的 Servlet 处理器。

设计要点

这一章的代码里有几个可以带到别的项目里的设计决定。每条按「做法 → 取舍 → 替代方案 → 还能用在哪」来写；系统的讨论见设计篇。

1容器只认识 Servlet 接口

容器通过 javax.servlet.Servlet 调用应用代码，应用由第三方编写，双方只共享接口。

取舍
双方可以独立演进；代价是接口一旦发布就很难改，Servlet API 二十年来只能「加」不能「改」。
替代方案
约定方法名 + 反射调用（脆弱，没有编译期检查）。
还能用在
做插件系统时，先把 SPI 接口放进一个单独的 api 包或模块，插件和宿主都只依赖它。
延伸：第 30 章 · 扩展点设计
2按类名在运行时加载

URLClassLoader.loadClass(name) + 反射创建实例，容器编译时不知道会有哪些 Servlet。

取舍
换来了「不改容器就能部署新应用」，失去了编译期检查，错误推迟到运行时才暴露。
替代方案
ServiceLoader、依赖注入容器、显式注册表。
还能用在
插件、驱动、策略类的动态装配；记得在启动阶段就加载并校验，尽早失败。
延伸：第 31 章 · 设计模式实战
3用外观对象挡住内部方法

Request 有 parse() 等公开方法，直接交给 Servlet，Servlet 就能向下转型去调用；RequestFacade 只暴露接口方法。

取舍
多一层委托代码；Java 17 版用 JDK 动态代理一次性生成，省掉了手写的几十个方法。
替代方案
包级可见性；JPMS 模块只 exports API 包，是更强的版本。
还能用在
把内部对象交给不可信代码（插件、脚本、回调）时，交出接口视图而不是对象本身。
延伸：第 31 章 · 设计模式实战
4按 URI 前缀分派给不同处理器

/servlet/ 开头交给 ServletProcessor，其余交给 StaticResourceProcessor。

取舍
分派规则写死在 if 里，加一种处理器就要改代码；第 5 章的容器和映射器把它变成了可配置的。
还能用在
「分派器 + 一组处理器」是 MVC 框架 DispatcherServlet 的雏形，也是命令行工具子命令的常见结构。
延伸：第 31 章 · 设计模式实战

小结

  • Servlet 接口有五个方法，其中 init、service、destroy 是生命周期方法。
  • Servlet 容器的核心工作：加载 Servlet 类、为每个请求创建请求/响应对象、调用 service。
  • URLClassLoader 可以从指定目录或 JAR 动态加载类；以 / 结尾的 URL 表示目录。
  • 直接把内部对象交给用户代码有安全风险；外观类只暴露接口方法，Tomcat 至今在用这个模式。
  • 现代 Java：jakarta.servlet 包名、接口默认方法、动态代理、instanceof 模式匹配、switch 表达式。

动手练习

  1. 在 Java 17 版里给 Request 实现 getParameter：解析 URI 里 ? 后面的查询串。然后写个 Servlet 打印 ?name=tom 的值。
  2. 现在每次请求都会新建类加载器、重新加载 Servlet 类。改成用一个 ConcurrentHashMap<String, Servlet> 缓存实例，并在第一次加载时调用 init(null)。观察控制台的 “init” 现在只打印一次。
  3. 给 HttpServer 加一个关闭钩子（第 16 章会讲），退出前对缓存里的所有 Servlet 调用 destroy()。
  4. 访问 /servlet/ModernServlet，阅读控制台里的异常信息，说说它为什么在本章的容器里跑不起来。
