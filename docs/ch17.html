第 17 章

Tomcat 的启动

前面 16 章拼出了 Tomcat 的所有零件：连接器、四种容器、载入器、管理器、Server、Service、Digester、关闭钩子。 这一章把它们串起来，回答一个问题：敲下 startup.sh 之后到底发生了什么？ 答案涉及两个 Java 类——Bootstrap 和 Catalina——以及一组启动脚本。

本章目标

  • 理解 Catalina 类：解析命令行、用 Digester 解析 server.xml、启动与停止 Server
  • 理解 Bootstrap 类：为什么要建立 common / catalina / shared 三个类加载器，为什么用反射调用 Catalina
  • 看懂 startup.sh → catalina.sh → java Bootstrap 的调用链

完整的启动链

理论上 Bootstrap 和 Catalina 可以合并成一个类。分开的原因是要支持多种运行方式：Bootstrap 用于以独立程序运行，BootstrapService 用于作为 Windows NT 服务运行……它们都复用同一个 Catalina。

Catalina 类

process：解析命令行

public void process(String args[]) {
    setCatalinaHome();          // catalina.home 默认为 user.dir
    setCatalinaBase();          // catalina.base 默认为 catalina.home
    try {
        if (arguments(args))
            execute();          // starting → start()；stopping → stop()
    } catch (Exception e) {
        e.printStackTrace(System.out);
    }
}

protected boolean arguments(String args[]) {
    ...
    for (int i = 0; i < args.length; i++) {
        if (isConfig) { configFile = args[i]; isConfig = false; }
        else if (args[i].equals("-config"))   isConfig = true;
        else if (args[i].equals("-debug"))    debug = true;
        else if (args[i].equals("-nonaming")) useNaming = false;   // 不启用 JNDI
        else if (args[i].equals("-help"))     { usage(); return (false); }
        else if (args[i].equals("start"))     starting = true;
        else if (args[i].equals("stop"))      stopping = true;
        else { usage(); return (false); }
    }
    return (true);
}
ⓘ catalina.home 与 catalina.base

catalina.home 是 Tomcat 的安装目录（bin、lib），catalina.base 是一个实例的目录（conf、logs、webapps、work）。一套安装可以跑多个实例，每个实例有自己的 base。两者默认相同。

start：Digester 解析 server.xml

protected void start() {
    Digester digester = createStartDigester();
    File file = configFile();                          // 默认 conf/server.xml
    InputSource is = new InputSource("file://" + file.getAbsolutePath());
    is.setByteStream(new FileInputStream(file));
    digester.push(this);                               // ★ Catalina 压在栈底
    digester.parse(is);                                // 解析完 this.server 就有值了
    ...                                                // JNDI、安全管理器、替换 System.out 等
    Thread shutdownHook = new CatalinaShutdownHook();
    server.initialize();
    ((Lifecycle) server).start();
    Runtime.getRuntime().addShutdownHook(shutdownHook);
    server.await();                                    // 等关闭命令
    Runtime.getRuntime().removeShutdownHook(shutdownHook);   // 先移除，避免 stop 被调两次
    ((Lifecycle) server).stop();
}

digester.addObjectCreate("Server", "org.apache.catalina.core.StandardServer", "className");
digester.addSetProperties("Server");
digester.addSetNext("Server", "setServer", "org.apache.catalina.Server");   // 栈底的 Catalina.setServer(server)

digester.addObjectCreate("Server/Service", "org.apache.catalina.core.StandardService", "className");
digester.addSetProperties("Server/Service");
digester.addSetNext("Server/Service", "addService", "org.apache.catalina.Service");

digester.addObjectCreate("Server/Service/Connector",

digester.addSetProperties("Server/Service/Connector");
digester.addSetNext("Server/Service/Connector", "addConnector", "org.apache.catalina.Connector");
...
digester.addRuleSet(new EngineRuleSet("Server/Service/"));
digester.addRuleSet(new HostRuleSet("Server/Service/Engine/"));

digester.addRule("Server/Service/Engine", new SetParentClassLoaderRule(digester, parentClassLoader));

注意 addObjectCreate 的第三个参数 "className"：server.xml 里任何元素都可以用 className 属性换成你自己的实现类——这正是 Tomcat 可扩展的关键。

stop：只解析 <Server>

停止时用的 createStopDigester() 只有 Server 的三条规则：它只需要从 server.xml 里读出关闭端口和关闭命令，然后像第 14 章的 Stopper 一样连上 127.0.0.1:port 发送命令。

Bootstrap 类

startup.sh 最终执行的是 Bootstrap 的 main 方法。它做两件事：建立类加载器、通过反射启动 Catalina。

commonLoader = ClassLoaderFactory.createClassLoader(
    unpacked /* common/classes */, packed2 /* common/endorsed, common/lib */, null);
catalinaLoader = ClassLoaderFactory.createClassLoader(
    unpacked /* server/classes */, packed /* server/lib */, commonLoader);
sharedLoader = ClassLoaderFactory.createClassLoader(
    unpacked /* shared/classes */, packed /* shared/lib */, commonLoader);

Thread.currentThread().setContextClassLoader(catalinaLoader);
Class startupClass = catalinaLoader.loadClass("org.apache.catalina.startup.Catalina");
Object startupInstance = startupClass.newInstance();

// 反射调用 setParentClassLoader(sharedLoader)：Web 应用加载器的父加载器就是它
Method method = startupInstance.getClass().getMethod("setParentClassLoader",
    new Class[] { Class.forName("java.lang.ClassLoader") });
method.invoke(startupInstance, new Object[] { sharedLoader });

// 反射调用 process(args)
method = startupInstance.getClass().getMethod("process", new Class[] { args.getClass() });
method.invoke(startupInstance, new Object[] { args });
🔑 为什么要用反射调用 Catalina？

Bootstrap 由系统类加载器加载，Catalina 由 catalinaLoader 加载。如果 Bootstrap 的源码里直接写 new Catalina()，编译后 JVM 会用加载 Bootstrap 的那个类加载器（系统类加载器）去找 Catalina——那就要求 Catalina 在 CLASSPATH 上，隔离也就失去了意义。通过反射，Bootstrap 在编译期完全不依赖 Catalina 类。

启动脚本

为了不让用户记住一长串 java 命令行参数，Tomcat 提供了脚本：Windows 下是 startup.bat、shutdown.bat、catalina.bat，Unix/Linux 下是对应的 .sh。startup 和 shutdown 只是把 start / stop 参数传给 catalina 脚本。

catalina.sh 参数作用
run在当前窗口前台运行（日志直接输出到终端）
start后台运行，输出重定向到 logs/catalina.out
stop / stop -force发送关闭命令；-force 时再按 CATALINA_PID 里的进程号 kill -9
jpda start以 JPDA 调试模式启动，可以用 IDE 远程连接调试
debug、embedded、-security在调试器中启动 / 嵌入式模式 / 启用安全管理器（Tomcat 4 时代的选项）

原书花了不少篇幅介绍批处理和 shell 的基础语法（rem、if exist、goto、shift、$1、case、`dirname`……）。catalina 脚本本身做的事情可以归纳为：

  1. 解析符号链接，找到脚本所在目录，推出 CATALINA_HOME；CATALINA_BASE 默认等于它。
  2. 调用 setclasspath 检查 JAVA_HOME，确定 java 可执行文件。
  3. 把 bootstrap.jar 等加入 CLASSPATH，拼出 -Dcatalina.home、-Dcatalina.base、-Djava.io.tmpdir 等参数，加上用户的 JAVA_OPTS / CATALINA_OPTS。
  4. 按第一个参数分支：start 时后台运行并写 PID 文件，stop 时运行 Bootstrap … stop。
elif [ "$1" = "stop" ] ; then
    shift
    "$_RUNJAVA" $JAVA_OPTS $CATALINA_OPTS \
      -Djava.endorsed.dirs="$JAVA_ENDORSED_DIRS" -classpath "$CLASSPATH" \
      -Dcatalina.base="$CATALINA_BASE" \
      -Dcatalina.home="$CATALINA_HOME" \
      -Djava.io.tmpdir="$CATALINA_TMPDIR" \
      org.apache.catalina.startup.Bootstrap "$@" stop
    if [ "$1" = "-force" ] ; then
        shift
        if [ ! -z "$CATALINA_PID" ]; then
            echo "Killing: `cat $CATALINA_PID`"
            kill -9 `cat $CATALINA_PID`
        fi
    fi

② 迷你 Bootstrap：独立的类加载器 + 方法句柄

URL[] repositories = Arrays.stream(System.getProperty("java.class.path").split(File.pathSeparator))
        .map(Bootstrap::toUrl).toArray(URL[]::new);
// 父加载器是平台类加载器：只认识 JDK，不认识 CLASSPATH 上的任何类
var catalinaLoader = new URLClassLoader("catalina", repositories, ClassLoader.getPlatformClassLoader());

Class<?> startupClass = catalinaLoader.loadClass("modern.ch17.startup.Catalina");
Object catalina = startupClass.getDeclaredConstructor().newInstance();

var lookup = MethodHandles.publicLookup();                         // Java 7 的方法句柄
lookup.findVirtual(startupClass, "setParentClassLoader", MethodType.methodType(void.class, ClassLoader.class))
      .invoke(catalina, sharedLoader);
lookup.findVirtual(startupClass, "process", MethodType.methodType(void.class, String[].class))
      .invoke(catalina, args);

运行时会打印「Catalina 由 catalina 类加载器加载（不是加载 Bootstrap 的 app）」——同一个 JVM 里，Catalina 这个类确实来自另一个类加载器。

③ 现代 bash 脚本

PRG="$(readlink -f "$0")"                     # 原书一整段 while [ -h "$PRG" ] 循环解析软链接

case "${1:-}" in
  run)   exec "$JAVA" … modern.ch17.startup.Bootstrap "$@" start ;;
  start) nohup "$JAVA" … modern.ch17.startup.Bootstrap "$@" start \
           >> "$CATALINA_BASE/logs/catalina.out" 2>&1 < /dev/null &
         echo $! > "$CATALINA_PID" ;;
  stop)  run_java "$@" stop ;;
esac

④ 真正的 Tomcat 11 Catalina

RealCatalina 直接使用 org.apache.catalina.startup.Catalina——和原书讲的是同一个类，只是 20 年后的版本。它准备一个临时的 CATALINA_BASE（只放一个 conf/server.xml），然后：

var catalina = new Catalina();
catalina.setAwait(true);       // start() 末尾调用 server.await()
catalina.load();               // createStartDigester() 解析 conf/server.xml，server.init()
catalina.start();              // 启动 → 注册钩子 → await → 移除钩子 → stop（与原书一致）

<Server port="${demo.shutdownPort}" shutdown="SHUTDOWN">
  <Service name="Catalina">
    <Connector port="${demo.port}" address="127.0.0.1" protocol="HTTP/1.1" connectionTimeout="20000"/>
    <Engine name="Catalina" defaultHost="localhost">
      <Host name="localhost" appBase="${demo.appBase}" autoDeploy="true" unpackWARs="true"/>
    </Engine>
  </Service>
</Server>

Tomcat 的 Digester 会把 ${...} 替换成同名系统属性。Host 里没有写 Context，Tomcat 依然部署了 /app1——这是 HostConfig 的功劳，也就是下一章的主题。

ⓘ 现代 Tomcat 的变化
  • 类加载器只剩 common（$CATALINA_HOME/lib）；server.loader、shared.loader 默认留空，可在 conf/catalina.properties 中配置。
  • 脚本把自定义配置拆到 bin/setenv.sh（JAVA_OPTS、CATALINA_OPTS），升级 Tomcat 时不用改 catalina.sh。
  • 安全管理器已在 Java 17 被废弃（JEP 411）、Java 24 起被永久禁用，Tomcat 11 也移除了 -security 支持。
  • Linux 上更多用 systemd 管理 Tomcat：ExecStart=/opt/tomcat/bin/catalina.sh run，由 systemd 负责后台化、日志和重启。

小结

  • 启动链：startup.sh → catalina.sh start → java Bootstrap start → Catalina.process → start。
  • Catalina 用 Digester 解析 server.xml（自己压在栈底，通过 setServer 拿到 Server），然后 initialize → start → 注册钩子 → await → stop；stop 命令只解析 <Server> 并发送关闭命令。
  • Bootstrap 建立 common / catalina / shared 类加载器，用 catalinaLoader 加载 Catalina 并通过反射调用，保证容器类与 Web 应用隔离。
  • 脚本负责环境变量、类路径、前台/后台运行和 PID 文件。

动手练习

  1. 给迷你 Catalina 的 Digester 增加对 className 属性的支持，让 server.xml 能把 Engine 换成你自己写的子类。
  2. 写一个 bin/setenv.sh，在其中设置 JAVA_OPTS="-Xmx256m"，修改 catalina.sh 让它在启动前 source 这个文件（如果存在）。
  3. 复制一份 conf/ 到另一个目录并改掉端口，用 CATALINA_BASE=那个目录 bin/startup.sh 同时运行两个实例。
  4. 为迷你 Tomcat 写一个 systemd unit 文件（Type=simple，ExecStart=…/bin/catalina.sh run），并思考：此时还需要关闭端口吗？
